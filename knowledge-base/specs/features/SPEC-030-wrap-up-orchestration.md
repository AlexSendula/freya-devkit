# Wrap-Up Orchestration

## What

`wrap-up` is the mutating counterpart of `status`: it runs the post-implementation pipeline in
a fixed order and lands the result in two commits. There is no `wrap-up` script. The skill is
prose that an agent follows, and every deterministic guarantee in it is the exit code of a
*different* skill's script — `verify_links`, `adr verify`, `verify_intent`, `behavior-graph
--build/--check`.

The sequence is: code commit (Phase 0) → dependency graph → docs → specs → behavior integrity
and the accepted-behavior run, with the governance checkpoints (Phase 3.5) → security scan
(Phase 4) → artifacts commit (Phase 5). Phase 5 first advances the declared-intent baseline and
regenerates `knowledge-base/BACKLOG.md`, then stages docs, specs, ADRs, resolution logs,
tracking files, the security report and any unaccepted behavior scaffolds.

Phase 3.5 has its own order, and it is the load-bearing one: link and ADR integrity, then the
G1 declared-intent gate, then rebuild-and-run the affected accepted behaviors — all
deterministic and all hard-blocking — and only then the three model-judgment checkpoints, G2
principles, G3 contradictions and P4b declarative drift, each resolve-to-proceed. The rationale
for that split belongs to ADR-009 and is not restated here; what this spec records is that the
order is an observable guarantee of the workflow and that nothing but the agent enforces it.

One claim in the prose has gone stale and is worth knowing before reading it as authority:
`skills/freya-wrap-up/SKILL.md:190` says `behavior.json` is written under "the git-ignored
`knowledge-base/.graph/`". ADR-017 decides the opposite — the directory's own `.gitignore`
names the regenerable files individually and leaves `behavior.json` tracked — and in this
repository `git ls-files knowledge-base/.graph/` returns `behavior.json`. The file is committed.

## Why

The two-commit pattern exists so the security scan has a stable commit to reference and so the
history separates what a human wrote from what a tool generated. The one-commit lag it creates
(`.security-last-scan` points at the code commit; the artifacts commit is one ahead) is
harmless precisely because the artifacts contain no code to scan, and saying so in the skill is
what stops a future maintainer from "fixing" it with a tracking-file hack.

The ordering exists because a wrap-up that is going to fail should fail on facts. Running the
judgment checkpoints first would spend a human's attention adjudicating a principle finding in a
change that a broken link or a red accepted test was going to reject anyway.

## Intentional Design Decisions

### There is no wrap-up engine

**Decision**: `skills/freya-wrap-up/` contains `SKILL.md` and nothing else — no script, no
tests, no entry in `bin/commands.json`. The phases, their order, the staging rules and the
resolve-to-proceed obligations are instructions to an agent.

**Rationale**: The steps are mostly calls into other skills' deterministic scripts, and the
parts that are not — judging a diff against a principle, deciding whether a prior refutation
still applies — are model work by definition. A wrapper script would add a process boundary
around work that is already scripted where it can be, and could not encode the judgment where
it cannot.

**Security Scan Note**: This is the honest ceiling of what this spec can promise, and it should
be read that way rather than as a missing test suite. Nothing prevents an agent from running
Phase 4 before Phase 3.5, skipping the never-synced guard, or completing while a principle
finding is unresolved. The deterministic gates are real because the scripts they call return
real exit codes; the *ordering* of those calls is convention. Do not cite this spec as evidence
that the sequence is enforced.

### A behavior scaffold's commit class follows its lifecycle state, not its directory

**Decision**: A `proposed` or unaccepted scaffold under `features/` is staged with the
artifacts, and joins the code commit only once it is `accepted` and its `TODO(scaffold)` marker
is gone. Specs, ADRs, `INTENT-NNN` records, resolution logs and the backlog are always
artifacts; an accepted test's edit plus its `Intent: INTENT-NNN` trailer is always code.

**Rationale**: ADR-003 — only `accepted` is authoritative, so anything below it is intent under
review regardless of where the file sits. ADR-008 governs the intent record that rides with an
accepted test's edit.

**Security Scan Note**: A `.feature` file in the code tree being committed as a documentation
artifact is intentional. Classify by reading the behavior's `state` in its spec frontmatter,
never by path.

### An incremental update never silently becomes a full generation

**Decision**: If a project has no tracking file — no `knowledge-base/specs/.spec-last-update`,
no `.graph/`, no `.security-last-scan` — wrap-up reports the project as unsynced and either runs
the explicit first-time command deliberately or skips that phase with a message. It must not let
`update` run a full-codebase generation by falling through.

**Rationale**: A surprise full generation on someone's first wrap-up produces a large,
unreviewed artifact commit attached to an unrelated code change, which is how generated content
stops being read.

**Security Scan Note**: The guard is a refusal to do work, not missing initialization. The
remedy is the explicit `scan`/`build` command, run on purpose.

### Wrap-up spends nothing

**Decision**: Phase 4 runs `codebase-security-scan update` only. The `scan` and `audit` modes,
which drive paid agent CLIs, must not run here — including on the first wrap-up of a project,
where `update` deliberately covers the no-baseline case with a full in-loop pass.

**Rationale**: ADR-015 carries the measurement behind this (a single finder worker on a trivial
fixture at $0.396, and a plausible audit budget of ~90 agent calls) and records `audit` as
on-demand and deliberately not part of wrap-up.

**Security Scan Note**: The lighter scan in the routine pipeline is a cost decision, not a
weaker security posture by accident. The exhaustive mode still exists; it is invoked explicitly.

### The graph is rebuilt before the check, and a failed rebuild aborts

**Decision**: Phase 3.5 chains `behavior-graph --build` and `--check` with `&&`, and a failed
build is treated as a blocking error rather than a skipped step.

**Rationale**: `--check` against a stale or absent graph reports a false green — the worst
available outcome for a regression gate, because it is indistinguishable from a passing run.

**Security Scan Note**: The `&&` is load-bearing. Splitting the two commands, or continuing past
a build failure to "at least run the check", converts a hard gate into a rubber stamp.
