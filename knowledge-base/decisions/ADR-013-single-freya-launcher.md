# ADR-013: One self-locating `freya` launcher is the sole command surface

## Decision

Every SKILL.md invokes `freya <command> <args>`. The launcher lives at `bin/freya` in the canonical store, resolves the suite root from `Path(__file__).resolve()` (`bin/freya_cli.py:36`), dispatches via `bin/commands.json`, and executes target scripts with `sys.executable` (`bin/freya_cli.py:108`). One SKILL.md set serves every agent, Claude included — no per-agent variant, no per-agent path variable, no MCP server.

## Rationale

The Claude-specific surface was measured, not estimated: 83 `${CLAUDE_PLUGIN_ROOT}` sites across SKILL.md files — spec-manager 34, wrap-up 25, code-graph 9, behavior-graph 7, codebase-security-scan 4, behavior-runner 2, status 2 (`docs/design/portability/01-design.md:29`, including the 2026-08-18 correction that re-counted security-scan from 3 to 4 and reconciled the total).

Putting the "where am I" logic in one place removes that variable everywhere and fixes a latent bug for free. All 80 script invocations called bare `python` and none called `python3`, and `python` does not exist on many modern systems. The launcher resolves the interpreter once via `sys.executable`, for every agent and every platform.

MCP was evaluated as the alternative surface and dropped: the tools are already local Python CLIs that the agent runs via bash, so a server would be something to build, run and maintain for no gain.

Verified shipped: zero `${CLAUDE_PLUGIN_ROOT}` occurrences remain in any SKILL.md, and `bin/commands.json` dispatches `code-graph`, `behavior-graph`, `behavior-runner`, `status`, `detect-project`, `spec`, `adapters`, `adr`, `contradictions`, `drift`, `intent`, `principles`, `project-shape`, `verify-intent`, `verify-links` and `security`.

## Rejected Alternatives

- **Per-agent path variables and per-agent SKILL.md variants.** Guarantees drift between copies, and the bare-`python` bug would need fixing once per agent.
- **Absolute paths baked into invocations.** Breaks the moment the store moves, is installed elsewhere, or is symlinked.
- **Exposing the suite over MCP.** A server to build, run and maintain in exchange for capability the agent already has through bash.
- **Leaving `${CLAUDE_PLUGIN_ROOT}` on the Claude path and porting only other agents.** Two surfaces, guaranteed drift, and the interpreter bug survives on the most-used path.
- **A first-run PATH bootstrap for the Claude marketplace-plugin path.** Specified as this decision's cost, then deliberately never built, because the premise was wrong. Verified empirically on macOS (2026-08-18): a Claude Code session's `$PATH` already contained `~/.claude/plugins/cache/freya-devkit/freya-devkit/0.1.0/bin`, and it was there even though the cached 0.1.0 snapshot has no `bin/` directory at all — which shows the entry is added by convention rather than discovered (`docs/design/portability/01-design.md:104`). `bin/freya` is mode `100755` in git, so it resolves by bare name. What the decision costs instead is a stated dependency on unversioned host behaviour, remediable with no new code by running `install.sh`, which places the launcher in `~/.local/bin`.

## Revisit Conditions

- If Claude Code stops adding `<plugin-cache>/<plugin>/<version>/bin` to `PATH` — an undocumented host behaviour that nothing in this repo tests and that `freya doctor` structurally cannot check, because doctor only ever runs *through* the launcher it would be checking for.
- If a target agent appears with no shell. That is the one case that makes MCP worth reconsidering.
- Residual gap: Windows resolves bare commands through `PATHEXT` and `bin/freya` is extensionless, so the `freya.cmd` shim is generated by the installer rather than shipped in the store. If that shim proves unreliable, the store layout has to change.
