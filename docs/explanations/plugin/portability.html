Portability

One toolkit, any coding agent

freya-devkit began as a Claude Code plugin. Everything deterministic in it — every Python script — was already portable. The layer that tells an agent how to use those scripts was written for exactly one host. On GitHub Copilot the suite didn't install, and the parts that did wouldn't run.

The one idea

Stop asking each host to understand our layout. Give the suite one self-locating entry point — the freya launcher — and let the instructions speak in commands rather than paths. Then move the parts that depended on a Claude-only runtime into our own code.

What was actually Claude-specific

The track opened by counting rather than estimating. Four surfaces were host-specific, and nothing else was:

The finding that made it tractable

Every Python script already resolved its own location from __file__, and no .py file anywhere used ${CLAUDE_PLUGIN_ROOT}. The engine was portable before anyone tried to port it — which bounded the whole project to the skill layer's markdown, plus one orchestration engine.

Surface 2 being the larger one mattered: the instinct was to treat the path variable as "the port" and the slash references as cleanup. It was the other way round.

The launcher

One stdlib-Python entry point resolves the suite's location from its own __file__ (via realpath, so it survives being reached through a symlink), looks the command up in a checked-in manifest, and runs the target with sys.executable. Sixteen commands are the entire public surface.

A latent bug, fixed for free

All 80 invocations called bare python. On a modern system that binary frequently doesn't exist — only python3 does. Routing every call through one launcher that uses sys.executable fixed a breakage nobody had reported yet.

The manifest is enforced in both directions: a test fails if an entry points at a missing script, and another fails if a script with a __main__ block isn't registered — so a new CLI can't be added and silently left unreachable.

Install: the checkout is the store

There's no build and no copy step. install.sh symlinks each skill directory into the agent's skills directory and places the freya launcher in ~/.local/bin — possible only because the repo's directory names are already the installed names (skills/freya-code-graph/ → freya-code-graph). It does not edit your shell profile: if ~/.local/bin isn't on PATH it prints the line to add, in the shell you are actually in.

This code deletes things in a home directory

So every target is classified before anything is touched, and apply_plan raises before mutating if any target blocks — a half-applied install is impossible.

StatusMeaningAction
createnothing theremake the link

foreigna symlink pointing elsewherereplaced only with --force

Uninstall removes only symlinks that resolve back into this store, so another checkout's links and anything you created survive. --copy mode writes a .freya-install marker naming its source store; a directory without that marker is never removed. On Windows the installer doesn't wait to be told: it probes whether a symlink can actually be created before it changes anything, and switches to --copy itself if creation is refused — Developer Mode off, or an unelevated shell. The launcher is always written there rather than linked, with a freya.cmd beside it, because an extensionless freya is not runnable on Windows.

Keeping it alive

freya update

Fast-forward only. Preconditions first, then fetch, then an explicit "can this fast-forward?" so a diverged store gets its own message rather than git's. Then it re-links — a pull is not an install: a skill added upstream has no link, a deleted one leaves a dangling link, and a copy tracks nothing.

The notify check

At most one ls-remote a day, bounded at 2 s, one line to stderr so stdout stays parseable for the agent that ran the command. It never applies anything — auto-update was rejected outright for a toolkit that gates wrap-up.

freya init

Writes a marker-delimited section into a project's AGENTS.md — the file some ~30 agents read — with the skill table generated from each SKILL.md so it can't drift. Idempotent, CRLF-preserving, atomic, and it never rewrites a byte outside its own markers.

freya doctor

Reports what's installed where, and warns on the two failure modes that look fine from the outside: a link left behind when the checkout moved, and the same skill registered twice because both install paths were used.

An update mid-session is invisible to that session

Agents read their skill list once, when a session starts. A skill added upstream won't appear; one renamed or removed keeps being offered and then fails on use. The fix is a reload, not a restart — /reload-skills in Claude Code, /skills in Copilot. freya update prints this reminder whenever it actually moves the store.

The interesting one: who schedules the fan-out

Three flows fan out to parallel workers — docs-manager (12 document types), spec-manager scan (5 discovery areas), and codebase-security-scan (6 category scanners plus per-finding refutation passes). All three issued parallelism as an unconditional imperative with no fallback written anywhere.

Why prose wasn't enough for the security scan

Asked to run six category scans in parallel, Copilot ran them itself, sequentially — and then reported that it had run them in parallel. The problem wasn't the speed. It was that nothing could tell you whether the fan-out happened, because the agent narrates parallelism either way. Instrumenting the run settled it: zero delegation calls across a 12-way fan-out.

And it isn't a capability gap

Copilot does support subagents. Its own instructions tell it not to use them for "reviews, audits, and summaries" split by labeled area when the scope is small enough to read directly — "regardless of how it divides into separate areas." Six named categories, twelve named doc types and five named spec areas are precisely that shape. A reasonable policy that happens to disqualify exactly our design.

So the scan stopped asking

scan became a preset of the same Python driver that already ran audit: MAX_ROUNDS 5 → 1, everything else shared. One table, one new parameter. No second module — two modes with two definitions of "a finding" would drift, and the cheaper one would drift toward missing things.

ModeDiscovery roundsVerification lensesRuns in wrap-up?
freya security scan --yes13no — paid, on request
freya security audit --yesup to 5 (stops after 2 dry rounds)3no — paid, on demand
no driver — freya-codebase-security-scan update—in-loopyes — git-diff scoped, spends nothing

Neither driver mode runs inside wrap-up. Both spawn headless agent workers and cost real money, so both confirm before spending unless --yes is passed — and an agent shell has no tty to answer with, which is why the skill's prescribed invocations carry --yes and put the money gate in the conversation instead. wrap-up's security step is the skill's update mode, scoped to a git diff and its blast radius and run in the agent's own loop. That holds on a project's first wrap-up too, where there is no previous scan to diff against: update covers it with a full in-loop pass rather than falling into the paid driver.

Rounds, never lenses

The cheaper-looking lever is fewer skeptics. It's a trap: a finding is deleted on a unanimous refutation, and with one lens a single refutation is unanimous — a real vulnerability would vanish silently. The preset takes its saving out of discovery and leaves verification untouched.

docs-manager and spec-manager deliberately keep the prose form. Not for lack of scale — docs-manager fans out to twelve workers against the scan's six — but because their workers write files, and the driver's guarantee rests on workers that can't.

The gate that keeps it portable

A conformance checker runs over skills/**/*.md and skills/**/*.py. Each rule was added red — flagging real violations — and driven green by the work of its phase, so none is decorative.

Zero exemptions, on purpose

R1 and R4 carried exemptions for the audit workflow while it still existed. Deleting the engine removed both exemptions in the same commit. The checker now has none at all — so a single leftover reference anywhere fails the gate. That's what makes "the port is finished" a checkable claim rather than an assertion.

R10 is the one added because a live agent proved it was needed: one skill's description ran 1251 characters against the spec's 1024 limit, so Copilot dropped it — silently, for five phases — while Claude loaded it happily. R11–R13 close the same class from the other side: the frontmatter contract the spec requires, and the Claude-only paths no rule had ever looked at.

The first time it ran on Windows

For most of this project's life both gates above were enforced by prose — "run them before you commit" — and the Windows half of the portability story had never been executed at all. install.ps1, --copy mode and the launcher shim were documented, shipped, and unrun on the one platform they exist for. .github/workflows/ci.yml ended that: 8 jobs on every push — tests and a real end-to-end install, each on ubuntu-latest and windows-latest, each on Python 3.9 and 3.13.

The first Windows leg came back 29 failed

Against a green Linux leg, and every one of the 29 was pre-existing — this was simply the first time the suite had ever executed there. Four root causes, and two were product bugs, not test bugs:

  • Extended-length paths. Windows hands back a symlink target as \\?\C:\… while the source is spelled C:\…, and the installer proved ownership by comparing those strings. So every link it had just created classified as foreign: freya install refused to manage its own install, and relink skipped every agent. 17 of the 29 were downstream of that one comparison. One helper decides it now.
  • Backslash graph keys. The code graph keyed weirddir\x.ts, so every forward-slash lookup missed. Wider than one skill — behavior-graph and behavior-runner read those keys expecting forward slashes, so blast radius came back silently empty on Windows.
  • remove_link retried a failed unlink as rmdir unconditionally. On Windows the fallback succeeded, so a failed removal was reported as a successful one.
  • The manifest escape guard leaned on the interpreter. It used os.path.isabs, and 3.13 changed ntpath.isabs so a rooted path with no drive is no longer absolute on Windows: /etc/passwd was rejected on 3.9 and accepted on 3.13. A guard on a trust boundary, holding by accident.

All 29 are fixed and the matrix is green. But the honest lesson isn't the fix count — it's that two further sites were found by review, and CI structurally could not have caught either: cmd_shim_plan is Windows-exclusive, so no POSIX run reaches it, and is_git_store was latent. Neither could ever turn a leg red. Both would have shipped broken behind a green build.

What CI proves is that the toolkit installs on Windows and its own tests pass there. It does not prove a live scan works there: the agent CLIs aren't installed on the runner, and no agent has ever driven a skill on Windows.
