portability · phase 5 · 14 Aug 2026

Ten tasks. Eight needed a second pass — and the plan was wrong more often than the code.

Phase 5 added the three commands the design had promised since the beginning: freya update, a notify-only staleness check, and freya init. It also made doctor able to see the one failure a user cannot diagnose from the symptom. This page is the phase on its own — what shipped, every finding, and what none of it proves yet.

What it added

Two new modules, bin/updater.py and bin/agents_md.py, plus changes to the launcher and the installer. Nothing in the engine moved.

CommandWhat it doesWhat it refuses
freya update Fast-forwards the store, then re-links every agent that already has the suite: new skills linked, deleted ones pruned, copies refreshed one at a time. No git, not a checkout, no upstream, a dirty tree, a diverged branch, an unreachable remote — each with its own message, exit 2.
the notify check At most one ls-remote a day, under a 2 s timeout, printing one line to stderr. It never applies anything. FREYA_NO_UPDATE_CHECK=1, a non-git store, and every command that would act on the notice.
freya init Writes a freya-devkit section into a project's AGENTS.md, between HTML comment markers, with the skill table generated from each SKILL.md so it cannot drift. A malformed managed block — it changes nothing rather than guessing where a half-written one ends.
freya doctor Now reports the install mode per agent, and names entries pointing at a store that is not this one, or at a skill this store no longer has. —
Why re-linking is not optional

A symlink picks up edits inside a skill for free, which makes it tempting to believe a fast-forward finishes the job. It does not. A skill added upstream has no link at all, one deleted leaves a dangling link behind, and a --copy install tracks nothing whatsoever. update is a pull and a re-install, or it is a lie.

The review that ran before any code

new this phase

Three things the plan mandated were sent to an adversarial reviewer before implementation started, because each was the kind of choice a reviewer would later call a bug. Two of the three were wrong, and one hid a wrong answer rather than a style problem.

📴

"That error path can't be tested honestly"

The plan left the failed-fetch branch uncovered and forbade mocking it. But delete that guard and the flow reaches merge-base against the stale local ref, which succeeds — so an offline machine prints "already up to date" and exits 0 over a store that is not. Not a coverage gap: a wrong answer, and the one this command must never give. The test that now pins it uses a real repository with failure injected at the fetch call alone.

🗑️

"It matches the existing precedent"

The copy refresh deleted every copied skill, then re-copied them all. The defence was that apply_plan's --force path already deletes before writing. It does — for one target, so its window is one copy long. The plan's was the entire suite for the length of ten. Now it removes and rewrites one skill at a time.

The third — a bare except Exception in the update check — survived, with two corrections: the write to stderr moved inside the guard, because a broken pipe was escaping a function whose whole contract is that nothing escapes; and FREYA_DEBUG now prints the traceback, because a permanently broken check was otherwise indistinguishable from "no update available" forever.

The one that could not heal itself

relink called apply_plan with force=False, which raises RuntimeError for an occupied target — caught by nothing, so it surfaced as a traceback after orphan removals had already run. And it was self-perpetuating: a copy that failed partway leaves a directory with no marker, which audits as occupied forever, so every future freya update crashed at the same place and never recovered.

The pattern: guards misfiring at the people they protect

Every serious defect in this phase was in code written to protect the user, doing damage in a case its author hadn't pictured.

🚧

The barrier that half-installed

Added so a blocked second agent could not leave the first installed. Planning everything up front to achieve that made every plan's status stale — and produced a partial install by a different route.

🔒

The rule that locked you out of your own file

Markers had to be unambiguous so a stray one could not delete a user's prose. The fix counted marker text anywhere — so a user who merely wrote about freya-devkit in their AGENTS.md could never run init again. Being over-strict about a file you do not own is its own kind of damage.

🏠

The check that could not break a command

Built to be unable to affect anything it precedes. Wiring it in front of main silently turned four existing tests into ones that wrote the real ~/.freya and called the network — confirmed by the file sitting on disk with the test run's timestamp.

📄

The write that emptied the file first

open(target, "w") truncates before it writes, so a failure mid-write left the user's AGENTS.md empty — in the one module whose single hard rule is that everything outside its markers survives. Now a temp file and os.replace.

One error class, three separate times

freya_cli.main catches (OSError, ValueError) and reports "cannot read the command manifest — run freya doctor". Three times this phase, an unrelated failure fell into it: a throttle-file write on an unwritable $HOME after a successful update, an unreadable SKILL.md during init, and a half-written install during relink. Each was fixed where it arose. A catch-all that names one cause will keep collecting others; that is a design note for phase 6, not a bug that is now closed.

What this phase still cannot prove

🌐

freya update has never reached a real remote

The branch it was written on had no upstream, so the command's central path had only ever run against local fixtures. Retired by phase 6: once pushed, it fast-forwarded from GitHub for real, and every refusal was observed in the field. The run →

⏱️

The hang paths are untestable by design

Injecting a return value cannot reproduce a stall, and a sleeping fixture buys a slow suite and no information. The 2 s ls-remote bound and the 60 s fetch bound are unexercised. Phase 6 can pull the network cable; nobody will sit out the 60 s one.

🪟

Windows, still

--copy is the mode relink exercises hardest and the least exercised path in the project. os.replace, symlink privilege and install.ps1 remain unrun. Since resolved — and this card was pointing at the right place: when CI finally ran Windows, the installer's ownership check misread every link it had created, and relink was one of the two commands it broke. 🤖

Whether re-linking is even enough

The question update exists to answer: does a coding agent pick up a re-linked or re-copied skill without a restart? If Claude Code or Copilot caches its skill list per session, the command is correct and still not useful. Only a live run decides that.
