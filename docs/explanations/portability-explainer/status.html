Windows finally ran it. The first run failed 29 times.

This page is deliberately unflattering, and for the first time most of it is evidence rather than claim. The toolkit has been installed from a clean clone, updated from a real remote, and driven through both Claude Code and GitHub Copilot — which immediately found the security scanner missing on Copilot, silently, for five phases. Phase 6's worst finding, that Copilot will not delegate a fan-out and will say it did, was fixed in phase 7 by taking the scheduling away from the agent. The line every previous version of this page ended on — what remains untested is Windows — is now out of date: CI runs the suite, the conformance gate and a real install on Windows and Linux on every push, and all eight jobs are green. Getting there cost 29 test failures and four root causes, two of them product bugs rather than test bugs. What is still not covered is listed below, and it is no longer the platform itself.

Three questions this page asked, now answered

Is the permission guard reachable on every argv path? Yes — both adapters return through _guard, and make_ask is the only place a subprocess is spawned. No bypass.
Does the unlocked Budget matter? Measurably, no: 40 trials × 16 threads at a 1 µs switch interval produced zero overrun, and in production every thread sits in subprocess.run for seconds between spends. It took a lock anyway, because the cost is one line.
Is the Python a faithful port? Almost — one undocumented divergence (finding 5) and one lost property (finding 4), both now closed.

Windows, run at last — and it was waiting on code after all

Every previous version of this page said Windows needed a machine and no code. That was wrong, and it was wrong in the way this page exists to catch: an untested claim reads exactly like a tested one until something runs it.

There is now a CI workflow. It runs 8 jobs — the test suite plus the conformance gate, and a separate end-to-end install, each on ubuntu-latest and windows-latest, on Python 3.9 and 3.13 — on every push. All eight pass. The install job is not a smoke test: it drives the documented entry point, asserts a skill resolved through the link, resolves freya by name off PATH, runs doctor, then uninstalls and checks nothing was left behind.

The first Windows run: 29 failures, all pre-existing

Nothing regressed. This was simply the first time the suite had ever executed on the platform, and the failures had been sitting in the tree for the whole track. Four root causes account for all 29 — and two of them were product bugs, not test bugs.

A caveat this page owes you: that run is no longer available. The earliest CI run you can reach is b629a46, which is already after the first batch of fixes — so the 29 is sourced from the commit body of b629a46 and from this page, not from anything you can click. Every figure below it, and the eight green jobs, are still checkable.

Worth noting which jobs failed. On that first run both Windows install jobs passed; only the two Windows test jobs went red. The thing this site had spent seven phases apologising for — install.ps1, never once executed — worked first time, because phase 3 deliberately left no logic in it. The breakage was in the Python that had been reviewed repeatedly and read correctly every time.

Root causeWhat it actually brokeKind
Extended-length paths. Windows hands back a symlink target as \\?\C:\… while the source is spelled C:\…, and the installer proved ownership by comparing those two strings. Every link the installer had just created classified as foreign. So freya install refused to manage its own install, and relink skipped every agent. 17 of the 29 were downstream of this one comparison. product bug
Backslash graph keys. The code graph keyed weirddir\x.ts, so every forward-slash lookup missed. Wider than one skill: behavior-graph and behavior-runner read those keys expecting forward slashes, so blast radius came back silently empty on Windows — the failure mode with no error attached. product bug
remove_link retried a failed unlink as rmdir, unconditionally. On Windows the fallback succeeded, so a failed removal was counted as a successful one and relink reported failed=0 while nothing had been removed. The fallback is now gated on Windows, where DeleteFileW genuinely refuses a directory reparse point. reporting
The manifest escape guard used os.path.isabs. Python 3.13 changed ntpath.isabs, so a rooted path with no drive is no longer absolute on Windows: /etc/passwd was rejected on 3.9 and accepted on 3.13. A guard on a trust boundary that held by accident of the interpreter. It now judges every value with both path flavours on every host. trust boundary
And two that CI structurally could not have caught

Both were found by review, not by the runner, and neither could ever have turned a leg red. cmd_shim_plan is Windows-exclusive — no POSIX run reaches it at all — and is_git_store was latent. They would have shipped broken behind a green build. That is the part worth keeping: a green matrix is evidence about the paths the matrix executes, and adding the platform did not make it evidence about everything on that platform.

The suite went from 758 to 935 passing across the same 24 files over this work and the branch review that preceded it. On CI, Ubuntu reports 934 passed / 1 skipped and Windows 931 passed / 4 skipped. Both skip the one test that needs macOS/BSD file flags; Windows skips three more, two for POSIX mode bits and one for POSIX signal semantics, none of which exist on the platform. Every skip names a capability the host lacks, not a test that was switched off to get a green tick.

What has never been proven

Phase 6 retired three of the five claims that stood here and answered a fourth in the negative, and CI has now retired the Windows claim that outlived them all. What is left is listed as risk, not reassurance.

🪟

No agent has ever run on Windows

CI proves the toolkit installs there and that its tests pass there. It does not prove a scan works there: the agent CLIs are not installed on the runner, so no live freya security scan, no wrap-up, nothing that spends money has executed on the platform. Every live-agent claim on this page is a claim about macOS. The two Windows-only paths that had never executed have now — install.ps1, the freya.cmd shim resolved by name off PATH, and the symlink probe — but the shim proving the launcher runs is a long way from an agent driving the suite through it.

🔀

Two install modes, each untested on one platform

CI runs symlink mode on Linux and --copy mode on Windows, which mirrors how each platform is actually used — and therefore leaves the other diagonal blank. Linux --copy and Windows-with-Developer-Mode symlink installs are both uncovered. The second is the more interesting gap: --copy is not the Windows default, it is the fallback the installer switches to itself when the platform refuses a symlink, so the path a Developer-Mode machine actually takes is the one nothing has run.

📄

Whether Copilot delegates at scale

Instrumented in phase 7: a twelve-way docs-manager fan-out invoked task and explore zero times. Copilot's own sub-agent instructions say why — never delegate a review "small enough to read directly, regardless of how it divides into separate areas". But both clauses are conditioned on small scope, and every fixture used has been small. On a large codebase its policy would permit delegation. Untested, and it is the only version of this question left open.

🔁

audit's loop-until-dry, live under phase 7 code

Phase 7's single audit run hit its findings cap inside round 1, so the multi-round path never ran on the wire in this build. Five offline tests pin it and phase 6 exercised it live, but that is inference across a code change, not evidence.

Carried as unproven since phase 5 and closed by holding a real interactive session open while a skill's link moved: the registry is snapshotted at session start, the body is read from disk at invocation. The honest summary

The port was structurally complete before phase 6: nothing in the shipped skill layer names a Claude-only construct, the conformance gate has no exemptions left, and the Workflow engine is deleted rather than bypassed. What it lacked was evidence. It now has most of it — installed from a clean clone, updated from a real remote, and driven live through both agents.

And the evidence immediately earned its cost. The first question put to Copilot returned nine skills instead of ten, and the missing one was the security scanner — installed, linked, and silently dropped for a description 227 characters over a limit Claude Code doesn't enforce. Five phases of work, 700-odd passing tests and a nine-rule conformance gate had all failed to notice, because none of them had ever asked the agent. R10 — the rule that catches it — exists because of that question; it was not there to miss it.

That is the shape of the whole track's lesson, stated five times now. Phase 4b: the defects were at the driver's edges, not in its logic. Phase 5: the defects were in guards misfiring at the people they protect. Phase 6: the defects were in what the host does with a correct artefact. Phase 7: the defect was in believing what the host said it did — which is why the fan-out stopped being a request and became a worker pool. And now Windows: the defects were on the platform nobody had run, in code that had been reviewed repeatedly and read correctly every time, because reading cannot tell you that os.readlink returns a different spelling of the path you gave it. Everything above the line is verified. Everything below it is still a claim — and there is less below the line than there has ever been.
