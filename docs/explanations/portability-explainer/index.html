freya-devkit · portability

The engine was already portable. The instructions were not.

freya-devkit is a suite of AI-assisted development skills — dependency graphs, docs, specs, a behavior layer, security scanning, a wrap-up workflow. Every deterministic part was plain stdlib Python that would run anywhere. But the layer that tells an agent how to use those scripts was written for exactly one host. On GitHub Copilot it didn't install, and the parts that did wouldn't run.

The problem, measured

The initiative started with a claim that sounded plausible and turned out to be wrong: "it's a Claude plugin, so porting it is a rewrite." The first real step was to stop estimating and count. Four surfaces were Claude-specific — and nothing else was.

The finding that made this tractable

Every Python script already resolved its own location — Path(__file__).resolve().parents[2] — and no .py file anywhere used ${CLAUDE_PLUGIN_ROOT}. The engine was portable before anyone tried to port it. That bounded the whole project to the skill layer: markdown, plus one orchestration engine.

Surface 2 being larger than surface 1 mattered more than it looks. The instinct was to treat the ${CLAUDE_PLUGIN_ROOT} paths as "the port" and the slash references as cleanup. It was the other way round, and planning it backwards would have mis-sized the work.

A bug found for free

All 80 script invocations called bare python. On a modern system that binary frequently doesn't exist — only python3 does. Routing every call through one launcher that uses sys.executable fixed a latent breakage nobody had reported yet.

The one idea

Stop asking each host to understand our layout. Give the suite one self-locating entry point, and let the instructions speak in commands rather than paths.

That single move de-Claude-ified both invocation and path resolution at once:

The inversion at the centre of it

Three of the four surfaces were substitutions. The fourth was a genuine architectural change, and it's the most interesting thing in the track.

The audit mode ran on Claude's Workflow tool: a Claude-owned runtime executed a JavaScript file that called our logic. Its rigour lived precisely in the deterministic parts — loop-until-dry discovery, cross-round dedup, N-skeptic majority voting. Expressed as prose for another agent, those guarantees become suggestions.

Before — the host owns the loop

Claude Workflow runtime ↓ calls our agent() steps

Portable to exactly one host. Untestable — the loop only existed inside a runtime we didn't control.

After — we own the loop

our Python driver ↓ calls any agent CLI, headless

Runs on Claude or Copilot. The engine takes an injected ask callable, so its logic is unit-tested offline for free.

Why this was worth doing rather than dropping

Reading the 143-line workflow settled it: roughly 90 % was ordinary logic — a while loop, a Set for dedup, upheld * 2 > total vote arithmetic, a disposition ladder. Only the agent(…) call itself was Claude-provided. The port was mostly relocation, and it made the engine testable for the first time.

What we refused to do

Three deliberate non-goals kept the scope honest.

🚫

No MCP server

Considered and dropped. Our tools are local Python CLIs an agent runs via bash. MCP would add a server to build, run and maintain for no gain. Worth revisiting only for a shell-less agent.

🔗

No dependency on skills.sh

The ecosystem installers are built for single skills and fit a coupled suite poorly — the documented "install related skills independently → behavioural drift" problem. We reused their store-plus-symlink pattern, not their tooling.

🤖

No auto-updating

An update that silently pulls latest main onto a work laptop mid-task is exactly wrong for a toolkit that gates wrap-up. Manual freya update, with a throttled notify-only check.

🪟

No pretending about Windows

An install.ps1 ships, deliberately thin — interpreter discovery and delegation only. For seven phases it had never been run, and this site said so rather than implying otherwise. CI now runs it on every push; the first Windows run failed 29 times. The record →

Where it got to

All seven phases are on the branch, the last two of them validation and the fix it forced. The numbers below are counted from the working tree, not estimated.

131 commits

On feat/polyglot-portability, pushed on 14 Aug after 97 of them had lived on one machine — which is also what finally gave freya update a remote to fetch from. Still not merged.

8,014 lines added

Across 22 new files: the launcher, the installer, the conformance checker, the two install scripts, the four audit-driver modules, and phase 5's updater and AGENTS.md writer — with their tests.

935 tests · 24 suites

All passing, and now on CI across Linux, Windows and Python 3.9/3.13. Not one invokes a real agent CLI or touches the network — tested entirely offline by design, which is also the reason the audit driver's failure paths went unexamined for a phase. Nine mutations were introduced and reverted in phase 7 alone to prove the new tests fail when their guard is removed.

1 file deleted

workflows/codebase-security-audit.js. Its removal is the proof the port is complete rather than parallel.

Not finished

All seven phases are on the branch. Phase 6 ran the toolkit live on both agents — which immediately found the security scanner missing on Copilot, silently, for five phases, and then found that Copilot would not delegate a fan-out and would say it had. Phase 7 fixed that by taking the scheduling away from the agent, and ran the last two flows that had never been run, docs-manager and spec-manager scan.

The line that used to end this paragraph — one thing remains untested: Windows — no longer holds. CI runs the suite, the conformance gate and a real install on Linux and Windows on every push, all eight jobs green. It cost 29 failures and four root causes to get there, two of them product bugs, which is rather more than the "needs a machine, not code" this site had been claiming.
