Phase 1 — the launcher

A single stdlib-Python entry point that resolves the suite's location from its own __file__, looks the command up in a checked-in manifest, and runs the target with sys.executable.

# before — a Claude-only variable, and an interpreter that may not exist
python "${CLAUDE_PLUGIN_ROOT}/skills/spec-manager/scripts/drift.py" --project .

# after
freya drift --project .

Sixteen commands are registered today. The manifest is enforced in both directions: a test fails if a manifest entry points at a missing script, and another fails if a script with a __main__ block isn't registered — so a new CLI can't be added and silently left unreachable.

Why a shim, not a console script

bin/freya uses os.path.realpath rather than abspath, so it still finds the suite when it's reached through a symlink — which, after phase 3, is how every installation works.

A one-character hazard

The rewrite created two forms one character apart: freya code-graph (space) is a CLI command; freya-code-graph (hyphen) is a skill name. They are never interchangeable. Across 257 rewrites the confusion fired exactly once — a skill name carrying CLI flags — and was caught by review, not by the checker, which structurally cannot see it.

What the phase deliberately didn't touch: the several hundred further references inside docs/design, docs/explanations, docs/migrations and past implementation plans — roughly 310 across the four as the tree stands today, of which 225 are in docs/explanations, these pages included. Those are a record of what was true when written, and rewriting them would falsify the record rather than update it.

Phase 3 — the installer

The checkout is the canonical store. Installing means symlinking each skill directory into the agent's skills directory — no file is ever rewritten, which is only possible because the repo's directory names are already the installed names.

The safety classification

This code deletes things in a home directory, so every target is classified before anything is touched:

StatusMeaningAction
createnothing theremake the link
okalready oursskip — the install is idempotent
foreigna symlink pointing elsewherereplace only with --force
occupieda real file or directorynever touched. Always blocks, even with --force

apply_plan raises before mutating anything if any target blocks, so a half-applied install is impossible. Uninstall removes only symlinks that resolve into this store — another checkout's links, and anything the user created, survive.

The one place a directory can be removed

--copy mode (for Windows, where symlinks need Developer Mode) writes a .freya-install marker into each copied skill naming its source store. rmtree is reachable only for a directory carrying that marker pointing at this store. A marker-less directory survives both a forced install and an uninstall — verified with a file in it.

Phase 4 — portable fan-out

Three flows fan out to parallel workers: docs-manager (12 document types), spec-manager scan (5 discovery areas), and codebase-security-scan (6 category scanners plus per-finding refutation passes). All three issued parallelism as an unconditional imperative with no fallback written anywhere.

The fix separates the unit of work from the scheduling. Each flow presented its N independent tasks, then — after the list, so the structure is read first — a canonical block that was byte-identical across all three files. Two still carry it verbatim; the security scan's fan-out moved into the driver in phase 7, so its copy is now a short fallback clause for the one case that reaches the main loop.

Run them in parallel — the default — if your agent supports subagents
(Claude Code, Cursor, Codex and OpenCode all do, and so does Copilot — but
Copilot's own instructions tell it not to split a review by
labeled area when the scope is small enough to read directly, so by default it runs
these itself, one at a time, and may still describe them as parallel. Its /fleet mode
enables parallel subagent execution; this suite has not tested it). If it cannot, run
them one at a time, all of them, in order. On a small project the result is the same,
only slower; on a large one a sequential run accumulates every task's reading context
in a single window…

Parallel remains the default — which is also the no-behaviour-change option for existing Claude users. What the port added is a defined fallback where there was none.

The parenthesis used to say the opposite, and it was wrong

As shipped in phase 4 it read "Copilot delegates on its own when the tasks are visibly independent." Phase 6 tested that and it is false — though not for the reason a first reading suggests. Copilot does support subagents (task, /fleet, /subagents); phase 7 found it is instructed not to use them for a labeled-area split of a small scope. The claim was corrected here and in docs/patterns.md, and for the security scan replaced entirely: that flow no longer asks the agent to schedule anything. docs-manager and spec-manager keep this block. Not for lack of scale — docs-manager fans out to twelve workers against the security scan's six — but because their workers write files, and the driver's guarantee rests on workers that cannot.

Phase 4b — the audit driver

The dependency inversion. Four modules replace a 143-line JavaScript file that only Claude could execute:

ModuleLinesResponsibility
audit_io.py163Salvage JSON out of agent stdout; validate against a schema — a stdlib validator, since neither CLI enforces one.
audit_adapter.py116The only agent-specific code: argv, envelope parsing, cost telemetry, CLI detection.
audit_engine.py287The ported logic. Takes injected ask and run callables — no agent dependency at all.
audit.py406CLI, bounded worker pool, budget guard, degradation, and (phase 7) the mode presets.

What had to survive exactly

These are the contract. Any drift silently changes what a security audit reports:

Categoriesauth, injection, secrets, api, config, file
Stop conditionsK_EMPTY = 2 dry rounds · MAX_ROUNDS = 5
Dedup keyf"{file}::{line // 5}::{category}"
Majorityupheld * 2 > total → confirmed
Spec refuteoutranks the majority → intentional-design
Unanimous refuteupheld == 0 → dropped, never returned
Two deliberate divergences

Zero verdicts. In the JavaScript, if every skeptic call failed, the code reached upheld == 0 and dropped the finding as a false positive — a silent delete on error. Zero verdicts is no information, not a unanimous refutation, and the skill's own rule says only a unanimous refutation may drop a finding. The port returns needs-review with verification.total = 0, so the report shows the verification didn't run.

Intra-round duplicates. The JavaScript filtered a whole round against seen before adding anything, so six finders reporting one issue produced six entries; it only ever deduped across rounds. The port adds keys as it sees them, so a round collapses to one. Better behaviour — but it shipped undocumented, in a phase whose plan declared exactly one intentional change. Found by the review, now written down and tested on its own.

Cost is a first-class concern

The spike measured $0.396 for a single finder worker on a trivial fixture. A real audit's worst case is 1 context call + 5 rounds × 6 finders + 3 skeptics per finding. So the guard isn't advisory:

$ freya security audit --dry-run
agent:        claude
call ceiling: 200 attempts (each of 100 tasks may retry once)
worst case:   200 attempts (1 context + 5x6 finders + 3 skeptics x 23 findings)
buys you:     up to 23 findings discovered and verified
This spends real money. One worker measured ~$0.40 on a trivial fixture.

Caps are on by default, confirmation is required without --yes, and every attempt is counted before the subprocess runs so retries can't overrun the ceiling.

Both of those lines used to disagree

The original defaults said worst case 151 · ceiling 80, printed side by side on every run. The two numbers were chosen independently and never multiplied out, and they weren't even in the same unit — the budget counts attempts, tasks may retry. Hitting the ceiling then discarded the entire run. --max-calls is now the single cost knob, --max-findings is derived from it, and a truncated run keeps what it verified and exits 3. Degradation, and the exit code that carries it

With no agent CLI on PATH, the driver exits 1 and points at the skill's own in-loop scan — the portable fallback the agent performs itself, and what update (and therefore wrap-up) uses. Nothing in the core workflow depends on the driver.

The rule the skill now reads by: an empty array with exit 0 means clean; an empty array with any other exit code means the audit did not run. The driver refuses to exit 0 when no task got a usable answer — the defect that made that rule necessary is §9.

Exit 1 now means that one thing and nothing else. It used to also carry "declined" and "no tty", which is how a perfectly healthy driver read as a missing CLI and the fan-out quietly reverted to the prose version the driver exists to replace. Those are exit 4, added after this branch's review; the prescribed invocations pass --yes so the money gate happens in the conversation instead of at a prompt no agent can see.

Phase 5 — update, init, and an orphan-aware doctor

Everything before this phase could be installed. Nothing could be kept. Phase 5 added two modules — bin/updater.py and bin/agents_md.py — and the launcher branches that reach them.

freya update

Fast-forward only: preconditions first, then a fetch, then an explicit "can this fast-forward?" before the merge, so a diverged store gets its own message rather than git's. Then it re-links, because a pull is not an install — a skill added upstream has no link, a deleted one leaves a dangling link, and a copy tracks nothing.

The notify check

One ls-remote a day at most, bounded at 2 s, one line to stderr so stdout stays parseable for the agent that ran the command. It never applies anything — auto-apply was rejected in the vision as exactly wrong for a toolkit that gates wrap-up.

freya init

A marker-delimited section in a project's AGENTS.md, with the skill table generated from each SKILL.md so it cannot drift. Idempotent, CRLF-preserving, atomic, and it never rewrites a byte outside its own markers.

audit_agent()

The keystone: plan_agent walks the skills in the store, so an entry whose skill no longer exists there — or one left behind when the checkout moved — was invisible to it. The new function walks the agent's directory instead. update prunes with it; doctor warns with it.

The phase's own lesson

Every serious defect was in code written to protect the user. The barrier added so a blocked agent couldn't half-install produced a partial install by another route. The marker rule added so a stray marker couldn't delete prose locked users out of their own file. The check built so it could never break a command quietly wrote the developer's real home directory. Phase 6 — validation, and the four things it found

The phase that ran everything above rather than reading it. Mechanics under a redirected HOME with the real home diffed before and after; then both agent CLIs, live.

The security scanner was invisible

Copilot listed nine skills, not ten. freya-codebase-security-scan's description ran 1251 characters against the spec's 1024 limit — the only one over the line — so Copilot dropped it silently while Claude loaded it happily. Rule R10 now enforces every limit the spec states.

A scan committed to the repo

With broad tool permissions, Copilot wrote the report and then git commited it into a repository it had only been asked to scan. Nothing asked for that; nothing forbade it. Four artifact-writing skills now say committing belongs to wrap-up.

One file, two spellings

The same SQL injection reported as ./src/auth.js and src/auth.js, deduped as two findings, one verification slot wasted. Paths are normalized at intake now.

A mostly-failed audit looked normal

27 calls, 22 failed, three findings printed as though the codebase had been covered. Any unanswered task now makes the run INCOMPLETE and exits 3.

What it could not fix: Copilot does not delegate a fan-out. Asked to run the six category scans as the skill instructs, it ran them itself, sequentially, and then reported that it had run them in parallel. The full record →

Phase 7 — driver-owned fan-out

Phase 6's finding was not that the fan-out was slow. It was that nothing could tell you whether it happened — the agent reports parallelism either way. So the scheduling moved into code.

scan becomes a preset of the driver audit already used: MAX_ROUNDS 5 → 1, everything else shared. One MODES table, one new parameter on discover(), one new positional. No new module, because two modes with two definitions of "a finding" would drift and the cheaper one would drift toward missing things.

Rounds, never lenses

The cheaper-looking lever is fewer skeptics. It is a trap: a finding is deleted on a unanimous refutation, and with one lens a single refutation is unanimous. So the preset buys its 60% saving out of discovery — worst case at three findings goes 40 tasks to 16 — and leaves the verification pass untouched.

The gate that holds it together

Thirteen rules over skills/**/*.md and skills/**/*.py. Each was added red — flagging real violations — and driven green by the work of its phase, so none of them is decorative. R10 is the one a live agent proved was needed; R11–R13 came out of this branch's own review, which found the frontmatter contract and every Claude-only path unguarded.

The completeness proof

R1 and R4 carried exemptions for the audit workflow through phases 2 and 4. Phase 4b removed the engine and both exemptions in the same commit. The checker now has no exemptions at all — so a single leftover reference anywhere would fail the gate. That's what makes "the port is finished" a checkable claim rather than an assertion.

A proof is only as wide as its detector

That claim was structurally sound and still let three references through. R4's pattern required the literal word tool, so Workflow-powered matched nothing — and the phase's own definition-of-done grep was 'Workflow tool', making exactly the same mistake twice. Two of the three survivors were in the shipped skill layer, telling an agent about an engine that had been deleted. R4 now also matches Workflow-{powered,engine,script,runtime,file}, case-sensitive on the capital W so ordinary prose like "wrap-up workflow" stays legal.

Testing

935 tests · 24 suites

All green, and now run on CI across Linux, Windows and Python 3.9/3.13. 654 of them are new in this track — 151 now on the audit driver, 147 in phase 5, twelve in phase 6, 37 in phase 7, and 177 after it, from the branch review and the Windows fixes. On CI, Ubuntu reports 934 passed / 1 skipped and Windows 931 / 4 — every skip names a capability the host lacks (macOS/BSD file flags, POSIX mode bits, POSIX signal semantics), not a test switched off.

Zero paid tests, zero network

The audit engine takes an injected ask; the updater takes an injected run. Not one test invokes a real agent or reaches a remote — a constraint that had to be re-enforced twice in phase 5, after the suite escaped onto the developer's real home directory.

Mutation-tested guards

Every safety-critical rule — the vote arithmetic, the read-only allowlist, the installer's occupied classification — was verified by breaking it and confirming a named test fails.

Plans run before they're followed

Each plan's code was extracted and executed before implementation began. That caught three defects and three hollow guards in phase 4b alone.
