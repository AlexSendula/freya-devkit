portability · the phases

Eight phases, each with its own record.

Every phase produced something independently testable and left the toolkit working on Claude throughout — there was never a window where the suite was broken "until the port lands". Start anywhere; each page stands alone and says what that phase got wrong as well as what it built.

In order

The design named six phases. Two more appeared once reality intervened: 4b, when a fourth Claude-only surface turned up mid-track, and 7, when validation disproved a premise phase 4 was built on.

Five commits after phase 7 belong to no phase at all — a review of the whole branch, and the CI that followed it. They are not listed below and have no page of their own, because they had no plan document and were not scoped as a phase; calling them one after the fact would be tidier than it is true. Phase 1 · 13 commits

The freya launcher

One self-locating entry point replaces a Claude-only path variable. The keystone every later phase assumes — and a one-word difference between abspath and realpath that would have broken every install.

 Phase 2 · 16 commits

De-Claude-ify the skill layer

80 invocations and 177 references rewritten across ten skills, with the conformance checker written first and deliberately red so the rewrite had an objective finish line.

 Phase 3 · 15 commits

Rename, then the installer

The phase where the design turned out to be impossible. One sentence in the Agent Skills spec forced a rename of all ten skills — and made the installer simpler than planned.

 Phase 4 · 10 commits

Portable fan-out

Separate the unit of work from the scheduling, and add rule R9 so the old form cannot come back. Correct in every respect except its central assumption, which phase 6 disproved.

 Phase 4b · 11 commits

The audit driver

A dependency inversion: a Claude-only runtime owned the loop and called our logic; now our logic owns the loop and calls the agent. 143 lines of JavaScript deleted, not bypassed.

 Phase 5 · 24 commits

update, init, orphan-aware doctor

The store can refresh itself. Eight of ten tasks came back from review with findings — and nearly every one was a defect in the plan, not the implementation.

 Phase 6 · 7 commits

Validation, on real agents

Run for the first time rather than read. Four defects no offline suite could reach — beginning with the security scanner being invisible on the agent the whole track was built for.

 Phase 7 · 13 commits

Driver-owned fan-out

The answer to phase 6's worst finding. Stop asking the agent to schedule the work; schedule it in code. Instrumented until the reason was found in the host's own system prompt.

Before phase 1 — the design, and a paid spike

Five commits before any code. They counted the Claude-only surfaces instead of estimating them, resolved four design decisions, and — critically — spent real money on a spike against both agent CLIs before committing to the audit port.

The spike earned its cost immediately

It proved the headless adapter was viable, which is what let phase 4b be planned at all. It also turned up the finding that shaped every worker invocation since: GitHub's "deny beats allow" applies to the write tool, not to writes performed through the shell. --allow-all-tools --deny-tool=write let a worker create a file with a shell redirect. Only an explicit allowlist that excludes the shell held.

That is why audit_adapter.py refuses to emit a blanket permission flag even if one is smuggled in through a prompt — a guard designed before the thing it guards existed.

The design also missed something, and a review pass before implementation caught it: a fourth Claude-only surface. The audit mode depended on the Workflow tool, an entire orchestration runtime with no equivalent anywhere else. That became phase 4b, and it was the largest single piece of work in the track.
