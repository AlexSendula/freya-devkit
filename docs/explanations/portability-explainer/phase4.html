portability · phase 4 · 31 Jul 2026

A careful piece of work built on a premise that was false.

Three skills told the agent to spawn workers in parallel, as an unconditional command, with no fallback written anywhere. Phase 4 fixed that properly: it separated what the work is from how it gets scheduled, and added a rule so the old form could not return. Every part of that is still right. The reason it was done that way was not.

What was actually wrong

Three flows fanned out: docs-manager (12 document types), spec-manager scan (5 discovery areas), and codebase-security-scan (6 categories plus per-finding refutation). All three issued parallelism as an imperative — spawn these in parallel — with nothing said about what to do on a host that cannot.

On Claude Code that is a directive the Task tool executes. On an agent without subagents it is an instruction that cannot be followed, and the skill offers no second path. The work would still happen, but by improvisation rather than design.

Separate the work from the scheduling

The fix is structural and reads as obvious in hindsight. Each flow states its N tasks as independent units, and then — after the list, so the structure is read first — a canonical block that was byte-identical across all three files. Quoted here exactly as phase 4 shipped it, in 06e155c:

Run them in parallel — the default — if your agent supports subagents (Claude
Code, Cursor, Codex and OpenCode all do; Copilot delegates on its own when the
tasks are visibly independent). If it does not, run them one at a time. On a
small project the result is the same, only slower; on a large one a sequential
run accumulates every task's reading context in a single window and may not fit,
so narrow the scope — fewer files, or fewer tasks per run — rather than letting
it truncate.

Parallel stays the default, which is also the no-behaviour-change option for existing Claude users. What the port added is a defined fallback where there was none, and — importantly — an explanation of the failure mode that makes the fallback necessary. Context exhaustion on a large repository is a real limit, and "narrow the scope" is real advice.

The parenthesis is quoted deliberately, because it is the sentence the next section is about: "Copilot delegates on its own when the tasks are visibly independent" was the premise, and phase 6 measured it false. It has since been rewritten in both surviving copies.

R9 — the rule that keeps it

Any fan-out language in a SKILL.md must be accompanied by the portability clause, detected by the phrase "if your agent supports subagents". The rule is file-scoped: one violation per file, because the sentinel fixes them all at once.

That scoping is a known trade-off, recorded rather than hidden — a second fan-out added to a file that already carries the clause will not be caught. Documented in CONTRIBUTING.md, and still true.

R9's detection had to be widened once during the phase, after its first version missed several forms and its gate turned out to be case-sensitive in a way that let real violations through. The rule that enforces a guarantee needed a guard of its own.

The premise

Why place the scheduling block after the task list? Because of this, from Copilot's public documentation: the main agent "decides execution strategy autonomously based on task structure."

Claude CodeGitHub Copilot
"run these in parallel"a directive — the Task tool does ita hint the model may ignore
Who decidesyouthe agent — delegation is agent-initiated
What influences it—task structure: N visibly independent units

So the reasoning went: the lever is not the sentence, it is the shape of what precedes it. Present twelve visibly independent tasks and the agent will recognise them as parallelisable. Every scheduling block was positioned accordingly.

Two phases later, measured

It does not work. Phase 6 asked Copilot to run the six category scans and watched it perform them itself, as a sequence of greps, then report "six category scans run in parallel." Phase 7 instrumented a twelve-way fan-out and counted zero task and explore invocations — then found the reason in Copilot's own system prompt: "never delegate parts of a codebase that is small enough to read directly, regardless of how it divides into separate areas."

What survives

Almost all of it, which is worth being clear about.

The separation was right

Stating N independent units and scheduling them separately is good structure regardless of who schedules. Phase 7's driver consumes exactly the same decomposition — it just executes it in Python instead of asking.

The fallback was right

It turned out not to be a fallback on Copilot but the only mode, which makes the "narrow the scope" advice the primary guidance rather than a footnote. Still correct; more load-bearing than intended.

The premise was wrong

And unfalsifiable from the inside — the agent reports parallelism either way. No test that reads the agent's answer could ever have caught it.

Two flows still ship it

docs-manager and spec-manager keep the prose form. Not for lack of scale, but because their workers write files and the driver's guarantee rests on workers that cannot. Recorded as a live gap →

The lesson, stated once

Words are not a mechanism

A skill file is data the agent reads. The host's system prompt is the agent's instructions. When they conflict the host wins — and it should, or a file in a repository could override a vendor's operating policy.

So no phrasing, however careful, can make a guarantee. Phase 4's error was not choosing the wrong words. It was believing that words were the kind of thing that could enforce something.
