portability · the course corrections

Every one of these was a plan that turned out to be wrong.

The design document was written before any code, and most of it held. But thirteen things were discovered only by building, or by finally running it — a specification rule that made the install architecture impossible, a security control that didn't control anything, a promise that this repo's own data refuted, three tests that proved nothing, a security tool that reported a totally failed run as a clean codebase, a whole phase in which every serious defect was a guard misfiring at the person it protected, once it was run for real a security skill the target agent could not see at all, a conclusion of "unfixable from this side" that turned out to be a failure of nerve, and finally a platform this site had spent seven phases calling untested-but-fine, which failed 29 times the first time anything ran on it. Each is recorded here because the correction is more useful than the original plan.

1 · A fourth Claude surface, found by re-reading

design phase

The first design pass identified three Claude-specific surfaces: the path variable, the slash references, and the fan-out prose. A review pass before implementation found a fourth — the audit mode's dependency on the Workflow tool, an entire orchestration runtime that had no equivalent anywhere else.

Why it mattered

Missing it would have meant shipping a "portable" toolkit with one mode that silently didn't work off Claude. It also turned out to be the single largest piece of work in the track — the other three surfaces were substitutions; this one was an architectural inversion.

2 · The install design was impossible

architecture change

This is the big one. The design said the installer would apply a freya- prefix at install time to both the directory name and the name: field inside each SKILL.md. Checking the Agent Skills specification before writing the installer turned up a rule that makes that impossible:

agentskills.io/specification

The name field "Must match the parent directory name." Claude Code's own docs say it from the other side: "The directory name becomes the command you type."

Installation is symlinking. A symlink from ~/.claude/skills/freya-code-graph to <store>/skills/code-graph produces a SKILL.md saying name: code-graph inside a directory called freya-code-graph — a spec violation that skills-ref validate rejects. You cannot rewrite the file, because there is only one file and every agent shares it.

Planned

Repo keeps skills/code-graph/. Installer prefixes at install time.

Fails: requires rewriting a shared file, or shipping an invalid skill.

Built instead

Repo renames to skills/freya-code-graph/, name: and all. Installer becomes a pure symlink.

Bonus: freya update becomes nothing but a git pull — symlinks propagate on their own.

The rename touched ten directories, ten name: fields, fifteen manifest paths, and ten hard-coded sibling paths in five scripts. A naive sweep would have found nine of those ten: one used os.path.join with a textual ../.. instead of the parents[2] idiom the others used, and was invisible to the obvious grep.

3 · A "non-standard" field that was in the standard

correction

The design described compatibility: frontmatter as non-standard and had it removed. The specification lists it as a standard optional field, alongside license, metadata and allowed-tools.

That error had already propagated: the conformance checker's allow-list was {name, description}, so it was rejecting four legitimate fields. Removing those two particular lines was still right — they enumerated Claude tool names — but the stated reason was wrong, and the rule built on it was wrong.

The lesson that stuck

A guard built from a remembered fact inherits the memory's error and then enforces it on everyone. Read the spec before encoding it.

4 · Copilot cannot be told to parallelise

design change

The plan for the three fan-out flows was to say "run these in parallel if your agent supports subagents." Checking the VS Code documentation showed that instruction means something quite different on the target host:

Claude CodeGitHub Copilot
"run these in parallel"a directive — the Task tool does ita hint the model may ignore
Who decidesyouthe agent — delegation is agent-initiated
What actually influences it—task structure: N visibly independent units

Copilot's docs say the main agent "decides execution strategy autonomously based on task structure." So the lever isn't the sentence — it's the shape of what precedes it. Every scheduling block in the three flows is therefore placed after its task list, so the list is read first.

Reframe

The portable phrasing stopped being a compromise for weaker hosts and became the only thing that works on the primary target.

Overtaken by evidence — phase 6

This section's conclusion was that task structure is the lever that gets Copilot to delegate. Run for real, it isn't: Copilot performed all six category scans itself, sequentially, and then reported that it had run them in parallel. §11 →, and in phase 7 the security scan stopped relying on the lever at all. §12 →

Phase 7 then found the reason, written down. A debug-logged run surfaced Copilot's own sub-agent instructions: "never delegate parts of a codebase that is small enough to read directly, regardless of how it divides into separate areas". The lever this section identified is the exact thing the host is told to ignore. The public documentation said what it said; the system prompt says the opposite.

The heading stays as written, and is worth reading precisely. Copilot can parallelise — it ships task, an explore agent, background agents and /fleet, "enable fleet mode for parallel subagent execution". What it cannot be is told, by a file in your project. A skill is data the agent reads; the system prompt is the agent's instructions, and the host wins every time. The capability was never the problem.

5 · A security control that controlled nothing

security

Before designing the audit driver, a spike ran both CLIs against a deliberately vulnerable fixture to establish how to enforce "this worker may read, but never write."

ConfigurationResult
Claude --allowedTools "Read Grep Glob" + --disallowedTools "Write Edit"Held. It tried Bash three times; all denied.
Copilot --allow-tool=read + --deny-tool=writeHeld. Write tool and an explicit shell redirect both failed.
Copilot --allow-all-tools + --deny-tool=writeBypassed. The worker created a file through a shell command.
The actual rule

"Deny beats allow" applies to the write tool — not to writes performed through the shell. Only an explicit allowlist that excludes the shell holds. --allow-all-tools must never appear in an audit invocation.

That finding is now enforced in code rather than remembered as a convention: a _guard function refuses to emit a blanket permission flag even if one is smuggled in through a prompt, and a test asserts no adapter can ever produce one.

6 · A promise refuted by our own measurements

correctness

The portable scheduling block — the paragraph copied verbatim into all three fan-out flows — originally ended:

Original wording

"If it does not, run them one at a time: the result is identical, only slower."

The whole-phase review refuted this using a file already in the repository. The behaviour-layer dogfooding notes record a real spec-manager scan: 7 parallel discovery agents, ~260k subagent tokens. Running those tasks inline collapses seven isolated context windows into one — each worker's file-reading context is retained, not discarded. On a 200k-context agent that run does not produce an identical result; it does not complete.

Worse, the block's own next paragraph explained why, by noting that each subagent carries its own context window. The claim contradicted the sentence beneath it.

Now reads

"On a small project the result is the same, only slower; on a large one a sequential run accumulates every task's reading context in a single window and may not fit, so narrow the scope — fewer files, or fewer tasks per run — rather than letting it truncate."

7 · --dry-run deleted your installation

critical

The installer's uninstall path returned before it ever consulted args.dry_run. So freya uninstall --dry-run — a flag whose help text reads "print the plan, change nothing", advertised in the README as a preview — removed all ten symlinks.

Bounded damage: only our own links, recreatable by re-installing. But a safety flag that performs the destructive operation is the exact failure the phase's constraints existed to prevent. The same review found uninstall never removed the launcher either, so deleting the checkout afterwards left a dangling freya on PATH.

Why the review caught it and the tests didn't

Every unit test exercised uninstall_agent() directly. Nothing tested the flag wiring in main(). The tests were green and the feature was broken — which is the argument for a review that runs the thing end to end rather than reading the diff.

8 · Three tests that proved nothing

hollow guards

The audit engine's vote arithmetic is the part of the port where a silent error changes security findings. Its tests all passed. Mutation testing — deliberately breaking the code to confirm a test fails — showed three of them were hollow:

MutationWhy the test missed it
upheld * 2 > total → >=Only a 1-of-2 split distinguishes them. Every test used 1-of-3 or 2-of-3, where both operators agree.
K_EMPTY = 2 → 3The test asserted against audit_engine.K_EMPTY itself — so it adapted to the mutation and stayed green.
Delete the dry = 0 resetThe test counted findings; both paths yield one. Only the round count differs.

All three now have tests that distinguish, and all six engine mutations are verified to be killed by a specifically named test.

A trap worth knowing

Mutation runs land within the same filesystem timestamp tick, so Python happily reuses cached bytecode and reports the previous mutation's result. Two mutations looked "killed" when they had never been loaded. Clear __pycache__ between runs, or use python3 -B.

9 · Two numbers that were never multiplied together

found by review

Phase 4b was the one phase that skipped its whole-phase review. When the review finally ran, the engine logic held up — every constant, the dedup key, the vote arithmetic, the disposition ladder. Nothing was wrong with the port. Both serious findings were at the driver's edges, and neither was an edge case.

🚨

A failed audit reported a clean codebase

Every failure path in ask was a bare continue. With an expired login, all 26 calls failed, the driver printed "done: 0 findings", exited 0, and emitted [] — from which the skill wrote a report saying the codebase was clean. The captured stderr was discarded unread. For a security tool that is the worst available failure mode, and it is the likely first run.

🧮

The defaults could not finish a run

--max-findings 40 needs 151 tasks. --max-calls was 80. The two were chosen in the same sitting and never multiplied out — even though estimate(), the function that does exactly that multiplication, sits 25 lines below them. And they were in different units: the budget counts attempts, and each task may retry once.

The second compounded the first: exhausting the budget discarded everything, including findings already fully verified. A real run would spend its entire ceiling and return an empty array with exit 2.

The fix that mattered most wasn't the arithmetic

Refusing to return a partial audit that could be mistaken for a complete one is the right instinct. But the answer is to label truncation, not delete the evidence of it. Verification now settles in batches, a halt keeps the completed ones, and exit 3 marks the result incomplete. With that in place the exact cap values stop being load-bearing — and --max-calls became the single cost knob, with --max-findings derived from it so the two cannot disagree again.

A third finding falsified this track's own completeness proof. Retiring the engine claimed that R1 and R4 having no exemptions left meant a single leftover reference would fail the gate. R4's pattern required the literal word tool — and three "Workflow-powered" references had shipped straight past it, two of them in the skill layer, describing an engine that had been deleted. The proof was sound in structure; the detector was too narrow.

And one hollow guard, again

The review's own fix for the unlocked Budget shipped with a test that passed with the lock removed — the window between check and increment is a few bytecodes wide, so a hammer loop never loses the race. Replaced with one that widens the window deliberately and fails every time without the lock. Ten mutations, ten killed. The same lesson as §8, one phase later.

10 · Every guard, misfiring at the person it protects

found by review

Phase 5 was reviewed harder than any before it — for the first time, its riskiest choices went to a reviewer before a line was written, and every task was reviewed again after. Eight of ten tasks came back with findings. Not one of them was in the feature logic. Every serious defect was in code written specifically to keep the user safe, doing damage in a case its author hadn't pictured.

🚧

The barrier that half-installed

Added because --agent claude --agent copilot with a blocker under the second left the first fully installed while exiting 2. The fix planned every agent before applying any — which made each plan's status a snapshot of the disk before anything moved. Two agents pointed at one directory both planned "create"; the first installed, the second raised FileExistsError. A partial install and an error, by a new route.

🔒

The rule that locked you out of your own file

freya init's markers had to be unambiguous, because a stray one could delete a user's prose. So the fix demanded each marker appear exactly once — counting occurrences anywhere, including mid-sentence. A user who merely wrote about freya-devkit in their AGENTS.md could then never run init again. Being over-strict about a file you don't own is its own kind of damage.

🏠

The check that could not break a command

The update notice is wrapped so nothing escapes it — it cannot change an exit code or print a traceback. Wiring it in front of main silently turned four existing tests into ones that wrote the real ~/.freya and called the network. The reviewer found the file on disk, timestamped to the test run.

♻️

The crash that could not heal

relink asked apply_plan to act on an occupied target, which raises RuntimeError — caught by nothing, so it surfaced as a traceback after orphan removals had run. Worse, it was self-sustaining: a copy interrupted partway leaves a directory with no marker, which audits as occupied forever, so every future freya update crashed at the same line.

The review that ran before the code

Three plan-mandated choices were sent to a reviewer before implementation. Two were wrong — and one of those was not a style disagreement. The plan had left the failed-fetch branch untested on the grounds that an offline remote can't be simulated honestly. But delete that guard and the flow compares against the stale local ref, which succeeds: an offline machine prints "already up to date" and exits 0 over a store that isn't. The mutation check later reproduced exactly that. The lesson is narrow and worth keeping: "this error path can't be tested honestly" is a claim about the test, and it says nothing about whether the branch's absence is visible to the user.

And one error message, three times

freya_cli.main catches (OSError, ValueError) and reports "cannot read the command manifest". In one phase, three unrelated failures fell into it: a throttle-file write after a successful update, an unreadable SKILL.md during init, and a half-written install during relink. Each was fixed where it arose, which is right and also not a fix: a catch-all naming one cause will keep collecting others. The full phase-5 record →

11 · The artefact was correct. The host disagreed.

found by running it

Ten corrections found by building. This one could only be found by running — and it went straight to the thing the whole track exists for.

Phase 6 asked Copilot to list its installed skills. It returned nine. The missing one was freya-codebase-security-scan — the security scanner, absent on the agent this port was built to reach. Installed. Correctly symlinked. Silently dropped.

227 characters

The Agent Skills spec caps description at 1024 characters. That one had grown to 1251, the only skill in the suite past the line — the next largest is 910. Copilot enforces the limit and drops the skill without a word. Claude Code ignores it and loads the skill anyway, which is precisely why five phases of work done mostly against Claude never saw it. Nothing raised an error: not the CLI, not doctor, not the conformance gate, whose R5 had always checked which frontmatter keys were present and never how long their values were.

Three more followed, each needing a live agent: the same SQL injection deduped as two findings because one worker wrote ./src/auth.js and another wrote src/auth.js; a security scan that ran git commit against a repository it had only been asked to read; and an audit in which 22 of 27 calls failed and the run printed its three findings exactly the way a complete audit prints them.

And one that looked unfixable from this side

Asked to run the six category scans the way the skill instructs, Copilot ran them itself — a sequence of greps — and then reported: "six category scans run in parallel." Phase 4 designed the fan-out flows around the documented assumption that N visibly independent tasks get delegated. They do not, and the agent's own account of its work cannot be used to tell the difference. This was recorded as unfixable, because the skills already carried the sequential fallback. §12 corrects that →

The pattern, stated three times

Phase 4b's defects were at the driver's edges, not in its logic. Phase 5's were in guards misfiring at the people they protect. Phase 6's are in what a host does with an artefact that is entirely correct by its own lights — enforce a limit the other host ignores, decline to delegate, infer a commit nobody asked for. A test suite can only ever check the artefact. The full phase-6 record →

12 · "Unfixable from this side" was the wrong conclusion

found by running it

§11 recorded Copilot's refusal to delegate as a fact to live with: the skills carried a sequential fallback, so the work was still correct, only slower. That reasoning has a hole in it, and phase 7 is the hole.

The fallback was never the problem

The problem is that nothing can tell you which mode ran. A skill that says "run these in parallel if you can" gets the same answer from an agent that did and an agent that didn't — the phase 6 finding was only visible because someone read the transcript and saw six greps. A correctness property you cannot observe is not a property. It is a hope.

So the fix was not to accept the sequential mode, and not to word the instruction more firmly. It was to stop issuing an instruction at all. The security scan now calls freya security scan — a driver that owns a worker pool, makes the six calls itself, and returns verified findings. The agent's cooperation is no longer part of the guarantee.

What made it affordable — and what nearly made it dangerous

scan is a preset of the driver audit already used, not a second driver. The obvious way to make the preset cheap is fewer skeptic lenses. That is a trap: a finding is deleted on a unanimous refutation, so with one lens a single sceptic having a bad moment silently deletes a real vulnerability. The saving came out of discovery instead — one round rather than five, 40 tasks down to 16 — leaving verification exactly where it was.

Running it then found two more things no test had: the same SQL injection reported twice under two different categories, non-reproducibly; and a failed run whose real reason ("OAuth session expired") sat unread inside the agent's JSON envelope while the driver printed exit 1. The full phase-7 record →

The correction to the correction

§11 was right about the observation and wrong about the remedy. When an agent's behaviour cannot be verified, the answer is not to document the uncertainty more carefully — it is to remove the agent from the part of the design that needed to be certain.

13 · Windows was not waiting on a machine. It was waiting on code.

found by running it

Every page of this explainer, for the whole track, carried the same sentence in some form: Windows is untested, it needs a Windows machine, and no code. The first half was true. The second half was an assumption that had been restated so many times it had started to read like a finding.

A CI workflow now runs the suite, the conformance gate and a real end-to-end install on ubuntu-latest and windows-latest, across Python 3.9 and 3.13. The Windows leg came back 29 failed against a green Linux leg. None of it was a regression — it was simply the first time the suite had ever executed there.

Two of the four root causes were product bugs

The installer proved it owned a link by comparing the target it read back against the source it wrote. On Windows os.readlink returns \\?\C:\… where the source is spelled C:\…, so every link the installer had just created classified as foreign — freya install refused to manage its own install, and relink skipped every agent. And the code graph keyed weirddir\x.ts, so every forward-slash lookup missed: behavior-graph and behavior-runner both read those keys expecting forward slashes, so blast radius came back empty and silent.

The third was a fallback that masked the failure it was catching — remove_link retried a failed unlink as rmdir, and on Windows the retry succeeded, so a removal that had not happened was counted as one that had. The fourth is the one worth keeping: a manifest escape guard written as os.path.isabs(rel), on a path that reaches the filesystem. Python 3.13 changed ntpath.isabs so that a rooted path with no drive is no longer absolute on Windows — so /etc/passwd was rejected on 3.9 and accepted on 3.13. The guard was correct on three of the four legs by accident of which interpreter was running it.

The correction, stated plainly

"Untested" and "fine" are not the same word, and repeating an untested claim does not move it toward the second one. What made this one durable is that the claim was specific and sounded like a measurement — needs a machine, not code — when nobody had ever been in a position to know. The cost of finding out was one workflow file.

And a green matrix is not the end of it. Two further defects were found by review rather than by the runner, and CI could not have caught either: cmd_shim_plan is Windows-exclusive, so no POSIX run reaches it, and is_git_store was latent. Both would have shipped broken behind eight green jobs. The full record →

What the plans got wrong about themselves

Beyond the thirteen above, the implementation plans were amended fifteen times mid-execution as standalone commits — and nine more times inside phase 5's fix commits, which carried their plan corrections with them rather than leaving the plan describing code that no longer existed. Two are worth naming because they were caught by refusing to proceed rather than by testing:

A plan that violated its own rule

The canonical scheduling block said "Claude Code's Task tool" — a phrase rule R4 had forbidden since phase 2 as a Claude-only tool name. The plan mandated text the gate rejects. Fixed by naming the agents rather than their internals; the rule stayed intact.

A definition of done that couldn't be met

Phase 4b's exit criteria demanded no ${CLAUDE_PLUGIN_ROOT} anywhere — including CONTRIBUTING.md's bullet that cites it as the anti-pattern not to write. The mention is the point of the bullet. The criterion was wrong, not the file.

The pattern across all of them

In both cases the right move was to stop and report the contradiction rather than quietly weaken a guard or edit the evidence. The plan is a hypothesis; the code and the specification are the facts.
