portability · phase 7 · 17 Aug 2026

A guarantee that lives in a sentence is a suggestion.

Phase 6 asked Copilot to run six security scans in parallel. It ran them itself, one after another, and then reported that it had run them in parallel. Phase 7 stops asking. The skill now calls a driver that schedules the work — and the agent that would not delegate now runs a fan-out that does. With the quota restored, wrap-up finally ran end to end too.

The finding this phase exists to fix

Phase 4 built three fan-out flows on a documented assumption: give an agent N visibly independent tasks and it will delegate them. Phase 6 tested that assumption against GitHub Copilot and it failed — but the way it failed is the part that matters.

The transcript was the only witness

Copilot answered "Scan complete — six category scans run in parallel." It had run six greps in sequence. The only reason anyone knows is that the transcript showed the greps. The agent's own account of its work cannot be used to tell the difference — which means no amount of careful prose in a skill file can make the guarantee checkable, and no test that reads the agent's answer can catch it failing.

So the fix is not better wording. It is the same inversion phase 4b applied to audit: stop asking the agent to schedule the work and schedule it here, in a driver, on a worker pool we own.

The decision the whole design turns on

Making scan cheaper than audit has two obvious levers: fewer discovery rounds, or fewer skeptics. The second one is a trap, and the disposition ladder is what springs it.

Why the preset cuts rounds and never lenses

A finding is dropped — deleted, never reported — when its refutation is unanimous. With three skeptic lenses that takes 3-of-3. With one lens, a single refutation is a unanimous one. One skeptic having a bad moment would silently delete a real vulnerability, and a security tool's worst failure is a false negative it never mentions.

The economics happen to agree. Discovery, not judgement, dominates the cost.

auditscan preset
Discoveryup to 5 rounds × 6 categories = 30 tasks1 × 6 = 6 tasks
Verification3 lenses × findings3 lenses × findings — unchanged
Worst case at 3 findings40 tasks16 tasks

So scan becomes what it always claimed to be — the lighter mode — without becoming the less careful one. It is a preset of the audit driver, not a second driver: one shared pool, one shared budget guard, one shared read-only allowlist, one definition of what counts as a finding. Two modes with two definitions would drift, and the cheaper one would be the one that drifted toward missing things.

Every run found all three planted issues. No run reported anything in the control file. After all five, the fixture was byte-identical to its pre-run checksums and git status was empty.

The second adapter earned its run twice over

The retry path finally ran. Phase 6 recorded that the extract-validate-retry design had never been stressed in the field — 47 live worker invocations, zero failed calls. On the Claude run, 2 of 27 attempts failed and both recovered on retry. unanswered stayed 0, so the degraded guard correctly did not fire. Attempts drive diagnostics; tasks drive the trust decision — observed live rather than only in tests.

And colocated caught a second pair. Claude reported the SQL injection under both auth and injection, as Copilot did — and the exported credentials under both secrets and api at module.exports = { findUser, isAdmin, DB_PASSWORD }. Four of its six findings are two real issues seen twice. Without the annotation the report would have listed six vulnerabilities in a five-file project.

The two adapters disagree on severity — Claude rated everything critical, Copilot high — and on volume: Claude found 8 candidates in one round against Copilot's 4. Neither is wrong. The disposition ladder normalises confidence, not severity.

Do the CLIs throttle? Yes — and the pool still wins

The design spec named one measurement only a live run could give: the same fixture at --concurrency 1 against --concurrency 6. The answer is 209.3 s versus 91.4 s — 2.29×, not 6×.

Some of that is structural: one serial context call, one wave of six finders, then twelve skeptic calls in two waves — about four waves at best. But at the serial rate of 13.1 s per call, four perfect waves would be ~52 s. The measured 91.4 s means per-call latency is roughly 1.75× worse under concurrent load. Copilot does apply back-pressure. Expecting linear scaling would have been wrong; having the pool is still worth more than double.

Two defects, both found by running it

👯

1 · One vulnerability, two categories, two findings

Run 1 reported the SQL injection at src/auth.js:5 twice — once from the auth finder, once from injection — because the dedup key is file + line-window + category. Six verification calls went to one issue. Run 2, same fixture, produced only one: the double-counting is not even reproducible, so a user cannot predict whether their report inflates.

🔇

2 · "last error: exit 1"

The claude adapter failed instantly on the test machine. The guard was right — it refused to call an empty result clean and exited 2 — but the reason it printed was useless. Reproducing the call by hand showed why: claude -p answers a failed call with returncode 1, empty stderr, and the reason inside its JSON envelope on stdout. It was an expired OAuth session, and the driver had the message in its hands the whole time.

The duplicate was fixed by refusing to fix it automatically

The tempting repair is to drop category from the dedup key. Don't: two genuinely different issues can share a five-line window — this very fixture has a hardcoded secret on line 2 and an injection on line 5 — and merging blind would delete one without a word. Between a visible duplicate and a silent deletion, a security tool takes the duplicate.

So survivors now carry a colocated list naming the other categories that reported the same place, annotated after the drop filter so a survivor is never told it shares a location with something the skeptics just deleted. The engine states the ambiguity; the skill's report loop, which has the titles and descriptions in front of it, decides.

A third fix rode along, independent of both: verification.lenses was a module constant, so a finding whose exploitability call timed out still reported all three lenses — a report describing a verification that did not happen. It now names the lenses that answered.

The test that mattered

Everything above tests the driver. The phase 6 finding was about the skill, so the real question is whether an agent asked to run the skill now reaches the driver at all. Sandboxed HOME, Copilot given shell and write tools, a throwaway fixture, and one instruction: "Run the freya-codebase-security-scan skill in scan mode on this project."

First attempt — the failure was the right one

Copilot said "Running the required full scan driver now" and invoked it. No greps. The driver autodetected the claude worker — its stated preference, because Claude reports per-call spend — was handed a Copilot model name from the prompt, and failed with unrecognized_model. Copilot reported the failure and wrote no report: a third live confirmation that a broken run cannot be mistaken for a clean one. It also exposed a real documentation gap. --agent and --model are a pair, and the two CLIs' model vocabularies do not overlap.

Second attempt, worker pinned. The driver returned four findings; Copilot resolved the colocated pair into one exactly as the new instructions say, labelling it Authentication & Authorization + Input Validation & Injection and saying in the summary that the merge happened. It wrote the dated report, findings.json and the tracking file — and did not commit them. One commit in the repo, the fixture's own. Phase 6's uninvited-commit fix is holding.

One gap the generated report exposed in passing: findings.json arrived with its findings list alone, missing the version, scanned_commit and report fields the schema requires — so a consumer could not tell which commit those findings described. The skill never listed the envelope fields. It does now.

The question every phase had deferred

"Does a session that is already open notice when freya update swaps the files underneath it?" had been carried as unproven since phase 5. Closing it needed something none of the earlier work had: a real interactive session held open while the filesystem changed. So the session was held open, a skill's link was moved out from under it, and it was asked about that skill.

Copilot: the two halves disagree

With freya-code-graph removed from disk, the session still listed it. But asked to actually load it: ENOENT: no such file or directory → NOT REGISTERED.

So the registry is snapshotted at session start while the body is read from disk at invocation. Note that the listing alone would have proved nothing — a model can simply recite its own answer from a minute earlier. The load probe is the evidence; the list is a story.

Claude was measured twice, and both attempts taught method rather than behaviour. The first moved plugins/marketplaces/…/skills/code-graph — which changed nothing, because a plugin install keeps two independent copies and the live one is under plugins/cache/<marketplace>/<plugin>/<version>/. The second moved the right copy and got "already loaded (no changes since last load)" — the session had loaded that skill minutes earlier and answered from memory. Both runs were executed correctly; both targeted a state that could not answer the question. What they do establish is that Claude caches a once-loaded skill for the session.

The fix is a reload, not a restart — and the tool said neither

Both hosts can reload in place: /reload-skills on Claude Code (verified present in the 2.1.220 binary) and /skills on Copilot. That is a much smaller ask than restarting, and it is the right advice.

freya update mentioned none of it. It printed updated e878a209 -> 34a9a310 (5 commit(s)) and stopped — so someone updating mid-task sees nothing change and concludes the update failed, when it worked perfectly and needed one command. It now prints the reminder whenever it actually moves the store, and never when there was nothing to move.

Third row of that table is not hypothetical: phase 3 renamed every skill to its freya- prefix. Anyone who had run freya update across that rename with a session open would have been handed phantom skills that fail with a filesystem path.

The other two fan-outs, run for the first time

Phase 4 built three fan-out flows, and the scoreboard had been quietly reporting one result for all of them. Only the security scan's six-way fan-out had ever been run on an agent. docs-manager (12 workers) and spec-manager scan (5 discovery areas) were shipping on the strength of a measurement taken in a third skill.

Both were run in the sandbox on Copilot, on separate identical fixtures so neither could benefit from the other's output — a small Express project with three routes.

docs-manager — 12 documents

Exit 0, 274 lines, plus an index. Not templates: API.md names the actual routes, the actual storage path /var/reports/<filename>, and the real req.db dependency. It reported "Placeholder resolution found none" and a passing consistency / accuracy / link check. src/ untouched, nothing committed.

spec-manager scan — 5 specs

Exit 0, across four of the five discovery areas (none for infra, which this fixture has none of), plus 8 proposed behaviors. Certainty scores of 68 / 72 / 78 / 84 / 88 — the scoring pattern working rather than declared. It flagged report file handling as lowest-certainty, which is the right call. Nothing committed.

Those two runs captured only the final message, so they proved the flows work without showing whether the twelve and five tasks were delegated. So docs-manager was run a third time with --log-level debug, producing an 800 KB structured log of every model request and tool call.

Zero delegation across a documented twelve-way fan-out. All thirteen files were written by the main loop. And the same log contains the reason — in the Task tool's own instruction block, which is Copilot's system prompt, not ours:

The host is explicitly told not to do what the skill asks

"For other reviews, audits, and summaries, never delegate parts of a codebase that is small enough to read directly, regardless of how it divides into separate areas; do them yourself. Never delegate passes over the same files."

"Never use explore to split a review, audit, or summary by labeled area when its total scope is small; do it yourself."

That is the freya fan-out described exactly: a review, split by labeled area, over the same files. So Copilot's refusal was never a quirk observed once — it is documented policy. And phase 4's founding premise, that task structure is the lever that gets Copilot to delegate, is contradicted by five words of it: "regardless of how it divides into separate areas." Structure is precisely what it is told to ignore.

To be clear about what this is not: Copilot is not missing the capability. It ships task, an explore agent, background agents, /subagents, and /fleet — "Enable fleet mode for parallel subagent execution". The machinery is all there and it is good. It is simply instructed not to reach for it here. And /fleet is an interactive toggle with no CLI flag, so a headless -p run — how the driver and any scripted use invoke it — cannot turn it on.

So can the fan-out be forced? No — and that is a property of skills, not of Copilot

The obvious follow-up is whether some setting makes it delegate. There isn't one: subagents.agents.<name> configures a subagent's model, not whether delegation happens, and /fleet is an interactive toggle with no CLI flag and no config key.

But the deeper answer is that no skill file can enforce anything. A skill is data the agent reads; the host's system prompt is the agent's instructions. When the two conflict the host wins — and it should, or a file in a repository could override a vendor's operating policy. Phase 4's error was not picking the wrong words. It was believing that words were a mechanism.

Which leaves exactly two ways to make a guarantee real: change the host's own configuration, or stop asking the agent. Only the second is available here, and it is what the driver does — separate operating-system processes, not subagents, so there is no decision for anyone to make.

The honest limit — and why this settles the design

Both clauses are conditioned on scope: "small enough to read directly", "when its total scope is small". Every observation, in phase 6 and here, was on a small fixture. At scale Copilot's own policy would permit delegation. So what is established is narrower than "Copilot never delegates": for scopes small enough to read directly, it will not delegate a labeled-area fan-out, by design.

Within that limit it settles the phase 7 decision completely. Against a host whose instruction is "do it yourself", no phrasing of a skill file buys concurrency. The driver is not a workaround for a quirk — it is the only mechanism left.
