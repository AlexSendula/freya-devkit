portability · phase 6 · 16 Aug 2026

The security scanner was missing on the agent this whole track was built for.

Five phases made the toolkit portable. This one ran it — on a real machine, against a real remote, through Claude Code and GitHub Copilot. It took one question to find something five phases of tests could not: Copilot listed nine skills, not ten, and the missing one was the security scanner.

How it was run

Two parts, gated separately. Part A exercised the whole install / update / init / doctor surface under a redirected HOME — free, and unable to touch the working machine. Part B drove the real agent CLIs, which costs money and needed credentials.

The isolation, described honestly

Every path the toolkit writes derives from Path.home() — verified at all six call sites — and Path.home() follows $HOME, as does Node's os.homedir(), which matters because both agent CLIs are Node programs. So HOME=/tmp/… relocates the entire install.

That is isolation by convention, verified by inspection — not an enforced boundary. A program calling getpwuid() would still find the real home. So the four real paths were checksummed before the run and diffed after: no differences. An escape would have been detected, not assumed away.

One limit surfaced immediately: redirecting HOME breaks macOS Keychain access. Only the System keychain remains visible, so Claude Code's login fails with "keychain not found", and copying the old .credentials.json does not help — 2.1.233 ignores it. The only route was symlinking the real keychain into the sandbox, which widens the very boundary the sandbox exists to hold. It was done with explicit approval, kept only for Claude-side work, and removed before Copilot ran with expanded tool permissions.

Part A — the mechanics held

A clean git clone plus ./install.sh — the path the README actually tells a user to take — linked ten skills per agent and put the launcher in place. doctor exited 0 with every check green.

Four defects, none of which a test suite could have found

Every one of these needed a live agent. They are listed in the order they were discovered.

🕳️

1 · The security scanner was invisible to Copilot

Asked to list its skills, Copilot returned nine. A direct yes/no confirmed freya-codebase-security-scan was genuinely absent — installed, correctly linked, and silently dropped. Its description ran to 1251 characters against the spec's 1024 limit, the only skill in the suite over the line. Claude Code ignores the limit and loads it anyway, which is exactly why five phases of Claude-side work never saw it. The fix cut it to 840 characters; phase 7's driver instructions took it back to 959, still inside the limit but with only 65 characters of headroom left. Rule R10 is what makes that a number anyone can see — R5 had always checked which keys existed and never how long their values were.

👯

2 · One file, two spellings, two findings

A live run reported the same SQL injection twice — once as ./src/auth.js, once as src/auth.js. The dedup key was built from whatever string a worker happened to write, so both survived, and one of only three verification slots was spent sending three skeptics after an issue already being judged. Paths are normalized at intake now, which fixes the key and the report together.

📝

3 · A scan committed to the repository

Running the security scan with broad tool permissions, Copilot wrote the report and then ran git commit — adding three files to the history of a repo it had only been asked to scan, with a literal \n\n mangling the subject line. Nothing in the skill asked for that. Nothing forbade it either, and an agent holding write tools filled the gap with an inference. Four artifact-writing skills now say plainly that committing belongs to wrap-up. Re-tested live: the report is written and left uncommitted.

📉

4 · A mostly-failed audit reported as a normal one

On a real 299-file codebase: 27 calls, 22 failed, three findings — printed exactly the way a complete audit prints its results. No failure count in view, no last error, exit 0. Phase 4b had fixed the all-or-nothing shapes; this is the shape between them, and it is the likelier one, because a run degrades long before it dies. Any unanswered task now makes the run INCOMPLETE, names the counts, surfaces the error and exits 3.

What was actually failing

The 22 failures had a mundane cause that only a live run could reveal: the Copilot account's monthly quota was exhausted. A later run confirmed it — You have exceeded your monthly quota — and this time the phase 4b guard did its job, stopping at the context call rather than spending on finders, exiting 2 with an empty stdout and the reason on stderr. The same underlying condition produced a silent degradation in one run and a correct refusal in the other. That gap is what defect 4 closes.

Copilot does not delegate the fan-out — and says it does

Asked to run the six category scans as the skill instructs, Copilot ran them itself, as a sequence of greps, then reported: "Scan complete — six category scans run in parallel." Phase 4 built the three fan-out flows around the assumption that giving Copilot N visibly independent tasks would get them delegated. It does not, and the agent's own account of its work cannot be used to tell the difference. The design's sequential fallback is not a fallback on Copilot; it is the only mode.

This is the finding phase 7 exists to answer. The security scan now calls a driver that schedules its own workers, so the guarantee no longer depends on the agent agreeing to delegate. Phase 7 →

One result had to be thrown away, and the fixture was to blame

The first Copilot audit marked both planted issues intentional-design, where Claude had marked them confirmed and needs-review. Before reading that as an adapter defect: the fixture's README announced that it existed to validate the audit driver. A skeptic lens reading that could quite reasonably decide the vulnerabilities were deliberate test data. Re-run against a fixture that says nothing about itself, Copilot marked both confirmed critical. The control had contaminated itself; the disposition ladder was fine.

What is still unproven

The phase is not finished, and this is the part that says so.

🪟

Windows — never reachable

install.ps1, symlink privilege, and --copy under Windows. No amount of sandboxing on a Mac gets near them, and --copy is the mode a Windows install falls back to when the platform refuses to create a symlink. Since resolved — CI now runs the suite and a real --copy install on windows-latest every push. The first run failed 29 times, so this card understated it: the platform was not only unreachable, it was broken. The record →

🔄

Whether a live session notices a re-link

Fresh sessions track the filesystem on both agents — proven. Whether a session already running picks up a re-linked skill needed an interactive session held open while the link changed. Since resolved — phase 7 held one open and moved the file: the registry is snapshotted at session start, the body is read from disk at invocation, so a removed skill is still offered and then fails with a raw ENOENT. The remedy is a reload, not a restart, and freya update now says so. The record →

The one flow that ties every skill together, and the only one that legitimately commits. Blocked when the Copilot quota ran out. Since resolved — it ran end to end on Copilot in phase 7, once quota was restored. The record →
