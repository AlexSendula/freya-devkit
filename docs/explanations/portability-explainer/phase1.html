portability · phase 1 · 27–28 Jul 2026

Everything else assumes this works.

Ten skills invoked their scripts through ${CLAUDE_PLUGIN_ROOT} — a variable only one host sets — and through a bare python that may not exist. Phase 1 replaced both with a single command that finds itself. It is the smallest phase in the track and the one every later phase is built on.

The problem, in one line

# before — a Claude-only variable, and an interpreter that may not exist
python "${CLAUDE_PLUGIN_ROOT}/skills/spec-manager/scripts/drift.py" --project .

# after
freya drift --project .

Two separate failures in that first line. ${CLAUDE_PLUGIN_ROOT} is set by Claude Code and nothing else, so on any other agent it expands to nothing and the path is garbage. And python is not python3 on a great many machines — on some it is Python 2, on others it does not exist at all.

Three pieces, deliberately boring

PieceJob
bin/freyaAn executable shim. Almost empty on purpose — it exists to put the real module on the import path.
bin/freya_cli.pyAll the logic, importable and therefore unit-testable without spawning anything.
bin/commands.jsonA checked-in manifest mapping a friendly name to a script path. Sixteen commands today.

The suite locates itself from its own __file__, looks the command up in the manifest, and dispatches with sys.executable — the interpreter already running, which is by definition present and correct.

The manifest is enforced in both directions

One test fails if a manifest entry points at a script that does not exist. A second fails if a script with a __main__ block is not registered. So a new CLI cannot be added and silently left unreachable, and a deleted script cannot leave a dangling command behind. Cheap, and it has caught real drift since.

One word that decides every install

The shim uses os.path.realpath, not os.path.abspath. That looks like a stylistic nit and is not.

sys.path.insert(0, os.path.dirname(os.path.realpath(__file__)))
Why abspath would have broken everything, two phases later

Phase 3 makes every installation a symlink — ~/.local/bin/freya points into the store. abspath resolves to the symlink's own directory; realpath follows it to the real one.

Ordinarily CPython papers over this by inserting a resolved sys.path[0] for you. Under -P, PYTHONSAFEPATH or isolated mode it does not — and then import freya_cli fails, from a directory that visibly contains freya_cli.py. A bug that appears only under an interpreter flag most people never set, on an install method that did not exist yet when the line was written.

The health check that crashed

freya doctor was added in this phase to answer "is this installation sane?". Its first version had two defects, and they are worth recording because they are the same defect twice, in opposite directions.

It reported OK when it knew nothing

If the manifest failed to load, doctor still printed "all scripts present". It had checked nothing and said everything was fine — the exact failure mode the whole track keeps rediscovering in bigger forms: a tool must never report absence of evidence as evidence of absence.

It crashed on what it existed to diagnose

Given structurally valid but semantically wrong JSON — an empty array, a null, a number where a path belongs — it dumped a traceback. The command whose entire job is diagnosing a broken manifest could not survive one.

Both were fixed with four regression tests, and a follow-up commit strengthened the guard after review pointed out the first version tested the symptom rather than the branch. That pattern — fix, then a second commit hardening the guard the fix relies on — repeats through the whole track.

What it cost

13 commits

Five building, three fixing, and five amending the plan mid-flight — including one that reordered tasks because doctor was scheduled to be wired in before the thing it checks existed.

16 commands

Registered in the manifest today, up from the handful phase 1 shipped. Every one reachable as freya <name> on any host with Python 3.
