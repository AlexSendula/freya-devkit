The problem

freya-devkit is a set of ten tools that help you build software — they track which files depend on which, keep documentation current, record why things were built a certain way, and scan for security problems.

The tools themselves were always portable. They are ordinary Python scripts that would run on any machine. The instructions were not.

Each tool ships with a file telling an AI assistant how to use it. Those files were written for one assistant — Claude Code — and named things only Claude has. Point a different assistant at them and four things break:

It couldn't find the scripts

The instructions referred to the install location using a shortcut that only Claude defines. On anything else it resolves to nothing, and the path is garbage.

It couldn't find the other tools

Tools refer to each other constantly. Every one of those references used Claude's naming convention, which no other assistant recognises.

It couldn't install

There was no installer. You got the tools by installing a Claude plugin, which is not a thing other assistants have.

One whole mode didn't exist

The deep security audit ran on a Claude-only automation engine. Not a naming problem — an entire piece of machinery with no equivalent anywhere else.

The goal was to make the same toolkit work on GitHub Copilot too, without breaking anything for existing Claude users. That took eight phases and 131 commits.

What was built

One command that finds itself. Instead of instructions containing a Claude-specific path, everything now runs through a single command — freya. It works out where it lives from its own location on disk, looks the requested job up in a list, and runs it with the interpreter that is already running. Sixteen jobs are registered. This is the piece everything else assumes.

Instruction files that name no assistant. Around 260 references to Claude-specific things were rewritten. To keep them from creeping back, a checker runs over the instruction files and fails if any Claude-only construct reappears. It has thirteen rules, and each was added because something real had violated it — never speculatively.

An installer. One command installs the toolkit for whichever assistants you have, by creating shortcuts from their skills folder into your copy of the repository. Because they are shortcuts rather than copies, updating is just pulling the latest code — the shortcuts follow automatically.

A security audit that runs anywhere. The Claude-only automation engine was replaced with about a thousand lines of ordinary Python that does the orchestrating itself and calls whichever assistant you have installed as a worker. The old engine was deleted, not left alongside.

Maintenance commands. update refreshes your copy and repairs the shortcuts. doctor tells you whether the install is healthy and names the problem if not. init drops a short primer into a project so any assistant working there knows the toolkit exists.

How the security scan actually works

This is the most involved part, and the part most worth understanding, because it is where the interesting decisions are.

A security scan looks for six categories of problem — authentication, injection, secrets, API issues, configuration, and file handling. Doing all six in one pass means one long conversation that gradually fills up with everything it has read. Doing them as six separate jobs is faster and each stays focused.

Read the project docs → Six searches, at once → Merge duplicates → Three challengers each → Report

The challengers are the interesting bit. Every candidate problem is handed to three separate reviewers, each told to disprove it, each looking from a different angle: can an attacker actually reach this? is something already preventing it? was this done deliberately on purpose?

A finding is only discarded if all the challengers reject it. If they disagree, it stays and is flagged for a human. If they all failed to answer, it also stays — because no answer is not the same as an answer of "no".

Why the challengers can never be reduced to one

With three reviewers, throwing a finding away needs all three to agree. With one reviewer, that same rule means a single reviewer having an off moment silently deletes a real vulnerability — and it disappears with no trace in the report.

This is why the lighter scan mode saves money by searching less thoroughly rather than by challenging less thoroughly. A security tool's worst failure is missing something and not mentioning it.

The five decisions that mattered

Everything else followed from these.

1. Shortcuts, not copies — which forced a rename

Installing by copying files means every update has to re-copy, and edits made in one place drift from another. Shortcuts avoid that entirely.

But the specification for these instruction files says the name inside the file must match the folder it sits in. The original plan was to add a freya- prefix during installation — impossible with shortcuts, because there is only one file and every assistant sees the same one. So all ten tools were renamed in the repository itself. The install became simpler than planned, and updating became nearly free.

2. Our code drives the assistant, not the other way round

Originally, Claude's automation engine ran the security audit loop and called our logic at points it chose. That made the whole mode exist only where that engine exists — and made it untestable without paying for real assistant calls.

This was turned around. Our code now owns the loop and calls the assistant as a worker. The consequence worth noticing: the logic can be tested by handing it a fake worker that returns canned answers, so all 935 tests run offline and none of them costs anything.

3. Workers are allowed to read, and nothing else

An early experiment found something important. Telling an assistant "you may use everything except writing files" does not stop it writing files — it can still write through the command line, which counts as a different permission. Only an explicit list of what is allowed, with the command line left off that list, actually held.

So every security worker is launched with a read-only permission list, and the code refuses to launch one with a blanket permission even if something tries to sneak it in.

4. Two findings in the same place stay two findings

Testing found the same SQL injection reported twice, because two different searches both spotted it. The obvious fix is to merge anything found in the same place.

That fix was rejected. Two genuinely different problems can sit on adjacent lines — the test project has a password on one line and an injection three lines below. Merging automatically would delete one of them silently. Instead the report flags them as possibly the same thing and the write-up step decides. Between a visible duplicate and a silent deletion, this takes the duplicate.

5. Stop asking the assistant to work in parallel — do it in code

This one reversed an earlier decision, and it is the biggest lesson in the whole project. It gets its own section below.

The mistake worth understanding

For most of this project, the instruction files asked the assistant to run the six searches at the same time. Written carefully, with a fallback for assistants that can't.

Copilot ignored it every time — and reported that it had complied. It ran the six searches one after another itself, then said "six category scans run in parallel." The only reason anyone noticed is that someone read the full transcript and saw the searches happening in sequence.

The part that makes this more than a bug

You cannot tell the difference by asking. An assistant that parallelised and an assistant that didn't give you the same answer. So no amount of careful wording makes the guarantee checkable, and no test that reads the assistant's reply can catch it failing.

Later, running the tool with detailed logging turned on gave the real explanation. Copilot can run work in parallel — it has all the machinery. But its own built-in instructions tell it not to, in words that describe our situation exactly: never split a review by category when the code is small enough to just read. Our carefully structured six independent tasks are precisely the pattern it is told to ignore.

So the fix was not better wording. The security scan now launches six separate copies of the assistant as ordinary programs, managed by our code. Nothing is delegated, so nothing can be declined.

The general lesson

An instruction file is information the assistant reads. The assistant's own built-in instructions are its orders. When they conflict, the orders win — and they should, or a file in any repository could override what a vendor built.

So an instruction file cannot guarantee anything. If a behaviour actually matters, it has to be moved into code. That is the difference between hoping and knowing.

How it was checked

Automated tests: 935, all passing. None of them contacts the internet or spends money. That is deliberate — but it also means they can only prove the code does what the code was written to do. They cannot prove an assistant behaves as expected, which is why the next part exists.

Every change is now checked on Windows as well as Linux, automatically. For most of this project that did not happen, and the project said so — while also saying, repeatedly, that Windows only needed someone with a Windows computer. That turned out to be wrong.

The first Windows run failed 29 times

Nothing had broken. It was simply the first time the tests had ever been run on Windows at all, and the problems had been sitting there the whole time. Two of them were faults in the tool rather than in the tests: the installer could no longer recognise its own work, because Windows describes a shortcut's destination in a slightly different spelling than the one used to create it — so it treated everything it had just installed as someone else's and refused to touch it. And the map the toolkit builds of a project used the Windows-style separator between folder names, so every lookup missed and the answer came back empty without any error, which is the worst way for something to be wrong.

All 29 were fixed. Two more were found afterwards by reading the code rather than by running it, and the automatic checking could never have caught either — one of them only ever runs on Windows in a situation the checking doesn't create. A clean automatic check is evidence about the paths it actually walks, and nothing more.

Guards were broken on purpose. For anything safety-critical — the voting rule, the read-only permissions, the installer's refusal to delete things it doesn't own — the protection was deliberately sabotaged to confirm a specific test fails. A test that passes whether or not the protection exists is not protecting anything.

It was installed and run for real, on both assistants. Fresh copy of the repository, real installation, real updates pulled from GitHub, and real security scans on a small test project.

That test project has three security problems planted in it on purpose — a hardcoded password, a SQL injection, and a file-path flaw — plus one file written to be completely safe.

Across five live runs of the scanner, on two different assistants

All three planted problems were found every time. The safe file never produced a finding, so nothing was invented. The test project was byte-for-byte unchanged afterwards every time, so the read-only rule held. Two further runs drove the whole tool end to end rather than just the scanner: the second wrote its report without committing anything to version control, which is a separate rule it had previously broken — and the first failed outright, on a mismatched model name, and correctly wrote nothing at all.

Running it for real is also what found most of the genuine defects — a security tool that reported a completely failed run as a clean bill of health, a scan that quietly committed to a repository it was only asked to inspect, and an entire tool that one assistant was silently ignoring because its description was too long. None of those were reachable by testing the code alone. The validation record →

What is still not proven

Stated plainly, because the useful version of this section is the honest one.

No assistant has been run on Windows

Windows itself is no longer the gap. The tests and a real installation now run there automatically every time the code changes, and they pass. But the assistants themselves aren't installed on the machine that does that checking, so nobody has watched a real security scan happen on Windows — only the toolkit around it.

Two ways to install, one checked on each system

There are two installation styles: shortcuts, and plain copies. The automatic checking runs shortcuts on Linux and copies on Windows, which is how each is normally used — and which leaves the opposite pairing on each system unchecked.

Two tools still ask nicely

The documentation and specification tools still request parallel work rather than forcing it, so on Copilot they run one step at a time. They produce correct results either way — just slower.

Behaviour on a large codebase

Copilot's rule about not splitting work up applies to code "small enough to just read". Every test used a small project. On something large it might behave differently, and that has not been tried.

The cost estimate

A figure of roughly seven times the token cost for parallel work appears in the documentation. It came from outside research, not from measuring this toolkit, and it is still unverified.

The shape of it, in numbers

131 commits, 8 phases

Six were planned. Two appeared when reality intervened — one when a fourth Claude-only dependency turned up mid-project, one when live testing disproved an assumption three phases old. The last few commits belong to no phase: a review of the whole branch, and the automatic checking that followed it.

935 tests, nothing paid

Across 24 test files, run automatically on Linux and Windows on every change. The security logic is tested by handing it a fake assistant, which is what makes running the full suite free.

13 rules, none decorative

Every rule in the checker was added in response to a real violation, and each one was verified by breaking it on purpose.

1 file deleted

The Claude-only automation engine. Removing it rather than leaving it alongside is what makes this a port instead of a second implementation.
