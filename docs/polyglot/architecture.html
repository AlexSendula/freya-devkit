Track B: one contract, four graphs

Scratch explainer for docs/polyglot/. Deleted when the feature ships — the real version goes on the site. Reflects the brainstorm as it stands; nothing here is decided yet.

The one-sentence version. Stop maintaining a homemade parser, put a contract where the parser was, plug an off-the-shelf tool in behind it, and keep each different kind of relationship in its own file joined by file path.

1. The problem

freya-code-graph is a regex import-scraper covering TS, JS, Python and Go. Real projects are Java, Helm, Docker, YAML, certs and shell scripts. Everything in the toolkit — blast radius, behaviour tracking, drift detection — stands on that graph, so a blind graph means a blind toolkit. Portability made freya run anywhere without making it see anything new.

2. The contract is the design

The instinct is to pick a better tool. The problem with picking a tool is that you get to do it again in two years. So the tool is not the architecture — the socket it plugs into is.

Two backends, not one. An interface with a single implementation is fiction — you discover what leaked into it the day you add the second. Homegrown and graphify are different enough (regex vs AST, zero-install vs dependency, 4 languages vs 40) that making both satisfy one contract proves the contract is real, which is what makes a third one cheap.

3. Why four graphs and not one

The thing that keeps surfacing in this brainstorm is that there is more than one kind of relationship, and they are not interchangeable.

The join key is the file path. Every graph converges on files, so nothing has to be merged — a query layer reads whichever artifacts are present and answers across them. This is not a new idea: behavior.json already sits beside graph.json and links to it by path, never by internal id. That is exactly why swapping the code substrate does not disturb the behaviour layer.

When a new graph is justified

A separate producer, with a different dependency and a different trust class. If one artifact held all four, a missing helm binary would degrade the whole file and you could no longer tell which edges survived. Separate files fail independently — which is the same reason the toolkit reports coverage-unknown rather than silently returning less.

4. Why config is not just "more languages"

This is the part worth internalising, because it is what forces the fourth graph.

In code, the relationship is in the text

import { foo } from './bar'

A parser reads it and knows this file points at that file. Same answer every time.

In config, it is not

image: myapp:1.2.3

Nothing there says which Dockerfile built myapp. The link exists by convention, not by syntax.

image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

Worse — the value is not even in the file. It is in values.yaml, merged by Go templating at render time. A Helm chart is not YAML until helm template has run.

graphify does handle config, but through a semantic pass — a model infers the relationships, and it needs an API key. That is a reasonable product decision, and the wrong trust class for freya, because blast radius blocks wrap-up. Blocking a commit on a parsed fact is fine; blocking it on a good guess is not. So freya uses graphify for code only (--code-only, deterministic, offline) and produces resource edges itself by rendering first and parsing second.

5. What "general" actually costs

The languages turn out to be the cheap part. graphify's grammar set already covers every language across webapps, Java projects and freya-devkit itself.

PieceWhat it takesWhen
Every languageone graphify adapter behind the contractv1
Manifests — pom.xml, package.json, go.modsmall deterministic parsers; feed module boundaries into the code graph. pom.xml is the load-bearing one — without it a Maven monorepo is one blobv1
Docs graphparse path:line citations and relative links. 62 already exist in this repo's own docs/v1
Docker, docker-compose, K8s manifests, CI workflowsplain parsing, no external binaryv1
Helmshell out to helm template, then parse the rendered manifests. The only piece needing a tool that may not be installedv2

The split is drawn at Helm because Helm is the only item that changes the shape of the problem — everything above it is parsing files that are already files.

6. Open questions

  • Which graphify? At least three near-identically named projects exist (Graphify-Labs/graphify, vchain/graphifyy, Graf-J/Graphify), and reported language counts vary from 19 to 40+. Pin down and verify hands-on before this reaches a spec.
  • Does graphify degrade or hard-fail? If it is not installed, does freya fall back to homegrown and say so, or refuse? The contract has to state this.
  • Cross-language mis-wiring. Syntactic substrates fail by linking Python's sorted() to a Swift func sorted. freya's rule is never to be confidently wrong, so per-edge confidence stops being optional.
  • Is the graph still reproducible? The homegrown one is content-stable but byte-unstable (measured: 10 of 10 differing entries were pure reordering). Do not assume a new backend inherits that — re-measure it.
  • Does this settle or reopen vision §6? §6 keeps behavior.json a sibling so the substrate choice stays decoupled. Putting the substrate behind a contract appears to reinforce §6 rather than conflict with it — which would dissolve the tension the 2026-07-12 "unify the graphs" lean created. Confirm that reading.
