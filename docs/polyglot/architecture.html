Track B: one contract, three artifacts

Visual companion to spec.md, which is the authoritative version. Scratch — deleted when the feature ships; the real version goes on the site.

The one-sentence version. Stop maintaining a homemade parser, put a contract where the parser was, plug an off-the-shelf tool in behind it, and keep each different kind of relationship in its own file joined by file path.

1. The problem

freya-code-graph is a regex import-scraper covering TS, JS, Python and Go. Real projects are Java, Helm, Docker, YAML, certs and shell scripts. Everything in the toolkit — blast radius, behaviour tracking, drift detection — stands on that graph, so a blind graph means a blind toolkit. Portability made freya run anywhere without making it see anything new.

2. The contract is the design

The instinct is to pick a better tool. The problem with picking a tool is that you get to do it again in two years. So the tool is not the architecture — the socket it plugs into is.

Two backends, not one. An interface with a single implementation is fiction — you discover what leaked into it the day you add the second. Homegrown and graphify are different enough (regex vs AST, zero-install vs dependency, 4 languages vs 37) that making both satisfy one contract proves the contract is real, which is what makes a third one cheap if it is ever wanted.

Homegrown is not legacy baggage. freya is stdlib-only today; graphify needs uv/pip and network access. The driving case for this whole initiative is a locked-down work laptop — and if enterprise policy blocks installing a Python package, graphify never runs in the one environment Track B exists to serve. The floor is what guarantees freya degrades to something everywhere rather than to nothing.

Two distinct opt-ins. graphify-the-backend is opt-in because it is a dependency you install. The semantic pass is opt-in because it costs money and needs a model. Either can be on without the other. When the pass runs it uses your existing subscription through the driver freya already owns — claude -p, copilot -p, never a separate API key — defaulting to gpt-5.6-luna on Copilot and Sonnet 5 on Claude, overridable with --model.

3. Three artifacts, not one store

There is more than one kind of relationship and they are not interchangeable — but fewer kinds than the first sketch claimed. The resource graph was dropped once we asked what consumes it (§5).

The join key is the file path. Every graph converges on files, so nothing has to be merged — a query layer reads whichever artifacts are present and answers across them. This is not a new idea: behavior.json already sits beside graph.json and links to it by path, never by internal id. That is exactly why swapping the code substrate does not disturb the behaviour layer.

When a new graph is justified

A separate producer, with a different dependency and a different trust class. If one artifact held all four, a missing helm binary would degrade the whole file and you could no longer tell which edges survived. Separate files fail independently — which is the same reason the toolkit reports coverage-unknown rather than silently returning less.

4. Why config is not just "more languages"

This is the part worth internalising, because it is what forces the fourth graph.

In code, the relationship is in the text

import { foo } from './bar'

A parser reads it and knows this file points at that file. Same answer every time.

In config, it is not

image: myapp:1.2.3

Nothing there says which Dockerfile built myapp. The link exists by convention, not by syntax.

image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

Worse — the value is not even in the file. It is in values.yaml, merged by Go templating at render time. A Helm chart is not YAML until helm template has run.

graphify does handle config, but through a semantic pass — a model infers the relationships, and it needs an API key. That is a reasonable product decision, and the wrong trust class for freya, because blast radius blocks wrap-up. Blocking a commit on a parsed fact is fine; blocking it on a good guess is not. So freya uses graphify for code only (--code-only, deterministic, offline) and produces resource edges itself by rendering first and parsing second.

5. What "general" actually costs

The languages turn out to be the cheap part. graphify's grammar set already covers every language across webapps, Java projects and freya-devkit itself, and it extracts package dependencies from pom.xml, go.mod and pyproject.toml — so the "manifest parsers" line item from the first sketch disappeared.

PieceWhat it takes
Every languageone graphify adapter behind the contract
Manifests, module boundariesfree — graphify already extracts them
Symbol-level edgesthread an optional symbol through the edge shape; file anchor stays
Docs graphparse path:line citations, links and related_code. 62 citations already exist in this repo
Agnosticism sweepthe Next/Prisma assumptions the graph does not fix: docs-manager templates, the Prisma check, the shape detector

What was cut, and why

Helm, Docker, K8s, the whole resource graph. Config relationships are one hop and never branch — a three-node chain is a list, not a graph. Nothing consumes the answer: if you change lib/auth.ts, knowing it eventually lands in a container image does not change which docs are stale or which behaviours to re-run. The code graph already answered.

Terraform is the one real DAG in that world — and it already ships terraform graph, so it would be consumed, never parsed. Not now.

6. Phase 0 — the spike, before anything else

The substrate choice gets measured, not argued. Five cheap tests against three repos: the testbed (232 files, 609 known internal edges), freya-devkit itself, and a Java project.

TestWhy it could stop the feature
Under-reportingDiff both backends' edge sets. A missing edge narrows a behaviour's closure, so it is not flagged as affected and a regression walks through the gate. A spurious edge only runs a test you did not need. Misses are the dangerous direction.
Deletion / stalenessgraphify's --update "preserves existing graph structure" — which could mean "does not rebuild untouched nodes" or "never removes anything". The second is fatal. Ours is already correct.
ReproducibilityOurs is content-stable but byte-unstable (measured: 10 of 10 differing entries were pure reordering). graphify unmeasured.
Config coverageDoes it give value-level YAML/JSON/HCL edges, or just structure? Either answer is fine — the point is to stop guessing.
Degradation & output locationWhat happens with graphify absent, and confirm it writes to its own graphify-out/ rather than into .graph/.

7. Open questions

  • Do docs edges anchor to symbols as well as files? Permitted, but most citations name a file or a concept, so the field would be mostly empty. Decide in Phase 4 with real data.
  • How are exclusions handed to graphify? A CLI flag, a config file, or a post-filter on its output. The decision is settled — exclusions are a project-level input the contract owns, and both backends honour them, so a backend never decides for itself what is out of scope. Only the plumbing is open.
