How it works

The contract, the two backends behind it, the shape of the data, and every way the system is allowed to fail.

The one-minute version

The code graph is produced by a backend. Which backend runs is a per-project setting. Whatever runs, the same contract governs what it must produce and what it must admit it could not see — and everything after the backend finishes thinking happens in one shared place, identically, for all of them.

knowledge-base/settings.json "which backend?" (default: the floor) │ ▼ ┌────────────────────────────┐ │ backends.select() │ never silent: the choice, and any fallback, │ │ is written into the artifact itself └──────────────┬─────────────┘ ▼ ┌────────────────────────────┐ ┌──────────────────────────────┐ │ backend.build(...) │───────▶│ a graph: nodes + edges │ │ homegrown | graphify │ │ and nothing else │ └────────────────────────────┘ └──────────────┬───────────────┘ ▼ ┌───────────────────────────────────────────────────────────────────┐ │ the contract's half — run once, the same way, for every backend │ │ │ │ link dependents → refuse to erase → validate → persist │ └───────────────────────────────────────────────────────────────────┘ │ ▼ knowledge-base/.graph/graph.json the active graph knowledge-base/.graph/graph.<backend>.json this backend's own copy

The split matters more than it looks. Before it, saving the file, checking it was valid and building the reverse index all lived inside the original resolver — so a different backend could do everything correctly and still produce nothing while reporting success. That is the failure this whole feature exists to remove, one level up.

The contract

skills/freya-code-graph/scripts/substrate.py. Standard library only, so a backend can depend on it without inheriting anything, and structural rather than a base class — a backend satisfies it by having the right attributes.

#ObligationWhy it exists
1Resolve the languages it claims, given a project root.The job.
2Report what it could not resolve. An unresolvable import is recorded as unresolved:<raw>, never dropped. A past defect: path aliases made every internal import resolve as external, producing an empty blast radius reported as if complete.
3Carry per-edge provenance — how directly the edge was read out of the source. A name-resolving parser can mis-wire across languages. An uncertain edge must not be presented as a certain one.
4Declare its coverage — the languages, extensions and relation kinds it actually handles. The headline failure. This is what lets a caller tell "no dependencies" from "does not read Java".
5Support incremental update, or decline it. A backend that cannot correctly remove deleted nodes says so, and the contract forces a full rebuild rather than trusting a stale incremental.
6Honour the project's exclusions, which are passed in. "vendor/ is not mine" is true whichever parser runs. Left to the backend, two backends would disagree about scope on the same repository.

Conformance is checked at runtime rather than by a type, and the check includes the exact call the caller makes, not merely that a method exists:

BUILD_KWARGS  = ('exclusions', 'non_interactive', 'selection_metadata')
UPDATE_KWARGS = ('exclusions', 'non_interactive', 'selection_metadata')

"Callable" is not a contract. A backend can pass an attribute check and still be uninvokable — which is exactly what happened, to this repository's own reference stub. The signature is bound against for real, so a non-conforming backend fails at registration instead of at query time.

The two backends

homegrowngraphify
Howregular expressions over source text tree-sitter ASTs, via an external binary
Needsnothing — Python standard library graphify on PATH (uv tool install or pip)
Languages4 — TypeScript, JavaScript, Python, Go 40, including Java, Kotlin, Swift, Rust, C#, Scala, Ruby, PHP, SQL, Terraform, Fortran, Elixir

Granularityfile → file symbol → symbol, projected onto file pairs

homegrown declares only two relation kinds even though the vocabulary has five. It resolves module references between files and has no notion of a symbol, so claiming calls because the word exists would make a caller trust a query it cannot answer. Overclaiming coverage is the failure the coverage block exists to prevent, and it applies to the backend that wrote the block as much as to any other.

Under-claiming is the worse direction, and graphify did it. Its extension list was hand-written from what two fixtures happened to produce — 34 of the 92 the tool actually dispatches — so a .groovy, .kts or .f90 file it had successfully parsed was written into the graph and then flagged by the contract's own validator as outside the declared coverage. It is now derived from graphify's dispatch table and pinned by a test that reads that table out of graphify's own interpreter.

Two things the coverage block still cannot say

graphify extracts no exports, and emits no external: edges for TS/JS/Python — it records package dependencies from manifests instead. Neither is a defect in the projection; the upstream extractor does not produce the material. But both are real differences between the backends, and the coverage vocabulary has no way to declare them.

Written down here and in the schema reference rather than left for someone to discover. If anything starts depending on exports, that is the moment the declaration needs a word for it.

Choosing a backend

Three rules, and the third is the one that was reversed after being built the other way.

  1. A named backend is used if it is available. Naming it — in the project's settings.json, or in the machine default it inherits from — is the opt-in; there is no separate permission list, because writing the name down is deciding. where that name comes from →
  2. A named backend that is unavailable degrades to the floor, and the run continues. It says so on stderr, and — more importantly — the fallback is recorded in the artifact as degraded_from, so a graph produced this way says on its face that it is thinner than it should be. A week later the stderr is gone; the graph is not.
  3. auto is the floor, and deliberately does not go shopping.
Rule 3 used to be the opposite, and that was wrong

auto originally scored every installed backend against the repository and picked the widest. With a second backend registered that stopped being hypothetical: graphify scored 63 against homegrown's 58 on this repository, and would have taken over on the next build.

Which means installing a binary anywhere on PATH would have silently changed the substrate — and therefore every blast radius — for every project on the machine at once, with no diff and no decision. A substrate change is supposed to be a measured migration.

Opt-in must not mean undiscoverable, though, so auto still runs the census — only to say what it is leaving on the table, which is the one thing a project cannot work out for itself:

code-graph: 'graphify' is installed and declares it reads 5 file(s) here that
'homegrown' cannot (.java, .kt).
  → freya code-graph --use graphify            (this project)
  → freya code-graph --use graphify --global   (and every future one)

The instruction rides in this run's output rather than living in the skill layer, where it would be read on every invocation to say nothing on almost all of them. It appears exactly when it is actionable, and it names a command rather than a file to hand-edit.

The hint counts only extensions that are real evidence. A backend may declare an extension whose selection is really name-based — package.json produces nodes, an arbitrary x.json does not — and those are excluded from the evidence while staying in the declaration. Otherwise the hint would fire on every repository in the world on the strength of a manifest the backend may well ignore.

Who decides, and where it is written down

Three layers, and only the middle one is new:

this project's knowledge-base/settings.json committed, travels with the repo ↓ (absent, or says "auto") the machine's ~/.freya/settings.json answered once, when you installed freya ↓ (absent) the floor homegrown, always available

An explicit name in the project file — including homegrown — is that project deciding for itself, which is how one repository opts out without changing the others. auto means defer. Absent means nobody has decided yet, and that is the only state the first build will write into.

Why the question is asked at install

Somebody has to choose, and three of the four places to ask are wrong:

WhereWhy not
Mid-workflow, in the terminal code-graph goes non-interactive whenever stdin is not a TTY — which is every agent-driven run and every wrap-up run. The prompt would fire almost exclusively for someone typing the command by hand.
Mid-workflow, through the agent Works, but the instruction telling the agent to do it lives in the skill layer, which is read on every invocation to say nothing on almost all of them. A standing cost for a question asked once per machine.
Per project, every time The same answer retyped in every repository.
At freya install chosen Run by a person, in a terminal, on purpose. The one moment a keyboard is guaranteed. freya update asks too, which is the whole migration for anyone installed before the question existed.
Which parser should freya use to read your code?

  [1] homegrown   4 languages — TypeScript, JavaScript, Python, Go. Built in
  [2] graphify    40 languages — adds Java, Kotlin, Swift, Rust, C#, Scala, …

Your choice (1-2, or Enter to skip):

It asks only when there is a real choice — a question with one answer trains people to skip questions — and only when the machine has not already answered. Enter skips, nothing is written, and it never blocks: a scripted install must not hang, and must not answer on your behalf either.

The half that makes a machine default safe

The first build in a project writes the machine answer into that project's own committed file.

Left implicit, the same commit would graph differently on a machine that has a default and one that does not — and integration behaviours' static fingerprints come from the graph closure into behavior.json, which is committed. The divergence would arrive as a diff that reads like behaviour drift. Written down, the repository is self-describing: a clone and CI resolve the same backend without sharing anyone's machine configuration.

A run with nothing configured writes nothing. "Not yet decided" is an honest state; a committed file recording the floor as though somebody chose it is the confidently-wrong answer this whole substrate exists to refuse.

freya code-graph --use graphify            # this project
freya code-graph --use graphify --global   # and every future one
freya code-graph --use homegrown           # opt this project out

The name is checked against the registry as it is written — the moment somebody is present to be told they typed it wrong, rather than a week later when it resolved to nothing and the project quietly ran the floor.

The file itself

knowledge-base/settings.json. Optional; absent, every default below applies.

{
  "substrate": {
    "backend": "auto",        // auto | homegrown | graphify
    "symbols": false          // record which symbol each edge leaves and arrives at
  },
  "directories": {
    "docs": "source",         // this project's docs/ really is source
    "packages/legacy": "exclude"
  }
}

Three properties were needed at once, and this location is the only one that has all three: it must survive a clone (a teammate gets the same backend), it must not be lost when the cache is cleared, and it must not add a file to the project root. Only knowledge-base/.graph/ is gitignored, so a file beside specs/ and decisions/ is committed by default.

Not package.json: Java, Python and Go repositories do not have one, and keying the polyglot toolkit's own configuration to a Node manifest is precisely the assumption this feature exists to remove.

A malformed file never fails a build. It degrades to defaults and says which key was wrong — a typo that is silently ignored is how a project ends up convinced it is running a backend it is not.

What is in scope

Some directory names are excluded by default: artifact trees like node_modules/ and dist/ at any depth, and convention names like docs/, examples/, scripts/ and generated/ at the repository root only.

That split is itself a fix. Matching a convention name at every depth is what hid forty of this repository's own files (skills/*/scripts/) and a real Next.js route (app/api/media/generated/route.ts). Matching an artifact name only at the root would let a nested node_modules/ through. Both rules are right for their own class of name.

Defaults, not verdicts

Nothing in this toolkit can know that your repository keeps real source in a directory called target/, or that your docs/ is a literate-programming tree. Say so in settings.json and it is believed.

Until 2026-08-20 that was accepted, written to disk, and then silently overruled — the file filter never consulted the verdicts at all. So the name lists were not defaults, they were hardcoded answers with no appeal, and a wrong one was unfixable.

Verdict sourceOverrides
settings.json, or a user classification Everything aimed at that directory — the convention lists and .gitignore — but not rules about what is inside it.
An ai classification Root convention names and .gitignore — but not artifact trees. A model classifying node_modules as source is a plausible failure and a person typing it is not, and the blast radius of the first is a 50,000-file graph.
rule / gitignore classifications Nothing. These are the defaults' own output, so letting them override would be circular.

Precedence, stated once: a stated verdict beats a derived one at any depth, and among equals the deepest wins. So packages/ can be source while packages/legacy/ is excluded.

An override used to have no floor, and that was worse than the defect it fixed

The check returned early for every path under an override and never reached the pattern matcher. So {"directories": {"packages": "source"}} on a workspaces tree pulled every packages/*/node_modules/** into the graph — the 50,000-file blast radius the two-tier design above exists to prevent, reached through an ordinary ancestor verdict.

And it could not be switched off: the classifier does not descend into a directory whose ancestor carries a stated verdict, so no nested exclusion is ever derived to catch it. The rule now is that the patterns are re-matched against the path below the override root — node_modules/ still catches the tail, while the entry naming the overridden directory itself matches no tail and correctly stops applying.

Getting there took three attempts, because three separate layers had to agree: the file filter, the directory classifier — which re-asserted the rule one level below an override and won, because a stale cached verdict sat deeper — and the exclusion set the CLI hands back into build(), assembled from the same .gitignore, which undid the override a step later. Overrides therefore travel on the contract itself, as Exclusions.overrides, so a backend that has never heard of the classifications cache honours them too.

An edge, anatomised

An edge used to be a string — the path it pointed at, sitting in an imports list. A string carries exactly one fact, so a.ts imports b.ts and a.ts re-exports b.ts were the same value, and "this function calls that function" could not be written down at all.

Schema 1 — until 2026-08-20 
"imports": [
  "src/lib/auth/config.ts"
]
Schema 2 — now 
"imports": [
  {"to": "src/lib/auth/config.ts",
   "kind": "imports",
   "provenance": "extracted"}
]

The far end

to going forwards, from in a dependents entry. It is one of three things, and the third is the interesting one:

  • a project-relative path — a real internal edge;
  • external:<package> — a third-party dependency, real but not ours;
  • unresolved:<raw> — it meant something in this project and could not be found. Never dropped. An honest gap beats a silent one.

kind — a fixed vocabulary of five

importsa file depends on another file, as stated in source
re_exportsa file re-exports another file's surface — barrels
callsa symbol invokes another symbol
inheritsa type extends or implements another type
referencesa symbol is named without being called

Fixed deliberately. A contract whose vocabulary each backend defines for itself is describing implementations rather than an interface, and a caller could not then ask "does this backend give me calls?" in a portable way.

provenance — how directly it was read

extracted means stated explicitly in the source text. inferred means derived by resolution the source did not spell out.

It is worth being precise about what this axis is not, because the obvious reading is wrong: it is not deterministic-versus-model-judged. The spike measured graphify emitting INFERRED edges from a pure AST pass with no model anywhere in the loop.

And it does not gate anything yet

The design says only extracted edges may gate wrap-up and inferred ones are advisory. No code implements that filter. The field is recorded faithfully on every edge and read by nothing, so an inferred edge reaches blast radius indistinguishable from an extracted one.

The practical exposure is small — over-approximating a blast radius is the safe direction, and exactly two file pairs on this repository rest solely on inferred links. But it was written down as a present-tense guarantee in the spec, in the decision record and on this page, and it was not true. Found by the final review; recorded rather than quietly deleted.

The optional refinement

With substrate.symbols on, an edge may also carry from_symbol, to_symbol and line. These refine the file anchor and never replace it, so anything that ignores them behaves exactly as it did before they existed — which is what makes symbol support optional per backend rather than a schema change.

Reading an old graph

Readers accept both shapes. graph.json is gitignored, so there is no committed copy to correct in a commit — an older one sits on someone's disk until something rewrites it, and refusing to read it looks exactly like a project with no dependencies. The schema version is what makes that tolerance temporary rather than permanent: without it there is no way to tell a graph that has been brought forward from one that never needed to be.

What is on disk

knowledge-base/ ├── settings.json committed — the project's choices └── .graph/ writes its own .gitignore ├── graph.json the active graph, whichever backend produced it ├── graph.homegrown.json per-backend copy ├── graph.graphify.json per-backend copy ├── docs.json doc section → code file ├── behavior.json COMMITTED — cannot be rebuilt from source └── classifications.json derived directory verdicts (cache)

Why two copies of the same graph. Switching substrates must not destroy the baseline you would want to diff the new one against — which is precisely the moment you need it. So each backend writes its own, and graph.json stays the active artifact that the other skills read.

A real entry, from this repository's own graph:

"skills/freya-code-graph/scripts/backends.py": {

  "imports": [
    {"to": "external:os",     "kind": "imports", "provenance": "extracted"},
    {"to": "external:sys",    "kind": "imports", "provenance": "extracted"},
    {"to": "external:typing", "kind": "imports", "provenance": "extracted"},
    {"to": "skills/freya-code-graph/scripts/settings.py",

     "kind": "imports", "provenance": "extracted"}
  ],

And the block every graph carries, which is the answer to "is this repository really this sparse, or is my backend blind?":

"substrate": {
  "backend": "homegrown",
  "coverage": {
    "languages":   ["go", "javascript", "python", "typescript"],
    "extensions":  [".go", ".js", ".jsx", ".py", ".ts", ".tsx"],
    "relations":   ["imports", "re_exports"],
    "incremental": true
  },
  "schema": 2,
  "exclusions": { "directories": [...], "patterns": [...], "overrides": ["docs"] }
}

Four more keys appear only when they have something to say, which is why a clean graph is byte-identical to one written before they existed: degraded_from and degraded_reason when a fallback happened, validation when the produced graph broke the contract, unmapped_relations when a backend emitted something this projection does not map, and direction_warnings when edge direction looked unreliable.

Asking it questions

CommandReturns
--query <file> Edge objects. "Tell me about this file" — so kind and provenance are the point.
--impact / --dependents / --dependencies Path strings. "Which files are affected" — a set of nodes, not edges.

That boundary is deliberate and it is the reason the edge migration did not ripple. Three other skills feed the node queries straight into set arithmetic, where an edge object raises unhashable type: 'dict' — in a different skill, for no gain. Drawing the line here meant behavior-graph, drift and behavior-runner needed no code change at all.

freya code-graph --build        --dir /path/to/project
freya code-graph --update       --dir /path/to/project     # incremental, via git diff
freya code-graph --query        src/lib/auth.ts
freya code-graph --impact       src/lib/auth.ts
freya code-graph --dependents   src/lib/auth.ts
freya code-graph --dependencies src/lib/auth.ts
freya code-graph --clear        --dir /path/to/project

--clear removes every backend's copy, not just the active one — a leftover copy is worse than a missing one, because it looks current and nothing reports it. It keeps classifications.json, which holds judgements you and the model made about which directories are source; a cache clear has no business discarding those.

Symbols projected onto files

graphify's nodes are symbols. The contract's are files. Its links run symbol → symbol. So every link is projected onto the file pair its endpoints live in.

graphify the contract validateToken() ──calls──▶ query() auth.ts ──calls──▶ db.ts │ │ in auth.ts in db.ts

Measured on this repository: 6,289 links out of the extractor, 73 distinct file pairs out of the projection. That collapse is not loss — most of it is structure that was never a dependency.

What gets dropped, and why

Relations that are not dependencies (2,861 links — 45%)

RelationLinksWhy not an edge
contains1,199 File has symbol. This is the node hierarchy, not a dependency.
method1,119 Class has method. The same thing, one level down.
rationale_for543 A docstring index — the source node's label is the first line of a docstring. 543 of 543 intra-file, 543 of 543 in .py files.

All 2,861 are 100% intra-file, which is the argument on its own: a relation that never crosses a file boundary cannot produce a file → file edge under any mapping. It can only produce self-edges.

Intra-file links of the relations we do keep (1,516 — 75% of the survivors)

A function calling another function in the same file is a real fact, and it has no file pair to be an edge between. Kept as an edge it would make a file its own dependent — and blast radius walks dependents, so every file would always be in its own blast radius. It is now a validation error as well as being skipped.

This is a deliberately discarded capability, not an oversight: recording an intra-file call graph needs a node type the contract does not have. It is filed rather than lost.

External modules — the one that fabricated edges

Found in review, Phase 2

graphify emits one node per external module — Foundation, express — and that node carries a source_file, which is whichever project file the module happened to be seen in first.

Read as a file, it fabricates edges. Three Swift files that each import Foundation produced s1.swift → s3.swift and s2.swift → s3.swift — edges that exist nowhere in the source, in the direction that inflates blast radius.

A module node now becomes external:<module>, which is exactly what the contract already had for this.

The mapping table has no default

An unmapped relation is counted and announced, never quietly folded into references:

"unmapped_relations": {"embeds": 40}

code-graph: graphify emitted 40 relation(s) this backend does not map (embeds);
they are recorded under substrate.unmapped_relations and dropped.

The reason there is no fallthrough is that the vocabulary cannot be enumerated reliably. Grepping graphify's own source for relation assignments yields 26 names — and reads_from, which this repository's graph actually contains, is not among them. A silent default would make a capability arriving upstream look like a repository that is thinner than it is.

Direction

graphify writes "directed": false, so the order of the source and target fields is the only carrier of direction. The spike measured what losing that costs: read as undirected, mean blast radius went from 5 files to 188. Each link also repeats its own source_file, which gives a free cross-check — when the two disagree it is counted into direction_warnings rather than silently trusted.

Symbol refinement

Off by default, behind substrate.symbols. On, an edge keeps its endpoints distinct by symbol name:

{"to": "skills/freya-code-graph/scripts/substrate.py",
 "kind": "calls",
 "provenance": "extracted",
 "from_symbol": "GraphifyBackend.translate()",
 "to_symbol": "make_edge",
 "line": 530}

Why off. Measured on this repository it turns 120 file-level edges into 698 — over the same 77 file pairs — because a test module calling one helper sixty times is sixty symbol pairs and one dependency. Nothing downstream reads them yet, so switching it on for everybody would be paying the size now for a consumer that does not exist.

The detail that made symbol names usable

graphify labels a method with its own name only — .setUp(), ._run(). Measured here, 64 of 1,731 code symbols share a bare label with a sibling in the same file: three different ._run() in one test module, and so on. A name that does not identify a symbol is not much use.

So method is dropped as an edge and kept as a lookup: the owning class is composed onto the label, giving TestGherkinScaffold.setUp(). Collisions go to zero.

Verified rather than assumed: --impact, --dependents and --dependencies return the same path strings with refinement on or off.

The behaviour layer

A behaviour records which files a test actually exercised. With Phase 3, an exercise entry may also carry the symbols that ran:

{"path": "src/lib/auth.ts", "symbols": ["validateToken", "refresh"]}

They come from the coverage report — istanbul's fnMap names each function and f counts its executions — and deliberately not from the code graph. observed means "the test ran this". Graph symbols would mix in things nobody executed, which is the difference between measurement and inference, and that distinction is what the whole trust model rests on.

Two filters, both from reading real output (775 functions across 123 files):

  • executed only — f[i] > 0;
  • named only — 405 of the 775 are (anonymous_N), where N is a positional counter per file, so inserting one function renumbers every later one. An anchor that moves when an unrelated function is added is not an anchor.

One entry per file, not one per symbol: behavior-graph intersects exercises[].path against the impact set, and splitting the entry would change that set's cardinality and every count derived from it. An entry with no symbols is byte-identical to one written before this existed — which is asserted by a test, not assumed.

The docs graph

docs.json records which doc section cites which code file, so "I changed graph_ops.py — which docs now lie?" is answered from a recorded edge instead of re-judged by a model on every run.

$ freya docs-graph --impact skills/freya-code-graph/scripts/graph_ops.py

docs/architecture.md#output-artifacts
docs/backlog.md#the-wall (cites line 30)
docs/decisions/ADR-005-repair-parsing-substrate-in-place.md#decision (cites line 328)

Everything is parsed, never inferred — from path:line citations in prose, markdown relative links, and the related_code: frontmatter specs and ADRs already carry. A docs graph that guesses is worse than none, because a wrong edge sends someone to rewrite a document that was fine.

Edges anchor at the section, not the line. A line number shifts the moment anyone inserts a paragraph; the heading is stable, and it matches the question actually being asked — which section is now wrong. The cited line is kept inside the edge as evidence.

On this repository: 35 documents, 171 edges.

When something fails

Six distinct failure modes, each with a defined answer. None of them is "return an empty graph and exit zero".

What happensWhat the system does
The configured backend is not installed Degrade to the floor. Continue. Record degraded_from in the artifact and say so on stderr.
The backend fails during the build — the tool was upgraded, it timed out, it exited zero having written nothing Degrade to the floor, with the exception text as the recorded reason. The floor is stdlib-only and always installed, so a traceback is never the best available answer.
The backend produces zero files where the cached graph had some refuse An empty files dict passes validation — there is no edge to be wrong about — so a backend that silently stopped working would overwrite a good graph and report status: built. It raises instead, and the previous artifact stays until something can replace it honestly.
The produced graph breaks the contract — a dangling edge, a self-edge, a file outside the declared coverage Write it, and record every error under substrate.validation in the artifact. The run's stderr is gone by the time anyone reads the graph.
The git query fails during an incremental update Return "unknown", never "nothing changed". Those had the same representation once, and the consequence was a permanent silent no-op.
The floor itself fails Raise. There is nothing left to fall back to, and pretending otherwise is the failure mode this whole system is built to refuse.
A backend is registered but does not satisfy the contract Fall back to the floor and record degraded_from. Until the final review this branch printed to stderr and recorded nothing, so the artifact was indistinguishable from an ordinary floor build.
The extraction has files but no edges at all refuse An upstream rename of the output's edge container would otherwise land as a full file set with every edge gone, reported as success — and the empty-graph guard cannot see it, because the file set is full.

Two of these were added by the final review, and one of them replaced a Python traceback. Refusing to overwrite a good graph is correct; reaching the user as an unhandled exception because they committed {"directories": {"src": "exclude"}} was not.

The rule underneath all six

A thin graph must never be indistinguishable from a thin repository. Every degradation is recorded in the artifact, because that is the thing that is still around a week later when someone asks why the blast radius looks small.
