The problem, and the plan

Where this started, what was rejected on the way in, and how the work was sequenced before any of it was written.

Every skill in this toolkit stands on one thing: a graph of which file depends on which. That graph was built by a few hundred lines of regular expressions that understood TypeScript, JavaScript, Python and Go. Point it at a Java repository and it produced nothing, said "Built dependency graph: 0 files scanned", and exited zero.

A toolkit that could not see

The release before this one made freya run anywhere — any agent, any operating system, no host-specific assumptions. It did not make freya see anywhere. Those are different problems and only the first had been solved.

The dependency graph is the load-bearing artifact. Everything else reads it:

┌──────────────────────────────┐ │ the code graph │ └──────────────┬───────────────┘ ┌─────────────┬───────┴───────┬──────────────┐ ▼ ▼ ▼ ▼ docs-manager spec-manager behavior-graph security-scan "which docs "which design "which behaviours "which findings are stale?" decisions?" must re-run?" are still live?"

So a blind graph is not a degraded feature — it is a toolkit that answers every question with a confident nothing. On a Java repository, "which behaviours does this change affect?" came back empty, and empty is indistinguishable from safe.

It went further than a wrong answer. spec-manager decides whether a repository is greenfield — brand new, nothing built yet — by asking the graph how many internal edges it has. Zero edges meant greenfield. So a mature Java codebase with two hundred classes was classified as an empty project, and every downstream skill adjusted its behaviour accordingly.

It could not see itself

The spike that was meant to evaluate a replacement found something about our own code first. Run against freya-devkit itself — fifty Python files:

Measured 2026-08-19

10 of 50 files indexed. Zero internal edges. Exit code 0. It printed Built dependency graph: 10 files scanned and reported success.

Because zero edges means greenfield, freya classified freya as a brand-new empty project.

Two independent causes, each sufficient on its own:

  • 'scripts' was in the always-exclude list and was matched against every path component. Every skill in this repository keeps its code in skills/<name>/scripts/, so forty files disappeared.
  • Python sibling imports — import behavior_graph, a file sitting in the same directory — were classified as third-party packages. Fixing the first defect took the count from 10 files to 51 and left one internal edge, which dangled.

Four more defects surfaced behind those two. They are listed in full on How it was built. The relevant point here is that they were fixed before any of the new architecture was written, and the reason is worth stating, because it was a genuine fork:

Phase 1's stated safety property was "no behaviour change, and the existing test suite is the regression gate." That suite was eighteen tests over synthetic fixtures, and it was green the entire time the resolver was this broken. A refactor pinned by a suite that cannot observe the behaviour preserves nothing — and what would have been frozen into the permanent zero-install floor was an empty graph on freya's own language.

Why an empty graph is worse than no graph

This is the principle the whole feature is built around, and it predates it — it is ADR-005.

A missing graph

Every consumer knows it has no answer. docs-manager falls back to a plain git diff. wrap-up says it could not compute a blast radius. The gap is visible and the operator can act on it.

A confidently empty graph

Every consumer gets an answer, and the answer is "nothing is affected". Nothing warns. The behaviour is not re-run, the doc is not flagged, the finding is closed — and the run reports success.

So the requirement is not "read more languages". It is: a backend must be able to say what it could not see, and everything downstream must be able to tell "this repository has no dependencies" from "this parser does not read Java".

Why not "just pick a better parser"

The obvious move is to find a good multi-language parser and wire it in. It was rejected, and the reason is one sentence: picking a tool means picking again in two years, and by then five skills depend on its output shape.

So the parser is not the architecture. The socket it plugs into is.

Why two backends, not one

An interface with a single implementation is fiction. It silently encodes the assumptions of its only caller, and nobody finds out until the second one arrives.

That is not a slogan here — it is what happened. The contract was written in Phase 1 with one backend behind it, and a review then built a second one that satisfied every documented obligation. It crashed the command-line twice, and then exited zero having written no graph at all. The full account is on How it was built.

Homegrown and graphify differ on every axis that matters — regex against AST, zero-install against a dependency, four languages against forty, file-level against symbol-level — so making both satisfy one contract is real evidence the contract is real.

Why the old one stays

The load-bearing constraint

The driving case for this whole initiative is a locked-down work laptop. freya is stdlib-only; graphify needs uv or pip and network access. If enterprise policy blocks installing a Python package, graphify never runs in the one environment Track B exists to serve.

Keeping the homegrown resolver is what guarantees freya degrades to something everywhere rather than to nothing. It is not legacy baggage. It is the floor, and the floor is load-bearing.

That constraint decided several later arguments on its own — most visibly that the default never goes shopping for a better backend, and that monorepo package resolution had to be fixed in the homegrown resolver rather than left for graphify to cover.

What we deliberately did not build

Roughly half the original design was cut before implementation started. Each cut has a reason, and each is recorded so that it is not silently re-litigated later.

Not builtWhy
A resource graph for Docker, compose and Kubernetes A graph earns its keep on transitive closure. Config relationships are one hop and never branch: deployment.yaml → myapp:1.2.3 → Dockerfile → src/. A three-node chain that does not branch is a list. And nothing consumes the answer — knowing that lib/auth.ts eventually lands in a container image does not change which docs are stale.
Helm charts A chart is a Go template, not YAML, until helm template runs: image: {{ .Values.image.tag }} is not a value. Highest cost in the feature, least value.
A config identifier index Invented as the cheap replacement for the resource graph, then dropped. Worth reading as a caution: it was dropped because "graphify already parses YAML deterministically", and the spike refuted that premise. The conclusion survived on separate reasoning; the justification did not.
Terraform HCL parsing The one genuine branching DAG in the config world — and terraform graph already emits it. Consume that if it is ever wanted; never hand-roll HCL.
A SCIP backend Compiler-grade precision requires each language's full toolchain and a green build. That inverts "point it at any repo and it works".
Database migrations as graph material An ordered append-only log is a chain, not a DAG, and "what does the schema look like now" is answered by the schema file. Folding migrations to derive the current schema means executing them — the same must-run-to-know problem as Helm.
Materialising the governance graph SPEC → BEHAVIOR → TEST → CODE already exists and is navigable. Materialising it means another derived cache to keep in sync. Filed with a revisit trigger.

What counts as done

Four criteria, written before anything was built:

  1. Pointing freya at a Java repository produces a code graph with real internal edges.
  2. On the repositories the old resolver already handled, the new substrate does not under-report relative to it.
  3. docs-manager can answer "which docs does this change affect?" from a recorded edge rather than by re-deciding it every run.
  4. No project is required to install anything to keep what it has today.

All four hold. The evidence for each is on How it was built.

Measure first, build second

The substrate decision was made a measurement, not an argument. Nothing else started until a spike passed five acceptance tests, written down before anything was run, against three repositories: a 232-file Next.js testbed with 609 known internal edges, freya-devkit itself, and a hand-built Java project.

TestWhat it could have stopped
9.1 Under-reporting
blocking		 Build both backends on one repository and diff the edge sets both ways. A missing edge narrows a behaviour's closure, so the behaviour is not flagged as affected and a regression walks through the gate. A spurious extra edge only runs a test you did not need. Misses are the dangerous direction.
9.2 Deletion and staleness graphify's incremental mode "preserves existing graph structure", which could mean "does not rebuild untouched nodes" or "never removes anything". The second is fatal — a graph that accumulates deleted symbols returns a blast radius pointing at code that no longer exists.
9.3 Reproducibility Build twice on identical input and diff. If a substrate is not content-stable it cannot be trusted incrementally at all.
9.4 Config coverage Does YAML/JSON/HCL support yield real edges or nothing? Either answer was acceptable; the point was to stop guessing.
9.5 Degradation and output location What happens with graphify absent — and does it write into its own directory, or into ours? The second matters because behavior.json lives in ours and is the one artifact that cannot be regenerated from source.

Six phases

PhaseDeliverable
0 The spike. Five acceptance tests, three repositories. Nothing else starts until it passes. done
1 The contract. Define the interface; move the existing resolver behind it with no behaviour change; add coverage declaration and the unresolved signal. done
2 The graphify backend. Map its output onto the contract. Selection, degradation and provenance tagging. Re-run the blocking gate on all three repositories. done
3 Symbols. Extend the edge shape with an optional symbol, and thread it into the behaviour layer. File-level behaviour remains the floor throughout. done
4 The docs graph. A citation parser, docs.json, the chunking rules, and a docs impact query so staleness is read off a recorded edge instead of re-judged every run. done
5 The agnosticism sweep. The Next.js and Prisma assumptions the graph does not fix: doc templates, the stack detector, and the greenfield classifier. done

Phases 4 and 5 were done before 2 and 3, deliberately: both were blocked on nothing, while 2 and 3 were blocked on a design question the contract had left open — what a single edge is allowed to say.
