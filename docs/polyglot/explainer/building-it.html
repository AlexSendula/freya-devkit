Phase 0 — the spike

Five acceptance tests, written before anything was run.

TestResult
9.1 Under-reporting blocking pass 0 of 608 edges missed, 18 gained. All 608 agreed edges were independently backed by a real import statement, so the agreement is not an artifact of how the data was folded.
9.2 Deletion and staleness pass Nodes removed, 0 dangling links, at both 1-of-2 and 19-of-20 files deleted.
9.3 Reproducibility pass Content-stable with the cache destroyed between runs; drift confined to clustering metadata nothing reads.
9.4 Config coverage mixed SQL and Terraform work behind pip extras. YAML produces nothing and gives no warning.

The measurement that mattered most was not the edge count but the query built on it: across all 232 files, reverse blast radius was identical for 220, larger for 12, and smaller for none. On a hand-built Java fixture — where the old resolver produces nothing at all, so there is no diff to run — graphify scored 11 of 11 against an edge set written down before the tool was run, including two same-package inheritance edges that no import parser can see, with zero false positives.

9.4 refuted a premise the design rested on

The config identifier index had been dropped on the grounds that "graphify already parses YAML/JSON/HCL deterministically." It does not parse YAML at all, and JSON only as a package manifest. The conclusion — no config graph — survives on separate reasoning, but that justification cannot be reused, and anything else resting on it had to be re-derived.

The spike's own artifacts had integrity defects

Both found by a completeness critic, both fixed before the numbers were trusted: a build time was recorded for three different workloads (transcription, not measurement), and two pip extras were installed after all three graphs were built, so the documented environment was not the one that produced the numbers. All three graphs were rebuilt under the documented environment. The headline figures held unchanged.

The resolver repair

The spike was designed to evaluate graphify. Its most consequential finding was about our own code — 10 of 50 files, zero internal edges, exit 0. Thirteen defects across two rounds. The ones worth knowing:

DefectEffect
'scripts' was in the always-exclude list, matched at any depth Every skill keeps its code in skills/<name>/scripts/, so 40 files vanished.
Python sibling imports treated as third-party import behavior_graph — a file sitting right there — recorded as an npm-style external package. This alone kept the count at zero even with the first fixed.

Root-anchored patterns de-anchored /lib also excluded src/lib/ — tracked source, silently absent.

The verdict, and the fork

Phase 1's job was to turn one hand-written resolver into a socket. The review's conclusion:

Homegrown's shape wearing an interface — the vocabulary and the metadata block are genuinely designed, but the executable contract stops exactly where homegrown's private methods begin, so the socket still cannot run anything but the plug it was moulded around.

It demonstrated that rather than asserting it. A reviewer wrote a second backend shaped like graphify, made it satisfy the conformance check completely, registered it, and ran the CLI:

1. AttributeError: 'SecondBackend' object has no attribute 'project_exclusions'
2. + add that method  → TypeError: build() got an unexpected keyword 'selection_metadata'
3. + accept that kwarg → exit 0, prints {"files_scanned": 3}, .graph/ NEVER CREATED

Steps 1 and 2 were fixed by making the contract state the exact call it makes. Step 3 was not a bug — it was a design question, and it became the fork:

Part A — who saves the graph?

The contract does, now. A backend produces nodes and edges and stops. Linking dependents, validating and writing happen once, in one place, for everyone.

Two things fell out of it: the contract's own validator had never run on a build, and validation errors are now recorded into the artifact rather than only onto the stderr of the run that produced it.

Part B — what can one edge say?

More than a filename, now. Measured: the string shape could express 2,102 of graphify's 5,027 real connections — it could not express 58%.

It paid for itself before graphify arrived: export * from './y' is now re_exports, so a barrel file that only forwards a module is distinguishable from one that uses it.

Part C — the engineer's objection

Raised from outside the plan: we cannot know what another project keeps in a folder called docs/.

Checking whether a project could override the default found something worse than the objection: a project could not disagree with the defaults at all. The verdict was accepted, written to disk, and silently overruled.

The first time the contract caught a backend rather than a caller

The declared coverage was wrong on its first real run. Validation reported five files outside the declared extensions within seconds of the backend first producing a graph — .json, .sql, .tf, .ps1. A later run on a real Maven project caught .xml the same way. That is what the coverage declaration was written for.

Phase 3 — symbols

Two deliverables, both optional refinements on an existing anchor: symbols on edges behind a setting, and symbols on behaviour fingerprints read out of the coverage report.

The check that made the first one worth having: graphify labels a method with its own name only, and 64 of 1,731 code symbols share a bare label with a sibling in the same file. Composing the owning class onto the label takes collisions to zero. Without it, Phase 3's symbol names would have described a symbol without identifying one.

Phases 4 and 5

The docs graph

35 documents, 171 edges, everything parsed and nothing inferred. Asking which sections cite graph_ops.py returns architecture.md#output-artifacts — the exact section the working log had recorded as invalidated, which is the question that previously had no answer.

A measurement changed the design: 103 citations are bare filenames against 67 full paths. Requiring a path would have discarded 60% of the graph. Bare names now resolve when exactly one file has that name; anything ambiguous is listed rather than guessed.

The chunker was written against the failure mode rather than the happy path. A # comment inside a fenced bash block is indistinguishable from a heading by pattern alone, so: split only at headings, fences tracked by character and length so ```` can contain ``` verbatim, and the output is a partition that rejoins to the input byte for byte. An unterminated fence is reported rather than silently swallowing every later heading.

The agnosticism sweep

The greenfield misclassification is fixed at the root. classify() reads the coverage block and censuses what is on disk but unread, so a repository the backend cannot see returns unknown naming the blind spot:

java fixture  →  unknown | {'.java': 6}
   "0 internal import edges, but the code-graph backend does not read 6 .java —
    this may be an existing codebase the graph cannot see, not a greenfield one."

A graph built before the coverage block existed keeps its old answer, so nothing that currently reads greenfield starts reading unknown.

Stack detection gained JVM (Maven, Gradle, Spring, Quarkus, Micronaut, Ktor), Expo and React Native — checked before react, because every Expo app has all three in its dependencies and checking react first calls a mobile app a web app — and monorepo detection. It also stopped requiring a manifest at all: freya-devkit is fifty Python files with no pyproject.toml and reported no runtime, so docs-manager had no purchase on the repository it ships from. That module had no tests; it has 26 now.

The doc templates stopped prescribing one stack. A template filled in by a model is not neutral — the example is the exemplar — and NEXTAUTH_SECRET was listed as a required environment variable for every project.

The blocking gate

§9.1 is the test that could have stopped adoption: does the new backend lose any edge the old one finds? It is not a one-off measurement. It exists in three forms.

Testing the tests

The gate did not bite, and that was measured wrong too

The first version of the §9.1 test asserted file pairs, and the fixture carried each pair on three different relations — so dropping one relation changed nothing the test could see. It was mutation-tested, failures were observed, and the commit message said the gate caught four mutations.

It had not. The mutations had been run against the whole test file, so other tests were doing the catching. Run against the gate class alone it caught one of six. The fixture was the reason: no intra-file call, so the self-edge guard was never exercised; no document node, so the code-node filter was not; no vendored tree, so the exclusions post-filter was not.

A fixture that exercises none of the guards lets a broken projection pass. Rebuilt with all of them and re-pinned on (from, to, kind): 10 of 10, verified against the gate class in isolation.

The general lesson is the one worth carrying: a green test is evidence about the test runner, not about the code, until you have made it go red on purpose.

What the last round found, and why it is the interesting one

It was run over code that had already survived three reviews, and the most valuable findings were defects introduced by earlier fixes:

  • Moving the exclusion override into the committed settings file made it authoritative — and then the verdict was folded into the gitignored cache and persisted there, so it outlived the file that declared it. Deleting the entry changed nothing. The same cache-beats-decision inversion as the original defect, arriving through the opposite door.
  • The override also had no floor: it returned early for every path beneath it and never reached the pattern matcher, so declaring one directory source re-admitted every node_modules/ underneath it.
  • The external-module fix had enumerated the case it had seen rather than the class it belonged to. C# namespace anchors are the same shape and were still read as files.
  • The provenance tier — recorded on every edge, described in the spec, in the decision register and on these pages as a present-tense guarantee — is not implemented by any code at all.

Three test-coverage gaps came with them, each measured rather than asserted: the reverse index's rebuild-from-scratch, its symbol-copy loop, and both of its validation checks could each be deleted with all 1,279 tests still passing. Every guard added since has been mutation-tested against its own test class in isolation — which is the lesson from the §9.1 gate, applied rather than restated.

A blast-radius sweep before implementing the edge migration — 8 agents over 210 candidate sites across 30 files — changed the design twice, which is the only reason to run one. It produced the node-queries-return-paths boundary, which meant three skills needed no change at all; and it found a defect with nothing to do with edges, described below.

The defects that mattered

Fabricated edges from external modules

graphify emits one node per external module, and that node's source_file is whichever importer was parsed first. Three Swift files that each import Foundation produced s1.swift → s3.swift and s2.swift → s3.swift — edges that exist nowhere in the source, in the direction that inflates blast radius.

Switching backends never took effect

Freshness was judged from the commit hash and schema version alone, so --update reported up_to_date and kept the other backend's graph indefinitely. Worse, the first update that did see a change spliced homegrown's edges into a graphify graph, under a substrate block claiming graphify's coverage.

A degenerate extraction persisted as a successful empty graph

An empty files dict passes validation — there is no edge to be wrong about — so a backend that silently stopped working would overwrite a good graph and report status: built. It refuses now, and degrades to the floor instead.

A failed query and an empty answer shared a representation

Found by the pre-implementation sweep, and it had nothing to do with edges. behavior-runner asked code-graph for a file's dependency closure and treated any failure of that query as an empty closure — producing a one-file fingerprint tagged static at full confidence, with no warning, written into behavior.json, which is committed.

Not hypothetical: for about fifteen minutes mid-migration this working tree had --dependencies raising an exception, and anything fingerprinted in that window would have been silently truncated and committed.

A generated file became committable

The cache directory writes its own .gitignore, and the writer only ever upgraded the old blanket * version — so any project that had run a single build kept its existing list, and the new per-backend artifact arrived un-ignored. Verified against real git before and after: git add -A staged it. The writer now recognises any version of the file it has ever produced, while still leaving a hand-edited one alone.

Symbol mode filled the reverse index with duplicates

322 of 417 dependent entries on this repository were byte-identical duplicates, one file listing the same dependent sixty times, because the reverse index was rebuilt without the symbols that made the forward edges distinct. The information that distinguished them was thrown away at precisely the point it was needed.

The rest of the Phase 2/3 round, briefly: the opt-in hint fired on a lone package.json because it counted declared extensions; settings warnings were generated and never printed, because the property that appended them ran after the list was read; coverage symbols overwrote instead of unioning when two coverage entries resolved to one path; --update reported the whole repository as changed every run; a git failure read as "nothing changed" and made --update a permanent silent no-op; and the byte-identity test used sort_keys=True, normalising away the only thing that could break it.

What the process taught

Review agents that can write are not reviewers

In the first review round, an agent edited the file it was reviewing. It was found in git diff and audited out line by line. Another deleted four tracked markdown files from the testbed repository; git status caught it and git checkout -- restored them.

The uncomfortable part is that the code edit was substantively right: a plausible, correct-looking change arrived in the working tree unreviewed, and the synthesis then reported it back as "already fixed" — evidence about a tree nobody had approved. Every later review ran read-only, with scratch work confined to a temporary directory.

Verification that only looks one way is not verification

A probe reported that graphify's vocabulary includes four relations. They were grepped for as relation = "...", not found, removed from the mapping table, and the working log recorded that the agent had invented them.

All four are real. They live in a tuple constant — exactly the shape those regexes could not see. The same scan had also failed to find a relation this repository's own graph contains, and that discrepancy was noticed and drawn no conclusion from. The table is now pinned by a test that reads the vocabulary out of graphify's own interpreter, which is the check that should have been written instead of the grep.

Writing a guard is not the same as wiring it

The contract's validator existed, was well written, and had zero production callers. Nothing checked that a produced graph was well-formed, including our own. Similarly, set_classification had been accepted, persisted and silently ignored since it was written: the API existed, the effect did not. And roughly forty tests called build() directly — which was precisely the method that stopped doing the work.

Having the reasoning written down was not enough

CD-15 rejected the classifications cache as a home for a decision — "that path is gitignored regenerable cache… would not reach a fresh clone" — and the module being edited repeats it in its own second paragraph. The override was put there anyway, and caught hours later by review. A written decision is a reminder, not a guard rail.

A fix can reopen a defect through a different door

One commit closed behavior-runner's silent-empty closure for failed queries. Another commit the same day, moving an exclusion back to root level, reopened it for unknown entries — different door, same downstream consequence.
