Everything in this toolkit stands on one artifact: a graph of which file depends on which. That graph was built by regular expressions that understood four languages. Point it at a Java project and it found nothing, said "Built dependency graph: 0 files scanned", and exited successfully. This feature replaced the parser with a socket — so a project can run the built-in resolver, or a real multi-language one, and everything downstream keeps working either way.

1. What was actually broken

Not "it only reads four languages". The problem was that it did not say so.

The failure, in one line

A repository the tool cannot read was indistinguishable from a repository with nothing in it.

So on a Java codebase, "which behaviours does this change affect?" came back empty — and empty looks exactly like safe. Worse: another skill decides whether a project is brand new by asking the graph how many internal connections it has. Zero meant brand new. A mature Java codebase was therefore classified as an empty starter project, and every skill downstream adjusted its behaviour to match.

Then the spike that was meant to evaluate a replacement found the same bug pointed at us:

Building the graph on freya-devkit itself indexed 10 of 50 Python files, produced zero connections, printed "Built dependency graph: 10 files scanned", and exited 0. freya classified freya as a brand-new empty project.

Two independent causes, either sufficient on its own — an exclusion rule matching a directory name at every depth instead of at the top level, and Python sibling imports being filed as third-party packages. Four more defects were behind those. the full account →

2. The idea: a contract, not a tool

The obvious fix is to find a better parser and wire it in. That was rejected, for one reason: picking a tool means picking again in two years, and by then five skills depend on its output shape.

So the parser is not the architecture. The socket it plugs into is.

Two backends, not one, deliberately. An interface with a single implementation is fiction — it encodes the assumptions of its only caller and nobody finds out until the second one arrives. That is not a slogan here: the contract was written with one backend behind it, and the review that built a second one found it could not actually run anything else.

Why the old parser stays

The case that started this whole thing is a locked-down work laptop. freya needs nothing but Python; graphify needs a package install and network access. If policy blocks that, graphify never runs in the one environment this exists to serve. Keeping the built-in resolver is what guarantees freya degrades to something everywhere rather than to nothing.

4. How it works, in five steps

  1. A project says which backend it wants — or says nothing and defers to the answer you gave once, when you ran freya install. The default never goes shopping: installing a tool somewhere on your machine must not silently change what every project on it believes about itself. The first build in a project writes that answer into the project's own committed settings, so a clone and CI resolve the same backend as you do.
  2. The backend reads the code and produces nodes and edges. That is all it does. It does not save anything.
  3. The contract does everything after that — builds the reverse index, refuses to overwrite a good graph with an empty one, validates the result, and writes the files. Once, identically, for every backend.
  4. The graph records who made it and what they could see — languages, extensions, relation kinds, and any fallback that happened. This block is the whole answer to "is this repo really this sparse, or is my parser blind?"
  5. Everything else reads one file, knowledge-base/.graph/graph.json, and does not care which backend produced it.

The one design decision worth understanding

An edge used to be a string — the path it pointed at. A string carries exactly one fact, so "A imports B" and "A re-exports B" were the same value, and "this function calls that function" could not be written down at all.

Before 
"imports": ["src/db.ts"]
After 
"imports": [{
  "to": "src/db.ts",
  "kind": "imports",
  "provenance": "extracted"
}]

Measured: the old shape could express 2,102 of the new backend's 5,027 real connections. It could not express 58%. The change paid for itself before the new backend even arrived — a barrel file that only forwards a module is now distinguishable from one that actually uses it. the trade-off in full →

5. How we know it works

One test could have stopped this feature: does the new backend lose any edge the old one finds? Misses are the dangerous direction — a lost edge narrows a behaviour's blast radius, so the behaviour is not flagged, so a regression walks through the gate. A spurious extra edge only runs a test you did not need.

The Java figure matches a ground-truth edge set that was written down by hand before the tool was ever run — 11 of 11, including two same-package inheritance edges no import parser can see. The single Python "miss" is the old resolver's own false positive: an import statement inside a string literal, which its regexes read and a real parser correctly ignores.

That test now exists in three forms — a committed fixture the suite runs on every commit, a live re-derivation on all three repositories, and the original spike harness, kept runnable. how the gate is enforced →

And the test itself was wrong the first time

The first version of that gate was mutation-tested, appeared to catch four defects, and was written up as such. It had not — the mutations were run against the whole test file, so other tests were doing the catching. Against the gate alone it caught one of six, because its fixture exercised none of the guards. 6. The decisions that shaped it

Twenty-seven, each recorded with the alternative it beat. The eight that decided the most:

DecisionThe alternative it beat
A contract, not a tool. Any backend that satisfies it can produce the graph Adopt the best parser and wire it in. Fastest to ship — and it reopens the whole question the first time that parser stalls
The old resolver stays as the floor. Zero-install, always available Replace it once the new one works. Less code, one path — and it makes the zero-install property depend on a third-party package
The default never switches on its own. Naming a backend is the opt-in Pick whichever backend reads the most. Measured: the new one scored 63 to 58 here and would have taken over on the next build — changing every blast radius on the machine, with no diff
You are asked once, at install, and the first build records the answer in the repository Ask in the middle of the workflow. Every agent-driven run has no keyboard attached, so the prompt fires for almost nobody — and the instruction telling the agent to ask would be read on every invocation to say nothing on nearly all of them
An edge is an object. Kind and provenance, and a versioned schema Stay file-level and honest. Cheapest — and it gives up 58% of what the second backend knows to avoid a migration that only gets more expensive
Symbols refine a file anchor, never replace it. Off by default Move to symbol anchors. Sharpest — and it makes every rename a breaking change to a committed artifact
Every default is arguable. A project can override any exclusion Scope the rule to this repository. Not implementable without hardcoding a path — and it leaves every other project with defaults it cannot appeal
An answer says what it could not see — to the agent, in the payload, and silently when there is nothing to say Print it for the human. The build almost never has one attached, so the warning lands nowhere — the same mistake the install-time question was written to avoid, one layer down

7. Where we were wrong

Four worth naming, because each cost real work and each has a general lesson.

An override that vanished on clone

The ability to override a default shipped storing that override in a gitignored cache file. It worked for whoever typed it and disappeared on git clone — so CI and every colleague would have silently graphed a smaller codebase and been told the build succeeded.

The decision rejecting that file, on exactly this ground, already existed — and was repeated in the second paragraph of the module being edited. Having the reasoning written down is a reminder, not a guard rail.

Correcting something that was right

An automated probe reported four relation names in the new backend's vocabulary. They were grepped for, not found, deleted from the mapping table, and the log recorded that the agent had invented them.

All four were real — in a tuple constant, exactly the shape those regexes could not see. The same scan had also missed a relation this repository's own graph contains, and that discrepancy was noticed and ignored. Verification that only looks one way is not verification.

Edges that did not exist

The new backend emits one node per external module, carrying the name of whichever file imported it first. Read as a real file, that fabricated edges: three Swift files importing Foundation produced two connections that exist nowhere in the source — in the direction that inflates blast radius. Caught by adversarial review, not by a test.

And the fix was itself incomplete. It named the case it had seen rather than the class it belonged to, so C# namespace anchors — the same shape one language over — were still read as files until the final review.

A guarantee that was never implemented

Every edge records whether it was read straight out of the source or worked out by resolution, and the design says only the first kind may block a commit. The final review went looking for the code that enforces that and there is none. The field is written faithfully and read by nobody. It had been stated as present fact in the spec, in the decision record and on these pages. The exposure is small — over-approximating a blast radius is the safe direction — but a guarantee nobody implemented is exactly the kind of claim this project is supposed to be able to check.
