The complete version

Everything measured, decided and found, with the reasoning. The short version is here if you want the summary first.

The verdict on Phase 1 ← short

Phase 1's job was to turn a single hand-written resolver into a socket — a fixed contract that a second tool can plug into, so the rest of the toolkit does not care which one is running. The review's conclusion:

Homegrown's shape wearing an interface — the vocabulary and the metadata block are genuinely designed, but the executable contract stops exactly where homegrown's private methods begin, so the socket still cannot run anything but the plug it was moulded around.

It demonstrated this rather than asserting it. A reviewer wrote a second backend shaped like graphify, made it satisfy the conformance check completely, registered it, and ran the CLI:

1. AttributeError: 'SecondBackend' object has no attribute 'project_exclusions'
2. + add that method  → TypeError: build() got an unexpected keyword 'selection_metadata'
3. + accept that kwarg → exit 0, prints {"files_scanned": 3}, .graph/ NEVER CREATED

Steps 1 and 2 are fixed. The contract now states the exact call it makes and verifies a backend can accept it — a check that caught our own reference stub the moment it was added, which is the point of having it.

Step 3 is not a bug. It is a design question with three defensible answers, which is why it is waiting for you.

Part A — who owns saving the graph? ← short

Three jobs happen after a backend finishes thinking:

  1. Validate the result is well-formed.
  2. Build the reverse index — dependents, i.e. "who imports me". This is what blast radius actually reads.
  3. Write the files to disk.

Decided 2026-08-20 · built

All three used to live inside CodeGraph, our own resolver. _write_graph was a private method of it. validate_graph — the guard written specifically to catch "a backend emitting something downstream cannot read" — had zero callers in production code. And dependents was not mentioned anywhere in the contract, despite being the thing every consumer reads.

Why that matters concretely. A graph with correct imports and no dependents passes validation, and then get_dependents('src/db.ts') returns an empty set. Blast radius comes back empty and confident. That is worse than a missing graph, because drift.py keys its safety fallback on the field being present — so the operator is told the radius is narrow rather than unknown.

What shipped

build() and update() now return a substrate.Result — the graph, plus what the backend did to get it. run_build / run_update own everything after: derive dependents, validate, write both artifacts. dependents is a pure function of imports, so deriving it centrally is strictly better than trusting every backend to emit it correctly — and it is rebuilt from scratch rather than appended to, so a dependent whose import was deleted does not survive.

Two things came out of it that were not in the plan. Validation now actually runs, on every build, and when it fails it records the errors into the artifact under substrate.validation — the run's stderr is gone by the time anyone reads the graph. And the contract now requires a backend to carry its project_dir, because the contract is what writes the files and it has to know where.

The tests were the tell. Forty-odd of them called CodeGraph.build() directly and asserted on what came back, which meant the suite had never once exercised the path production uses. They all go through the runner now.

Part B — what can a single edge say? ← short

Decided 2026-08-20 · built

This section was titled "does the graph track files, or symbols?" until 2026-08-20, and that was wrong in a way that caused real confusion. The nodes are files and stay files. The question was only ever about the edges between them — what one edge is allowed to state. Symbols are Phase 3; this is what makes room for them.

An edge was a string: "src/db.ts" sitting in the imports list of src/auth.ts. That says file A depends on file B and nothing more.

graphify knows considerably more — that validateToken() calls query(), that AuditedStore extends InMemoryStore, and whether each fact was read directly from the source or inferred. Our contract has words for some of that (calls, inherits, references are all in the vocabulary) but nowhere to put them, so they collapse to a file pair and the kind is discarded.

The sharper problem

The contract's obligation 3 mandates per-edge provenance — every edge saying how it was obtained. The constant exists. It is referenced by no code, and it cannot be: validation requires each entry to be a plain string, so an edge object is rejected outright.

And spec §10 lists provenance tagging as a Phase 2 deliverable. So Phase 2 as currently written cannot ship without reopening the very contract Phase 1 existed to close. That is the real reason this needs deciding now rather than later.

The three answers, and the one taken

OptionWhat it meansCost
File-level, honestly Remove calls/inherits/references from the vocabulary and strike provenance from the obligations and from Phase 2. Cheapest. Matches spec §5's deliberate file-level floor. Loses CD-16's finer promise and most of what graphify knows.
Edge as an object now recommended {'to': …, 'kind': …, 'provenance': …} instead of a bare string. Touches every reader of imports. But there is one producer and one consumer today, so it will never be cheaper — every later phase adds a reader.
Defer to Phase 3 Keep strings now; add the richer shape when symbols land. Matches the original plan, but Phase 2 then promises provenance it cannot deliver.

What shipped

An edge is {"to": …, "kind": …, "provenance": …}, and a reverse edge is the same thing keyed from. kind comes from the contract's fixed vocabulary; provenance says how directly it was read out of the source, which — as Phase 0 measured — is not the deterministic-versus-model axis it is easy to mistake it for.

It paid for itself before graphify arrived. export * from './y' is now recorded as re_exports, so a barrel file that only forwards a module is distinguishable from one that actually uses it — those were the identical string before. The backend's declared coverage claims that relation rather than over- or under-stating what it emits.

DecisionWhy
Node queries still answer in paths, not edges --impact, --dependents and --dependencies answer "which files". Three other skills feed the result straight into set arithmetic, where an edge object raises unhashable type: 'dict' in a different skill for no gain. Only --query returns edges. Those three skills needed no change at all.
Readers accept both shapes, and the schema version says which graph.json is gitignored, so there is no committed copy to fix in a commit — an older one sits on a machine until something rewrites it, and refusing to read it looks exactly like a project with no dependencies. Schema 1 → 2 is what makes that tolerance temporary rather than permanent.
--update rewrites a legacy artifact even when nothing changed It is the command the steady-state workflow runs, and it short-circuits on "no source changed". Without this the migration would reach almost nobody. Verified on a hand-downgraded copy of this repo's own graph: 419 edges in, 419 out.

What it caught on the way

An exhaustive sweep for readers of the old shape turned up a defect that had nothing to do with edges. behavior-runner asked code-graph for a file's dependency closure and treated any failure of that query as an empty closure — producing a one-file fingerprint tagged static at full confidence, with no warning, written into behavior.json, which is committed. Every later blast radius was then computed against a fingerprint that had quietly lost its dependencies. It is fixed: a failed query and an empty answer no longer share a representation.

Not hypothetical. For about fifteen minutes mid-migration this working tree had --dependencies raising an exception, and anything fingerprinted in that window would have been silently truncated and committed.

Phase 0 — the spike ← short

Five acceptance tests, written before anything was run, against three repos. The blocking one: does graphify lose any edge our resolver currently finds? A lost edge narrows a behaviour's blast radius, the behaviour is not flagged, and a regression walks through the wrap-up gate.

TestResult
9.1 Under-reporting (blocking) pass 0 of 608 missed, 18 gained. All 608 agreed edges independently backed by a real import, so the agreement is not an artifact of how I folded the data.
9.2 Deletion and staleness pass nodes removed, 0 dangling links.
9.3 Reproducibility pass content-stable; drift confined to clustering metadata nothing reads.
9.4 Config coverage mixed SQL and Terraform work behind pip extras. YAML produces nothing and gives no warning.
9.5 Degradation and output pass writes only to its own directory, so ADR-017's revisit trigger does not fire.

The measurement that matters most is not the edge count but the query built on it: across all 232 files, reverse blast radius was identical for 220, larger for 12, and smaller for none.

On the hand-built Java fixture — where our resolver produces nothing at all, so there is no diff to run — graphify scored 11 of 11 against an edge set written down before the tool was run, including the two same-package inheritance edges that no import parser can see, with zero false positives.

9.4 refuted a spec premise

The "config identifier index" idea had been dropped on the grounds that "graphify already parses YAML/JSON/HCL deterministically." It does not parse YAML at all, and JSON only as a package manifest. The conclusion (no config graph) survives on separate reasoning, but that justification cannot be reused.

The resolver repair ← short

The spike was designed to evaluate graphify. Its most consequential finding was about our own code.

freya could not graph itself. Building the graph on freya-devkit produced 10 of 50 Python files and zero internal connections, printed Built dependency graph: 10 files scanned, and exited 0. Because another skill treats "zero connections" as "brand new empty project", freya classified freya as greenfield.

Thirteen defects across two rounds. The ones worth knowing:

DefectEffect
'scripts' was in the always-exclude list, matched at any depth Every skill keeps its code in skills/<name>/scripts/, so 40 files vanished.
Python sibling imports treated as third-party import behavior_graph — a file sitting right there — recorded as an npm-style external package. This alone kept the count at zero even with the first fixed.
import type { X } invisible to the regex 16 real edges missed on the testbed.
Gitignore patterns matched as substrings A .next entry excluded app/api/auth/[...nextauth]/route.ts, because that directory name contains the characters .next. A sibling [...path] route survived, so the hole was invisible until two catch-all routes were compared.
Root-anchored patterns de-anchored /lib also excluded src/lib/ — tracked source, silently absent.
A file could import itself rich/abc.py does from abc import ABC, meaning the standard library. Blast radius walks edges, so a file became its own dependent.

Verified on code neither resolver was written against

Six real libraries from site-packages (jinja2, requests, urllib3, yaml, rich, click — 190 files), old resolver versus new:

Result: freya-devkit went from 10 files / 0 edges to 57 files / 63 edges, and classifies as brownfield. On the testbed, 232 files / 609 edges became 234 / 627 — which also closed the §9.1 gap from 18 extra edges to 1, so the blocking conclusion no longer depends on our resolver being broken.

Why this came before Phase 1, not after

Phase 1's stated safety net was "no behaviour change; the existing test suite is the regression gate." That suite was 18 tests over synthetic fixtures, all green while every one of those defects was live. A refactor pinned by a suite that cannot observe the behaviour preserves nothing — and what would have been frozen into the permanent zero-install floor was an empty graph on freya's own language.

Phase 1 — the contract ← short

ModuleHolds
substrate.pythe contract — coverage, exclusions, the edge-kind vocabulary, conformance and validation. Standard library only, so a backend can depend on it without inheriting anything.
settings.pyknowledge-base/settings.json

Every graph now carries a block naming which backend built it and what that backend can read:

"substrate": {
  "backend": "homegrown",
  "coverage": {
    "languages": ["go", "javascript", "python", "typescript"],
    "extensions": [".go", ".js", ".jsx", ".py", ".ts", ".tsx"],
    "relations": ["imports"],
    "incremental": true
  }
}

That is what distinguishes "this repo has no dependencies" from "this backend cannot read Java" — the confusion that made a Java repo classify as greenfield.

homegrown declares only imports, not the whole vocabulary. It has no notion of a symbol, and claiming calls because the word exists would have a caller trust a query it cannot answer.

Acceptance

The testbed built to 234 files and 627 edges before and after, and §9.1 still reports 0 misses. No behaviour change, measured rather than claimed.

Nine defects found reviewing it, all fixed

  • The committable-artifact bug.
  • A degraded run was announced on stderr and then lost — the artifact never recorded it. Now written into the graph, so a fallback is visible a week later.
  • --clear left a complete copy behind that nothing would report as stale.
  • The backend-selection census ran before every build even though, with one backend, it could not change the answer.
  • Exclusions were never passed by the only production caller, so the obligation the contract documents was unexercised.
  • A workspace glob of packages/** adopted a vendored copy of react as a workspace member — so a genuine third-party import resolved as internal and came back as a missing local file.
  • An absolute path in a workspace pattern crashes on Python 3.9, which CI runs.

Phase 5 — the agnosticism sweep ← short

The greenfield bug, fixed at the root

Zero internal edges means one of two very different things: no wiring yet, or a backend that cannot read the language. It now uses the coverage block to census what is on disk but unread, and returns unknown naming the blind spot:

java fixture  →  unknown | {'.java': 6}
   "0 internal import edges, but the code-graph backend does not read 6 .java —
    this may be an existing codebase the graph cannot see, not a greenfield one."

A graph built before Phase 1 has no coverage block and keeps its old answer, so nothing that currently reads greenfield starts reading unknown.

Phase 4 — the docs graph ← short

Staleness used to be decided by the agent judging which documents corresponded to the changed files — re-made every run, inconsistent, unverifiable. And the reverse question had no answer at all.

That is not hypothetical. Changing how one cache file is written invalidated claims in two documents; both cited the source in prose no tool read, and both were found by grep.

$ freya docs-graph --impact skills/freya-code-graph/scripts/graph_ops.py

docs/architecture.md#output-artifacts
docs/backlog.md#the-wall (cites line 30)
docs/decisions/ADR-005-repair-parsing-substrate-in-place.md#decision (cites line 328)
...

That first hit is exactly the section the working log recorded as invalidated.

On this repo: 35 documents, 170 edges. Everything is parsed, never inferred — a docs graph that guesses is worse than none, because a wrong edge sends someone to rewrite a document that was fine.

Anchored at section, not line

A line number shifts the moment anyone inserts a paragraph. The heading is stable, and it matches the real question: which section is now wrong. The cited line is kept inside the edge as evidence.

A measurement that changed the design

Docs write graph_ops.py:212, not the full path. Measured on this repo: 103 citations are bare filenames against 67 full paths. Requiring a path would have discarded 60% of the graph. Bare names now resolve when exactly one file has that name; anything ambiguous is listed rather than guessed. Zero were ambiguous here.

The chunker was written against the failure mode

A # comment inside a ```bash block is indistinguishable from a heading by pattern alone, and architecture.md is full of ASCII trees and mermaid diagrams a naive splitter would cut in half. So: split only at headings, fences tracked by character and length so ```` can contain ``` verbatim, and the output is a partition that rejoins to the input byte for byte. An unterminated fence is reported rather than silently swallowing every later heading.

Part C — depth, and then the thing underneath it ← short

Excluding a directory by name at any depth is what hid 40 of this repo's files (skills/*/scripts/) and a real Next.js route (app/api/media/generated/route.ts). But removing the names outright indexed the published website's bundled JavaScript and this spike's own planted test fixtures.

So the rule was split: artifact directories (node_modules, dist, .next) excluded wherever they appear, convention directories (docs, examples, generated) only at the repository root, where the convention actually holds.

Your objection

You pushed back: we cannot know what some other project keeps in a folder called docs/, so a default that includes or excludes it everywhere might break a repository neither of us has seen. You proposed scoping the rule to this project only.

I partly disagreed with that mechanism — you cannot identify "this project" without hardcoding a name or a path, and the nested-generated case is a genuine bug fix that helps everyone. And the new rule is strictly more inclusive than the old one, so it cannot cause a missed edge, only noise, which is the safe direction. Then I went to check whether a project could simply override the default, and found it could not.

The real defect. set_classification('docs', 'source') was accepted, written to classifications.json, and then silently overruled — the file filter never consulted classifications at all. So the name lists were not defaults, they were hardcoded answers with no appeal. Your "we cannot know the future" argument was not a reason to scope one rule differently; it was a reason the escape hatch had to exist, and it did not.

What shipped

Verdict sourceOverrides
user Everything, including artifact-tree names and .gitignore. Nothing in the toolkit can know that some repository really does keep source in target/.
ai Root convention names and .gitignore, but not artifact trees. A model guessing "node_modules is source" is a plausible failure; a person typing it is not.
rule / gitignore Nothing. These are the defaults' own output, so letting them override would be circular.

Three separate layers had to agree, and finding that out took three attempts. The file filter. The directory classifier — which re-asserted the rule one level below an override and won, because the ancestor walk preferred the deepest verdict and a stale cached one from an earlier build sat deeper than the override. And the exclusion set the CLI passes back into build(), assembled from the same .gitignore, which undid the override a step later. Overrides therefore travel on the contract itself, so a Phase 2 backend that has never heard of classifications.json honours them too.

Precedence is now one sentence: a stated verdict beats a derived one at any depth, and among equals the deepest wins.

scripts also went back to being excluded at the repo root. Dropping the name outright was the wider change — a root scripts/ had been excluded in every project this toolkit had ever run on, and un-excluding it everywhere to fix one repo's nested skills/*/scripts/ changed the answer for projects that had asked for nothing. Top-level-only restores the old behaviour at the root and keeps the fix below it.

Judgement call — what --clear keeps ← short

--clear now removes every backend's graph copy, which it previously did not — a leftover copy is worse than a missing one because it looks current and nothing reports it.

It still keeps classifications.json. That file holds judgements you and the model made about which directories are source; a cache clear has no business discarding them. Rule-derived verdicts inside it are invalidated automatically when the rules change, via a version stamp — which is itself a fix, because without it a rule change only ever reached a fresh clone.

Judgement call — where settings live ← short

You rejected a freya.json in the project root. Three properties were needed at once: it must survive a clone, it must not be lost when the cache is cleared, and it must not add a file to your root. knowledge-base/settings.json satisfies all three — only knowledge-base/.graph/ is gitignored, so a file beside specs/ and decisions/ is committed by default.

Not package.json: Java, Python and Go repos do not have one, and keying the polyglot toolkit's own configuration to a Node manifest is exactly the assumption Track B exists to remove. Worth supporting later as an optional override for Node projects; never as the home.

Process — I introduced a bug while fixing bugs ← short

The commit that fixed six review findings added a seventh: main() began calling project_exclusions() on the selected backend — a method the contract never mentions. Any second backend would crash on it.

The useful lesson is not "be more careful". It is that nothing checked the call. The conformance check verified that build existed and was callable, which is not a contract — a backend can pass both and still be uninvokable. The contract now states the exact keywords it passes and binds against the real signature. That check caught our own reference stub, the one docstring'd "a minimal conforming backend" and asserted conforming by a green test, the moment it was added.

Process — review agents that wrote ← short

In the first review run, an agent edited the file it was reviewing. I found it in git diff, audited it out line by line, and rewrote that logic myself. Its change was substantively right, which is the uncomfortable part: a plausible, correct-looking change arrived in the working tree unreviewed, and the synthesis then reported it back as "already fixed" — evidence about a tree nobody had approved.

A second agent deleted four tracked markdown files from the testbed repo. git status caught it; git checkout -- restored them. The testbed is back to exactly its prior state.

Every later review ran with an explicit read-only constraint and scratch work confined to /tmp. Worth remembering if these workflows get reused: review agents that can write are not reviewers.

One further caution. An automated pass reported "0 lost, 0 gained" on six libraries — an artifact of its two sides sharing state. Re-run properly the real figure was +688 gained. Two other numbers I repeated from an agent without checking were also wrong. Everything in these pages has been re-measured.

Process — the committable file ← short

The cache directory writes its own .gitignore. That writer only ever upgraded the old blanket * version, so any project that had run a single build kept its existing list — and the new per-backend artifact, added on top, arrived un-ignored.

Verified against real git before and after: git add -A staged graph.homegrown.json. The writer now recognises any version of the file it has ever produced and upgrades that, while still leaving a hand-edited one alone.

Related, and the reason this class of bug recurs: the two skills that write this file each carried a copy of the content with a comment saying they must stay identical. They had already drifted. There is now a test comparing the produced strings.
