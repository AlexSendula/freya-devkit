Track B · the polyglot substrate

The decisions

Twenty-seven decisions, each with the alternative it beat. The rejected branch is the part that is never in a diff, which is why it is written down here.

These are recorded in ADR shape as they were taken, not reconstructed at the end. The last restructure of this repository had to rebuild "what did we decide and what did we reject" from fifty-one documents plus a diff, and it took a day. This is the answer to that.

The shape of the thing

CD-1 · the substrate is a contract, not a tool

Decided. freya-code-graph defines a contract. Any backend that satisfies it can produce the code graph.

Why. The old resolver covers four languages and cannot be extended to Java without becoming a parser. But choosing a replacement tool means choosing again in a few years, and every consumer would move with it each time. The contract makes the choice configuration instead of architecture.

Rejected: pick graphify and wire it in directly — fastest to ship, and it reopens the whole question the first time graphify stalls, by which point five skills depend on its output shape. Extend the homegrown resolver per language — keeps the zero-install property, but Java needs a real parser and hand-rolling one was already named as the thing to stop doing.

Revisit if: a third backend turns out to be expensive rather than cheap to add. That would mean the contract leaked assumptions from its first two implementations.

CD-2 · two backends ship, and the homegrown one is the floor

Decided. homegrown stays installed by default and stays the default. graphify is opt-in because it is a dependency.

Why. Two reasons, and the second is load-bearing. An interface with a single implementation is fiction. And the driving case for Track B is a locked-down work laptop — if policy blocks installing a Python package, graphify never runs in the one environment this exists to serve.

Rejected: replace homegrown entirely once graphify works — less code, one path, and it makes the zero-install property depend on a third-party package. Keep homegrown only as a spike reference and delete it after — its value as a diff target expires; its value as a floor does not.

Revisit if: graphify ever ships as a single self-contained binary with no install step. The floor argument weakens considerably.

CD-3 · three artifacts joined on file path, no linking graph

Decided. graph.json (code), behavior.json (behaviour → test → code) and docs.json (doc section → code), each with one producer, joined on file path.

Why. Different producers, different dependencies, different failure modes. graphify may be absent; a test suite may be red; the markdown parser needs nothing. If one combined file degraded, a caller could not tell which half survived. A linking graph would be an empty table, because every artifact already speaks file paths.

Rejected: one merged graph — simplest to query, rejected on producer isolation. Unify the code graph and the behaviour graph — this was the recorded lean from an earlier session, and it is dropped.

CD-16 · a backend declares languages and relation kinds

Decided. The coverage block names both what it parses and which relation kinds it can emit.

Why. Languages alone answer "can you see this repository at all" — the headline failure. Relation kinds answer the finer question: blast radius wants import edges, and a query needing symbol-level calls should be able to degrade by itself rather than distrust the whole graph.

Rejected: languages plus extensions, no relation kinds — the simpler option, and it defers the edge-kind vocabulary to Phase 3 where it becomes a migration rather than a definition.

CD-17 · graphs are stored per backend, side by side

Decided. Each backend writes graph.<backend>.json. Switching backends does not overwrite the previous graph.

Why. A substrate swap is supposed to be a measured migration — diff before trusting. That is impossible if the new graph destroys the old one, because the baseline is gone at exactly the moment it is needed. The spike hit this directly.

Rejected: one graph.json, overwritten — matches today, and makes the mandated comparison cost a full rebuild of the backend you just replaced. A stashed graph.previous.json — cheap one-hop comparison, but it cannot hold two backends current, which is what validating a fallback needs.

CD-19 · the contract persists the graph; a backend only produces it

Decided. build() and update() return a Result. The contract derives dependents, validates, and writes both artifacts.

Why. Linking, validating and writing all lived inside the incumbent resolver, so a second backend built strictly to the contract produced nothing and reported success. Demonstrated rather than argued — see the verdict on Phase 1.

Rejected: leave persistence in each backend and document what it must do — a contract enforced by documentation is precisely what the review found. The second backend satisfied every documented obligation and still wrote no file.

What it cost: roughly forty tests called CodeGraph.build() directly and asserted on its return value — which meant the suite had never once exercised the path production uses. They all go through the runner now.

CD-23 · auto is the floor; any other backend is opt-in

Decided. auto resolves to the floor and does not go shopping. Naming a backend in settings.json is the opt-in.

Why. Scoring silently means installing a binary anywhere on PATH changes the substrate — and every blast radius — for every project on the machine at once, with no diff. Not hypothetical the moment a second backend existed: graphify scored 63 to homegrown's 58 here and would have taken over on the next build.

Rejected: keep scoring (above). A separate substrate.allow list — more machinery for the same answer. Silence when a better backend is available — opt-in must not mean undiscoverable.

This one supersedes behaviour that had already shipped in Phase 1, and was later refined by CD-26 — auto still never scores, but it now defers to an answer the engineer gave once.

CD-26 · the backend is chosen once, at install, and recorded per project

Decided. freya install asks, in a numbered menu. freya update asks too. The answer is the machine-level default in ~/.freya/settings.json; precedence is project, then machine, then floor; and the first build in a project records the machine answer in that project's own committed settings.json.

How it came up. Raised by the engineer, not by the plan. CD-23 made naming a backend the opt-in and never said how anyone was supposed to do that — and the answer turned out to be by hand. settings.write() existed with zero production callers; its own docstring said the file "is created when they ask for it", and there was no way to ask. The only discovery path was a stderr hint that fires when the other backend is already installed, so you had to own the thing before being told you might want it.

Why install, of four candidate moments. code-graph auto-enables non-interactive mode whenever stdin is not a TTY — which is every agent-driven run and every wrap-up, which is to say the workflow. A terminal prompt there fires almost exclusively for someone typing the command by hand. Install is the one moment a keyboard is guaranteed, and it is run deliberately. That update asks as well is the whole migration story for anyone installed before the question existed: no version check and no migration command, because "has this machine answered?" is the only state that matters.

Why the project file is the load-bearing half. A machine default left implicit would mean the same commit graphs differently on a machine that has one and a machine that does not — and integration behaviours' static fingerprints come from the code-graph closure into behavior.json, which is committed. That divergence would arrive as a diff reading like behaviour drift. Writing it down makes the repository self-describing, which is the property CD-15 exists for.

Rejected: ask through the agent, via the deferred-prompt protocol — needs_classification() / get_classification_prompt() / classify_with_ai_response() already exist for exactly this shape, and have no CLI flag and no caller, the fourth instance of this codebase writing an API whose effect does not exist. Finishing it would have been the bulk of the work and buys nothing here: the question is per machine, and install is a better place to ask a per-machine question than the middle of somebody's commit. The instruction telling the agent to ask would also live in the skill layer, read on every invocation to say nothing on almost all of them — a standing token cost for a question asked once per machine. The protocol is still the right answer for directory classification, which is genuinely per project and still stuck.

What an edge may say

CD-4 · provenance decides what may block

Decided. Every edge carries extracted or inferred. Only extracted edges may gate wrap-up.

not implemented The field is recorded; the filter does not exist. No production code anywhere reads an edge's provenance, so an inferred edge reaches blast radius indistinguishable from an extracted one. Found by the final review, which is late — this was written in present tense in the spec, here, and in the explainer, and none of it was true. The exposure is small (over-approximating is the safe direction, and two file pairs on this repository rest solely on inferred links) and the discrepancy is not.

Why. Adopting a name-resolving backend introduces a new failure mode: syntactic substrates mis-wire across languages, linking Python's sorted() to a Swift func sorted. That is confidently wrong rather than confidently empty — worse, because blast radius blocks commits.

Rejected: discard inferred edges entirely — this was the first recommendation. The objection was that inferred edges should not block, which argues for labelling them, not for throwing away real signal.

CD-20 · an edge is an object, and the schema is versioned

Decided. {"to": …, "kind": …, "provenance": …}, and {"from": …} going backwards. Schema 1 → 2.

Why. A bare string carries exactly one fact. Measured against the spike's own numbers: 2,102 of graphify's 5,027 links expressible, 58% not. And obligation 3 mandates per-edge provenance, which validation made literally impossible — it required each entry to be a plain string.

Rejected: file-level, honestly — drop the three symbol kinds and strike provenance from Phase 2. Cheapest, and it gives up most of what the second backend knows to avoid a migration that only gets more expensive. Defer to Phase 3 — matches the original plan, but then Phase 2 promises provenance it cannot deliver. Keep strings and add a parallel edges key — zero downstream risk, and two representations of one fact that drift. This repository has been bitten by exactly that.

Two boundaries drawn at the same time, both load-bearing: node queries still answer in paths, so three other skills needed no change at all; and readers accept both shapes, because graph.json is gitignored and refusing to read an old one is indistinguishable from a project with no dependencies.

CD-6 · symbols refine file anchors; they never replace them

Decided. Edges anchor on a file path with an optional symbol. Present, you get precision; absent or stale, it degrades to exactly today's behaviour.

Why. Symbol-level is sharper — "this function changed, these three callers care" beats "this file changed, these twelve importers care". But symbol names are not durable identifiers, and this project already learned that: behaviours carry stable BEH-NNN ids precisely because titles and filenames are not. Rename a function and a symbol-only anchor breaks silently — and behavior.json is committed, so a broken anchor becomes a diff someone has to resolve.

Rejected: fold symbol edges down and discard the detail — cheap, and it throws away precision the backend already computed for free. Move wholly to symbol anchors — sharpest, and it makes every rename a breaking change to a committed artifact.

CD-24 · symbols refine an edge, and are off by default

Decided. from_symbol, to_symbol and line, behind substrate.symbols, default off.

Why off: measured, 73 file-level edges become 417 — a test module calling one helper sixty times is sixty symbol pairs and one dependency. Nothing downstream reads them yet.

Rejected: symbols as graph nodes — that is a different graph, and it breaks every consumer that joins artifacts on file path.

CD-25 · a behaviour's symbols come from coverage, never from the graph

Decided. They come from the istanbul coverage report: fnMap names each function, f counts its executions. Executed and named only.

Why. observed means "the test ran this". Graph symbols would mix in things nobody executed — the difference between measurement and inference, which is the distinction the whole trust model rests on.

Rejected: one exercise entry per symbol — behavior-graph intersects exercises[].path against the impact set, and splitting the entry changes that set's cardinality and every count derived from it. Bump behavior.json's version — it is written and read by nobody; the real compatibility guarantee is that an entry with no symbols is byte-identical to one from before this existed, and that is asserted.

Recorded rather than reinterpreted: the spec asks to "thread it through the fingerprint comparison", and nothing in the toolkit compares two fingerprints' exercise sets. That is written down as a gap rather than quietly redefined into something that does exist.

CD-22 · graphify's symbol graph is projected onto file pairs, and three relations are dropped

Decided. Every link is projected onto the file pair its endpoints live in. The mapping table is derived from counting what each relation actually connects, not from its name. contains, method and rationale_for — 2,861 links, all 100% intra-file — are dropped.

Rejected: adopt rationale_for as a docs graph — it is not one. It is a docstring index and cannot express a relationship between two files. Default unknown relations to references — a silent fallthrough would make an upstream capability arrive as a graph that merely looks thin. Keep intra-file calls as self-edges — verified: one self-edge makes --impact report a file as its own direct dependent.

The consequence that mattered: a node marked type: module is an external module, not a file, and reading it as one fabricated edges.

Scope and configuration

CD-11 · exclusions belong to the contract

Decided. Excluded directories are a project-level input the caller passes in. A backend never decides for itself what is out of scope.

Why. "vendor/ is not mine" is a property of the project, not of the parser. Left to the backend, graphify would graph vendor/ and generated output while homegrown did not — two backends disagreeing about scope on the same repository is worse than either behaviour alone.

CD-15 · project settings live in knowledge-base/settings.json

Decided. Committed, travelling with the repository, outside the project root.

Why. Three properties at once: survive a clone, survive a cache clear, and do not add a file to the project root.

Rejected: freya.json at the repo root — proposed first and rejected: it pollutes the root of every adopting project for a tool that already owns a directory. Extend classifications.json — that path is gitignored regenerable cache, so configuration there would not survive --clear and would not reach a fresh clone. A "freya" key in package.json — fine for Node, and keying the polyglot toolkit's config to a Node manifest is exactly the assumption Track B exists to remove.

CD-21 · the exclusion defaults are arguable

Decided. A project can override any built-in exclusion, in settings.json, in two tiers of authority.

How it came up. Raised by the engineer, not by the plan: we cannot know what some other repository keeps in a folder called docs/. The proposed fix was to scope the rule to this project only — not implementable without hardcoding a name or a path. Checking whether a project could simply override the default found the real defect: set_classification('docs', 'source') was accepted, written to disk, and then silently overruled, because the file filter never consulted classifications at all.

So the name lists were not defaults. They were hardcoded answers with no appeal, and a wrong one was unfixable. That was a wider defect than the one originally raised, and it had been live since the API was written.

CD-18 · workspace packages resolve in the homegrown backend

Decided. The floor reads workspaces from package.json and resolves cross-package imports internally, rather than waiting for graphify.

Why. In a monorepo the cross-package edge is the architectural edge. Measured: apps/mobile importing @acme/domain resolved to external:@acme/domain — the toolkit reporting the most important relationship in the repository as a third-party dependency. And a floor that collapses on the layout the immediate real target uses is not a floor.

CD-12 · the dead category field is removed

Decided. The per-file category (auth/api/ui/…) was computed on every build and read by nothing. Three unrelated things in this repository are called "category" and the other two are live, which is why it looked load-bearing. Recorded rather than deleted silently, because silent deletion is how someone later reintroduces it.

CD-27 · blind spots ride in the answer, and never become a refusal

Decided. Every build records the in-scope source files its backend could not read at substrate.unmapped_source, with the directories to search instead. --build, --update, --query and --impact carry it in the answer; the two surfaces that reply with a bare array say it on stderr. The key is absent when there is nothing to say.

How it came up. Raised by the engineer: could a user believe a project is 80% covered when it is 30%? Worse than that. A repository of 12 .java and 3 .ts files builds, prints "Found 3 source files" and exits 0 — the Java files are not skipped, they are never enumerated, because the scanner globs by the extensions the backend reads. files_scanned reads like a denominator and is a numerator. Asked what shape that repository is, the toolkit answered brownfield, source_files: 3 and runtime: jvm in one evidence block, without ever noticing the two were in tension.

The reframing was the engineer's, and it was the better design. The consumer here is not a person — --non-interactive auto-enables whenever stdin is not a TTY, which is every agent-driven run and every wrap-up. The first proposed fix was to print a census, which repeats the exact mistake CD-26 exists to correct: putting the signal where nobody is standing. The right channel was already in this codebase — get_impact returns not_in_graph in the payload, with a comment saying stderr is not part of what a caller parses. That argument had only ever been applied to "the file you asked about is unmapped", never to "this answer is incomplete".

Why it is never a refusal. degraded_from means the project asked for a backend and did not get one — abnormal, and behaviour fingerprinting rightly declines to answer. Blind spots are the floor's normal condition on any polyglot repository. Routing them through the same door would return coverage: unknown for every integration behaviour on every such repo, freeze the committed behavior.json, and take wrap-up's gate green over zero behaviours. The rule is written into the source beside the refusal it must not join, and a named test fails if anyone joins them.

Rejected: wrap --dependencies in an envelope — its one consumer validates isinstance(data, list), so it would break closed, into a repo-wide silent green rather than a loud failure. Bump the schema version — forces a rebuild everywhere, and that rebuild changes the closures written into the committed behavior.json; a files: 0 sentinel in a gitignored file discriminates just as well for thirty bytes. Reuse the existing summarise_coverage() — its blind-spot helper has no dotfile guard, no materiality filter and no notion of project scope; the aggregation was never the missing half, the scope rule was. It was deleted rather than wired.

The measurement that set the filter. A census keyed on gitignore-style patterns reports 96 unread files on this repository, 68 of them deliberately out of scope — a 71% phantom. A caveat that cries wolf is worse than no caveat, because an agent learns to skip the field and then misses the one time it was real.

What the review then found. Two of the silences originally cited as evidence the filter was quiet enough were not evidence at all. One was an empty directory. The other was a real 40-file deployment repository whose entire codebase is shell scripts under scripts/ — a built-in exclusion, so the census honestly reports nothing unread, and the shape detector then called it greenfield. That is ADR-005's confidently-empty answer arriving through the feature built to remove it, via the same scripts/ rule that once stopped freya graphing itself. The census's silence is no longer treated as authoritative: it answers "what can this backend not read?", which is a narrower question than "is there anything here the graph does not represent?"

What we will not build

CD-9 · no graph for config-as-code

Decided. No resource graph, no config identifier index, no Helm support, no HCL parsing.

Why. A graph earns its place on transitive closure, and config relationships are one hop that never branches. And nothing consumes the answer: changing lib/auth.ts and learning it eventually lands in a container image does not change which docs are stale or which behaviours to re-run.

Revisit if: a concrete question arrives with a caller that only a resource graph can answer. Absent a caller, no.

CD-10 · schemas are code; migrations are not graph material

Decided. schema.prisma, *.sql, JPA entities and Django models are graphed as code — they define types code depends on, usually through a generated client, which is a genuine import chain. Migrations are an ordered append-only log: a chain, not a DAG. Where a project has only migrations, the current schema is emitted as unresolved rather than derived by folding them, because folding means executing.

CD-7 · the docs graph exists, anchored at section

Decided. docs.json records doc-section → code-file edges, parsed from citations, relative links and related_code: frontmatter.

Why. The edge already existed conceptually and was re-derived by model judgment on every run — inconsistent between runs and unverifiable after them. And the reverse query had no answer at all. That is not hypothetical: changing how one cache file is written invalidated claims in two documents, both of which cited the source in prose no tool reads, and both were found by grep.

CD-8 · markdown is chunked structurally, never by size

Decided. Split only at heading boundaries; every fenced block, table and HTML block is atomic. Rejected: chunk by line count or token budget — standard in RAG pipelines, trivial to implement, and guaranteed to cut a mermaid diagram in half on this repository's own docs. The precedent is exact: a naive regex JSONC stripper once mis-read /* inside the string "@/*".

CD-5 · the semantic pass runs on the engineer's own subscription

Decided. graphify's model-driven pass is opt-in and off by default. When enabled it runs through the driver pattern the toolkit already owns — claude -p, copilot -p — never a separate API key. Rejected: require an API key — it adds a cost and a credential to a toolkit that has neither. Make the pass mandatory — everything it produces is inferred, so nothing that gates depends on it; mandatory spend for advisory output is the wrong trade.

How the work was run

CD-13 · the substrate change is a measured migration

Decided. No substrate is adopted on argument. Five acceptance tests, three repositories, and the blocking criterion is under-reporting.

Why. Misses are asymmetric. A missing edge narrows a behaviour's static closure, so the behaviour is not flagged, so a regression passes the gate. A spurious extra edge only runs a test that was not needed. Only measurement distinguishes them — and the tests are a gate on adoption, not a one-off: any future backend passes the same five before becoming a default.

CD-14 · repair the resolver before freezing it behind the contract

Decided. Phase 1 did not begin with the refactor. It began by fixing the resolver defects the spike found, adding real-repository regression tests, and re-running the blocking gate against the corrected baseline.

Rejected: refactor first, fix behind the contract afterwards — this was the spec's stated order and it is defensible, since a contract is backend-agnostic. Rejected on sequencing only: it validates the contract against a floor known to be broken, and re-runs the gate against a moved baseline.

Still open

QuestionStatus
Does the extracted/inferred split earn its two-tier machinery at file granularity? Unresolved, and now known to be unenforced. Two file pairs on this repository rest solely on inferred links, so the tier is at least exercised — but no code filters on it, so "inferred edges never gate" is a design intention rather than a property. Either implement the filter or strike the promise; measuring first is what decides which.
exports is empty under graphify, and no external: edges are emitted for TS/JS/Python Both are upstream limitations rather than projection bugs, and the coverage declaration has no vocabulary for "does not emit exports". Recorded in the schema reference. It becomes real the moment something depends on the field.
graphify's cache keys on mtime and AST hash only — no tool version, no extras set — so upgrading it invalidates nothing Unaddressed. The same defect class as the one this repository already fixed with a rules version stamp.
Is a ~9.3 KB-per-file artifact acceptable at scale, given every skill loads it per invocation? Untested past a few hundred files. A 5,000-file repository implies roughly 46 MB.
Does running a pre-1.0, single-maintainer dependency recursively over a whole codebase need a supply-chain position before it is recommended into other people's repositories? No position taken.
The intra-file call graph — 1,516 links on this repository A deliberately discarded capability. Recording it needs a node type the contract does not have.
